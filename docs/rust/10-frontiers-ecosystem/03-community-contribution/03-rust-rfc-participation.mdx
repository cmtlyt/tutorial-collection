# 参与 Rust RFC 讨论

> **版本**：v1.0  
> **最后更新**：2026-04-23

## 📚 概念介绍

RFC（Request for Comments）是 Rust 语言演进的核心机制。所有重要的语言特性、标准库变更和工具链改进，都需要经过 RFC 流程。这是一个公开、透明的设计决策过程，任何人都可以提交 RFC 提案或参与讨论。了解 RFC 流程不仅能帮助你跟进 Rust 的最新发展，还能让你直接参与到语言设计中来。

### RFC 的意义

- **透明决策**：所有重大变更都有公开的设计文档和讨论
- **社区驱动**：任何人都可以提交提案，不限于核心团队
- **深思熟虑**：强制性的书面讨论确保设计经过充分考虑
- **历史记录**：每个 RFC 都是设计决策的永久记录

## 🎯 RFC 生命周期

```
RFC 完整生命周期
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ Pre-RFC  │ →  │  提交    │ →  │ 讨论期   │ →  │ FCP      │ →  │ 接受/    │
│ 非正式   │    │ Pull     │    │ 社区反馈 │    │ Final    │    │ 拒绝/    │
│ 讨论     │    │ Request  │    │ 修改完善 │    │ Comment  │    │ 推迟     │
└──────────┘    └──────────┘    └──────────┘    │ Period   │    └──────────┘
                                                └──────────┘
                                                  10 天

状态说明：
  - Pre-RFC：在论坛/Zulip 上非正式讨论想法
  - 提交：正式提交 PR 到 rust-lang/rfcs 仓库
  - 讨论期：社区成员和团队成员提供反馈
  - FCP：最终评论期（10 天），团队成员投票
  - 接受：合并 RFC，进入实现阶段
  - 拒绝/推迟：关闭或暂缓
```

## 🔑 RFC 文档结构

### 标准 RFC 模板

```rust
fn describe_rfc_template() {
    let template = r#"
# RFC 标准模板结构

- Feature Name: (填写特性名称，如 `impl_trait_in_bindings`)
- Start Date: (填写提交日期)
- RFC PR: rust-lang/rfcs#0000
- Rust Issue: rust-lang/rust#0000

## Summary (摘要)
用一段话简要描述此 RFC 的提议。

## Motivation (动机)
为什么我们需要这个特性？它解决了什么问题？
提供具体的使用场景和现有的痛点。

## Guide-level explanation (面向用户的解释)
像教程一样解释这个特性。
- 引入哪些新概念？
- 用代码示例展示如何使用。
- 对不同用户群体有什么影响？

## Reference-level explanation (面向实现的解释)
详细的技术规范：
- 与语言其他部分的交互
- 边界情况处理
- 错误消息设计

## Drawbacks (缺点)
为什么我们不应该这样做？

## Rationale and alternatives (理由和替代方案)
- 为什么这个设计是最佳选择？
- 考虑了哪些替代方案？
- 不实施此特性会怎样？

## Prior art (先例)
其他语言/系统如何解决类似问题？

## Unresolved questions (未解决的问题)
在 RFC 合并前需要解决的问题。

## Future possibilities (未来可能性)
此 RFC 未来可能的扩展方向。
"#;

    println!("{template}");
}

fn main() {
    describe_rfc_template();
}
```

## 🔑 如何有效参与讨论

```rust
fn describe_participation_tips() {
    println!("=== 参与 RFC 讨论的建议 ===\n");

    println!("✅ 推荐做法:");
    println!("  1. 先完整阅读 RFC 文本和已有讨论");
    println!("  2. 提供具体的使用场景和代码示例");
    println!("  3. 指出可能遗漏的边界情况");
    println!("  4. 建设性地提出替代方案");
    println!("  5. 引用其他语言的相关经验");
    println!("  6. 保持尊重和建设性的态度\n");

    println!("❌ 避免的做法:");
    println!("  1. 仅表达 +1 / -1 而不提供理由");
    println!("  2. 未阅读全文就发表意见");
    println!("  3. 偏离主题的讨论");
    println!("  4. 人身攻击或不尊重他人");
    println!("  5. 重复已经提出过的观点\n");

    println!("💡 高质量评论示例:");
    println!("  '这个提案在 X 场景下可能会遇到问题：'");
    println!("  '我在生产环境中遇到了类似需求，'");
    println!("  '目前的 workaround 是..., 但存在以下问题：'");
    println!("  '替代方案 Y 的优点是..., 但缺点是...'");
}

fn main() {
    describe_participation_tips();
}
```

## 🔑 Rust 团队结构

```
Rust 项目治理结构
├── Leadership Council     — 顶层治理委员会
├── Compiler Team          — 编译器开发
├── Language Team           — 语言设计（负责 RFC 决策）
├── Library Team            — 标准库
├── Cargo Team              — Cargo 包管理器
├── Dev Tools Team          — 开发工具（rustfmt, clippy 等）
├── Release Team            — 发布管理
├── Infrastructure Team     — 基础设施
├── Docs Team               — 文档
└── Community Team          — 社区管理

团队参与 RFC 的方式：
  - 相关团队成员审阅 RFC
  - 团队成员发起 FCP（最终评论期）
  - 通过团队内部投票决定接受/拒绝
```
