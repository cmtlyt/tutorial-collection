# Web3 与去中心化

> **版本**：v1.0
> **最后更新**：2026-04-24

## 📖 概述

Web3 是一个承载诸多理念的宽泛术语，核心主张是："用户拥有自己的数据、身份和资产，不依赖单一中心化机构"。其技术底座是区块链、去中心化存储、密码学身份等。作为架构师，不必追逐所有 Web3 热点，但需要理解其底层机制、能够评估特定场景是否适合"去中心化"范式，以及识别炒作与真实价值。本文从区块链基础架构、去中心化存储、智能合约架构三个方面展开。

## 🎯 学习目标

- 理解区块链的底层架构组成与主要共识机制
- 了解 IPFS 等去中心化存储的原理与适用边界
- 掌握智能合约的开发模式、部署结构和常见安全风险
- 能够判断一个业务是否真的需要去中心化，还是伪需求

## ⛓️ 区块链基础架构

### 核心组成

```
┌─────────────────────────────────────────────┐
│  应用层（DApp）                              │
│   钱包、DeFi、NFT 市场、游戏                 │
└──────────────────┬──────────────────────────┘
                   │ RPC / SDK
┌──────────────────▼──────────────────────────┐
│  智能合约层（On-Chain Logic）                 │
│   Solidity / Rust / Move 编写的业务逻辑      │
└──────────────────┬──────────────────────────┘
                   │ 调用 / 事件
┌──────────────────▼──────────────────────────┐
│  执行层（Execution Layer）                   │
│   EVM / WASM / Move VM                      │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│  共识层（Consensus Layer）                   │
│   PoW / PoS / DPoS / BFT 类                 │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│  网络层（P2P Network）                       │
│   Gossip 协议、节点发现、区块广播            │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│  存储层（State / Block Storage）             │
│   LevelDB / RocksDB + Merkle Patricia Trie  │
└─────────────────────────────────────────────┘
```

### 主要共识机制

| 机制 | 代表项目 | 优点 | 缺点 |
|------|---------|------|------|
| **PoW（工作量证明）** | Bitcoin | 安全性高，抗攻击 | 能耗极大，TPS 低 |
| **PoS（权益证明）** | Ethereum（合并后） | 能耗低，效率高 | "富者更富"问题 |
| **DPoS（委托权益证明）** | EOS、Tron | 高 TPS，出块快 | 去中心化程度较低 |
| **PBFT 类（拜占庭容错）** | Hyperledger、Cosmos | 确认快、最终性强 | 节点数受限 |
| **PoA（授权证明）** | 联盟链常用 | 高效、可控 | 中心化倾向 |

### 性能维度对比

| 维度 | Bitcoin | Ethereum L1 | Solana | 主流联盟链 |
|------|---------|------------|--------|-----------|
| **TPS** | 7 | 15~30 | 数千 | 数千~万 |
| **确认时间** | 60 分钟 | 15 分钟 | 秒级 | 秒级 |
| **节点规模** | 数千 | 数千 | 数百 | 几十 |
| **去中心化** | 极强 | 强 | 中 | 弱 |

### 扩展性方案：分层架构（L1 + L2）

为解决公链 TPS 瓶颈，业界共识是**分层**：

```
L1（主链）— 安全、结算、最终性
  │
  ▼
L2（扩展层）— 高 TPS，周期性将状态锚定回 L1
  │
  ├─ Optimistic Rollup（Optimism、Arbitrum）
  ├─ ZK-Rollup（zkSync、StarkNet）
  ├─ Validium / Volition
  └─ State Channel / Plasma（渐冷）
```

**Rollup 核心思想**：大量交易在 L2 打包 → 生成证明（欺诈证明 / 有效性证明）→ 定期提交到 L1，继承 L1 的安全性。

## 🗄️ 去中心化存储

### 为什么需要

链上存储**非常昂贵**（Ethereum 每字节数美元级），且不适合大文件。去中心化存储解决"大文件 + 可验证 + 抗审查"的需求。

### 主流方案

| 方案 | 定位 | 原理 |
|------|------|------|
| **IPFS** | 内容寻址网络 | 按内容哈希寻址，节点自愿缓存 |
| **Filecoin** | IPFS 的激励层 | 通过代币激励节点长期存储 |
| **Arweave** | "永久存储" | 一次付费永久存储，区块编织结构 |
| **Sia / Storj** | 加密分片存储 | 文件切分加密后分散存储 |

### IPFS 工作原理

```
文件 F
  │
  │ 切块（默认 256KB）
  ▼
块 B1, B2, B3 ...
  │
  │ 每块取 SHA-256 哈希
  ▼
CID（Content IDentifier）— 形如 "QmXxx..." 或 "bafy..."
  │
  ▼
用 CID 通过 DHT 查找拥有该块的节点
  │
  ▼
从就近节点并发拉取并组装
```

**关键特性**：
- **内容寻址**：同一内容哈希相同，天然去重
- **不可变**：改内容就是新文件（新 CID）
- **按需缓存**：节点可 `pin` 关心的内容，其他内容可回收
- **无内建激励**：想长期存储需要自己 pin 或用 Filecoin

### 实际使用模式

**模式 1：链上存哈希，链下存数据**（最常见）

```
业务数据  ──▶  IPFS / Arweave  ──▶ 返回 CID
                                      │
                                      ▼
                                  智能合约存 CID
                                  （几十字节，便宜）
```

**模式 2：内容平台的去审查发布**

用户内容发布到 IPFS，域名通过 ENS 解析到 CID，绕开传统 DNS 与中心化平台。

**模式 3：NFT 元数据存储**

```
NFT Token (链上)
   │ tokenURI
   ▼
ipfs://Qm.../metadata.json  (IPFS)
   │ image
   ▼
ipfs://Qm.../artwork.png    (IPFS)
```

避免元数据被中心化服务器篡改或删除。

### 边界与陷阱

- **"永久"是相对的**：IPFS 本身不保证永久，无人 pin 的内容会消失
- **隐私**：默认公开可寻址，敏感数据需先加密
- **检索效率**：冷门 CID 的首次拉取可能耗时数秒到数十秒
- **网关依赖**：Web 端常通过 `https://ipfs.io/ipfs/...` 网关访问，反而引入中心化

## 📜 智能合约架构

### 什么是智能合约

运行在区块链虚拟机（EVM、WASM、Move VM）上的**不可变代码**，由交易触发执行，状态变更进入区块。特点：

- **代码即法律**：部署后基本不可改（除非预留升级机制）
- **确定性**：同一输入必须得到同一输出（禁止随机、时间戳不可靠）
- **Gas 付费**：每个操作有成本，需防止"可变长循环"消耗无限 Gas
- **公开可读**：源码 verify 后人人可查

### 主流合约平台

| 平台 | 语言 | 执行环境 |
|------|------|---------|
| **Ethereum + EVM 系** | Solidity、Vyper | EVM |
| **Solana** | Rust、C | Sealevel 运行时 |
| **Polkadot / Near / CosmWasm** | Rust、AssemblyScript | WebAssembly |
| **Aptos / Sui** | Move | Move VM |
| **Hyperledger Fabric** | Go、Node.js、Java | Chaincode |

### 架构模式

#### 1. Proxy 升级模式（Transparent / UUPS Proxy）

合约部署后不可变，但业务逻辑需要迭代，所以有了"代理合约 + 逻辑合约"模式：

```
用户调用 ──▶ Proxy (地址不变)
                │
                │ delegatecall
                ▼
             Logic V1  ──(升级)──▶ Logic V2
```

- Proxy 持有**存储与地址**
- Logic 合约只包含**代码**，可替换
- 需要严格管理存储布局兼容性

#### 2. Diamond 模式（EIP-2535）

把合约拆成多个 Facet（切面），按函数选择器路由到不同 Facet，突破单合约字节码大小限制，支持模块化升级。

#### 3. 工厂模式

一个工厂合约批量部署同类子合约（例如 Uniswap 为每个交易对部署一个 Pool 合约）。

### 合约安全的常见坑

| 漏洞 | 说明 | 防御 |
|------|------|------|
| **重入（Reentrancy）** | 外部调用过程中被重入，如 DAO 事件 | Checks-Effects-Interactions 模式 + ReentrancyGuard |
| **整数溢出** | 溢出导致状态错乱 | Solidity 0.8+ 默认 revert；或用 SafeMath |
| **权限错误** | 敏感函数缺 `onlyOwner` | 明确的访问控制 + 多签 |
| **预言机操纵** | 价格源被瞬时操纵 | TWAP、Chainlink 等去中心化预言机 |
| **前向可见性（MEV）** | Mempool 交易被抢先 | 私有交易池、提交-揭示 |
| **逻辑漏洞** | 业务逻辑本身错误 | 形式化验证、审计、测试网灰度 |

### 合约示例（Solidity）

一个带访问控制和重入保护的简化金库合约：

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts/access/Ownable.sol";
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract Vault is Ownable, ReentrancyGuard {
    mapping(address => uint256) private _balances;

    event Deposited(address indexed user, uint256 amount);
    event Withdrawn(address indexed user, uint256 amount);

    constructor() Ownable(msg.sender) {}

    function deposit() external payable {
        require(msg.value > 0, "zero deposit");
        _balances[msg.sender] += msg.value;
        emit Deposited(msg.sender, msg.value);
    }

    // 遵循 Checks-Effects-Interactions + 重入保护
    function withdraw(uint256 amount) external nonReentrant {
        uint256 bal = _balances[msg.sender];
        require(bal >= amount, "insufficient");
        _balances[msg.sender] = bal - amount;   // Effects 先于 Interaction

        (bool ok, ) = msg.sender.call{value: amount}("");
        require(ok, "transfer failed");
        emit Withdrawn(msg.sender, amount);
    }

    function balanceOf(address user) external view returns (uint256) {
        return _balances[user];
    }

    function emergencyWithdraw() external onlyOwner {
        (bool ok, ) = owner().call{value: address(this).balance}("");
        require(ok, "transfer failed");
    }
}
```

## 📝 实际应用示例：联盟链供应链溯源

### 业务场景

服装行业多方协作溯源系统：品牌方、代工厂、物流、零售商、监管机构五方。需求：

- 生产、物流、销售的关键节点数据不可篡改
- 多方共同维护账本，无需信任单一中心
- 消费者扫码可验证商品真伪与流转路径
- 需要符合监管要求，具备可审计性

### 为什么选联盟链而非公链

| 维度 | 公链 | 联盟链 | 该场景选择 |
|------|------|--------|-----------|
| 参与方 | 任意 | 准入制 | **联盟链**（5 方已知） |
| 性能 | TPS 低 | TPS 高 | **联盟链** |
| 合规 | 难控制 | 可审计 | **联盟链** |
| 成本 | Gas 不可控 | 可预估 | **联盟链** |

选型：Hyperledger Fabric 或蚂蚁链 / FISCO BCOS。

### 架构设计

```
五方业务系统
   │  通过 SDK 调用
   ▼
┌─────────────────────────────────────────┐
│  联盟链网络（Fabric）                    │
│  ├─ 节点：每方 2 个（主备）              │
│  ├─ 共识：Raft / BFT                    │
│  ├─ 合约（Chaincode）：                  │
│  │   - 生产登记、物流流转、销售记录      │
│  └─ 通道隔离：敏感数据按需分通道        │
└──────────────────┬──────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│  大文件存储（IPFS 私有网络）             │
│   质检报告 PDF、原料照片、视频           │
│   链上只存 CID                          │
└─────────────────────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│  消费者 App                             │
│   扫码 → 查询链上记录 → 验证 CID 完整性  │
└─────────────────────────────────────────┘
```

### 关键决策

- **不是所有数据都上链**：原始高清图片走 IPFS，链上只存哈希与关键字段
- **隐私分通道**：价格等商业敏感数据只给相关方，监管方有全局通道
- **链下数据可信接入**：通过 IoT + 数字签名，防止"上链前数据已被篡改"
- **身份体系**：X.509 证书 + CA，与传统 PKI 体系打通
- **退出机制**：允许成员退出时将数据快照归档，不影响整体运行

## 🧭 什么时候不该用去中心化

架构师需要识别**伪需求**，出现以下情况时应慎重：

- 只有"单方信任"问题，而没有"多方不信任"问题 → 传统数据库足够
- 高频、强一致、低延迟的业务 → 区块链性能跟不上
- 数据需要随时修改 → 不可变性反成负担
- 单纯的"数据存证" → 传统的可信时间戳 + 数字签名更合适
- 仅为"蹭热点/融资" → 技术债务与运维复杂度会反噬

## 🔗 相关概念

- **分布式系统**：区块链是分布式系统的特殊形态，CAP、共识等理论全部适用
- **密码学**：非对称加密、哈希、零知识证明是 Web3 的底层支柱
- **WebAssembly**：越来越多新公链采用 Wasm 作为智能合约运行时
- **边缘计算**：去中心化与边缘有理念重合，但技术栈差异大
- **数据安全**：链上公开可读，敏感数据必须先加密再上链
