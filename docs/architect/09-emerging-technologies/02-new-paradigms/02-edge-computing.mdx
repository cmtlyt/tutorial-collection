# 边缘计算

> **版本**：v1.0
> **最后更新**：2026-04-24

## 📖 概述

边缘计算（Edge Computing）将计算、存储、网络能力下沉到靠近数据源的位置（基站、园区、设备端），以获得更低的延迟、更少的带宽开销、更强的隐私保护。它不是替代云，而是与云协同：云做全局的长期决策，边缘做局部的实时响应。本文讲解边缘-云协同架构、IoT 架构设计、低延迟方案，并给出适用场景的判断依据。

## 🎯 学习目标

- 理解边缘计算的定位，以及与 CDN、IoT、云计算的关系
- 掌握边缘-云协同架构的分层与职责划分
- 掌握 IoT 系统从设备到云的端到端架构设计
- 了解低延迟架构的关键技术手段
- 能够判断一个业务是否适合引入边缘计算

## 🌐 边缘计算的定位

### 与相关概念的区别

| 概念 | 核心特征 | 典型延迟 |
|------|---------|---------|
| **云计算** | 中心化、弹性无限、计算密集 | 50~200ms |
| **CDN** | 静态内容分发，读多写少 | 10~50ms |
| **边缘计算** | 通用计算，靠近数据源 | 1~20ms |
| **雾计算（Fog）** | 网络边缘的中间层 | 10~50ms |
| **设备端（On-Device）** | 在终端设备内推理/计算 | < 1ms |

### 适用场景的判断清单

出现以下一个或多个特征，就值得考虑边缘计算：

- **强延迟敏感**：AR/VR、云游戏、工业控制，要求 < 20ms
- **大带宽数据**：视频分析、4K 监控，回传云端成本高
- **弱网或离线**：矿山、船舶、偏远地区，无法保证稳定云连接
- **数据主权 / 隐私**：医疗、金融，敏感数据不能出园区
- **高密度终端**：单区域数万~百万终端，中心汇聚不现实

## 🏗️ 边缘-云协同架构

### 三层模型

```
┌────────────────────────────────────────────────┐
│              云端（Cloud / Region）             │
│  - 全局编排、模型训练、长期存储                 │
│  - 跨区域分析、计费、账户体系                   │
└──────────────────┬─────────────────────────────┘
                   │ 控制面（配置下发、指标上报）
                   │ 数据面（冷数据、聚合结果）
┌──────────────────▼─────────────────────────────┐
│           边缘节点（Edge / On-Prem）            │
│  - 本地实时计算、推理                           │
│  - 热数据存储、离线缓存                         │
│  - 设备接入、协议转换                           │
└──────────────────┬─────────────────────────────┘
                   │ 设备接入协议（MQTT/CoAP/工业协议）
┌──────────────────▼─────────────────────────────┐
│              终端（Device / IoT）               │
│  - 数据采集、简单过滤                           │
│  - 本地轻量推理（TinyML）                       │
│  - 执行器控制                                   │
└────────────────────────────────────────────────┘
```

### 职责划分原则

| 维度 | 云端职责 | 边缘职责 |
|------|---------|---------|
| **数据** | 全量长期存储、全局汇总 | 最近 N 小时热数据、本地聚合 |
| **计算** | 模型训练、报表、BI | 实时推理、规则触发 |
| **控制** | 策略定义、配置生成 | 策略执行、本地决策 |
| **运维** | 集中监控、远程调试 | 本地日志、故障自愈 |
| **安全** | 证书签发、审计中心 | 本地认证、边界防护 |

### 云边协同的三种模式

1. **管控协同**：云下发配置/策略，边缘执行（如 CDN 刷新规则）
2. **数据协同**：边缘预处理 + 过滤后上传云端，云端再深加工
3. **智能协同**：云端训练模型 → 边缘推理 → 反馈数据回流云端迭代

### 技术选型（边缘侧 Kubernetes 方案）

| 方案 | 定位 | 特点 |
|------|------|------|
| **KubeEdge** | CNCF 孵化，阿里/华为主导 | 云边通道 + 设备管理能力强 |
| **OpenYurt** | 阿里开源 | 最小侵入原生 K8s，适合边缘节点多 |
| **SuperEdge** | 腾讯开源 | 强调边缘自治 |
| **K3s / MicroK8s** | 轻量化 K8s | 资源受限的边缘站点 |

## 🔌 IoT 架构设计

### 端到端分层

```
┌─ 感知层 ────────────────────────────────────────┐
│  传感器 / RFID / 摄像头 / 工业 PLC              │
└────────────────────┬────────────────────────────┘
                     ▼
┌─ 接入层 ────────────────────────────────────────┐
│  网关（协议转换、聚合、本地缓存）               │
│  协议：MQTT / CoAP / LwM2M / Modbus / OPC UA   │
└────────────────────┬────────────────────────────┘
                     ▼
┌─ 边缘平台 ──────────────────────────────────────┐
│  设备接入、规则引擎、流处理、本地存储、推理     │
└────────────────────┬────────────────────────────┘
                     ▼
┌─ 云平台 ────────────────────────────────────────┐
│  设备影子、时序库、数据湖、AI 训练、OTA 升级    │
└────────────────────┬────────────────────────────┘
                     ▼
┌─ 应用层 ────────────────────────────────────────┐
│  大屏、App、工单、BI、对外开放 API             │
└─────────────────────────────────────────────────┘
```

### 核心设计要点

#### 1. 设备影子（Device Shadow）

设备可能离线，但业务侧希望随时可读/可下发指令。设备影子是设备状态的云端镜像：

```json
{
  "deviceId": "sensor-001",
  "reported": {          // 设备上报的实际状态
    "temperature": 25.3,
    "timestamp": "2026-04-24T10:00:00Z"
  },
  "desired": {           // 业务侧期望的目标状态
    "samplingRate": 5
  },
  "version": 142
}
```

设备上线后读取 `desired` 进行同步，并上报 `reported`；业务侧只读写影子，无需感知连接状态。

#### 2. 消息协议选择

| 协议 | 特点 | 适用 |
|------|------|------|
| **MQTT** | 轻量、发布订阅、QoS 分级 | 主流 IoT，带宽受限场景 |
| **CoAP** | 类 HTTP，UDP 之上 | 低功耗设备（电池供电） |
| **HTTP/HTTPS** | 简单、防火墙友好 | 对延迟不敏感的上报 |
| **LwM2M** | 设备管理专用 | 大规模设备 OTA、配置下发 |
| **OPC UA** | 工业互联标准 | 工业场景、PLC 对接 |

#### 3. 海量连接的接入层

单个 MQTT Broker 百万级长连接是常态，架构上需要：

- **无状态接入网关 + 共享路由表**：Broker 水平扩展
- **Topic 分片**：按设备 ID 哈希分片，避免单点热 Topic
- **背压保护**：连接数、消息速率限制，防止雪崩
- **会话持久化**：支持离线消息、断线续传

#### 4. 时序数据处理

IoT 数据具有典型的时序特征，选用专门的时序数据库：

- **InfluxDB**：开源主流，TSM 存储引擎
- **TDengine**：国产高性能时序库，强项是海量写入
- **TimescaleDB**：PostgreSQL 扩展，保留 SQL 能力
- **Prometheus**：偏监控场景，不适合业务时序

#### 5. OTA 升级

固件/模型的远程升级是 IoT 长期运营的刚需：

- **灰度策略**：按设备分组、地区、版本分批推送
- **断点续传**：差分升级，降低带宽
- **回滚机制**：A/B 双分区，升级失败自动回滚
- **安全校验**：固件签名，防止被篡改

## ⚡ 低延迟方案

### 延迟的来源

```
端到端延迟 = 传播延迟 + 传输延迟 + 处理延迟 + 排队延迟
           │         │         │         │
           │         │         │         └─ 队列拥塞（关键瓶颈）
           │         │         └─ 业务计算、序列化
           │         └─ 带宽 / 包大小
           └─ 物理距离 / 光速 / 路由跳数
```

### 常见优化手段

| 层级 | 技术 | 效果 |
|------|------|------|
| **网络层** | Anycast、BGP 优化、专线 | 减少跳数、稳定路由 |
| **传输层** | QUIC、HTTP/3、0-RTT | 连接复用、减少握手 |
| **协议层** | 二进制协议（Protobuf/Flatbuffers） | 序列化开销降低 |
| **部署层** | 就近接入、多活 | 传播延迟降低 |
| **计算层** | 边缘推理、本地决策 | 避免回源 |
| **存储层** | 本地缓存、预取 | 减少数据访问延迟 |
| **应用层** | 预计算、异步、流式 | 感知延迟优化 |

### P99 延迟治理的思维框架

低延迟架构的难点往往在"长尾"而非"平均"：

```
P50 易优化，P99/P999 难优化
│
├─ 识别长尾源：GC、重试、冷启动、锁竞争
├─ 隔离资源：CPU 绑核、NUMA 亲和、独立队列
├─ 超时控制：快速失败 + Hedged Request（双发取先返回）
└─ 容量保护：优雅降级、限流、熔断
```

## 📝 实际应用示例：智慧工厂质检系统

### 业务场景

在产线上部署高清摄像头，对产品进行实时视觉质检，要求：

- 单产线 20 路视频，每路 30 FPS
- 识别延迟 < 200ms（卡不住产线节拍）
- 单厂区网络带宽有限，视频不能全量回传
- 支持离线工作，云端断网时产线不停

### 架构设计

```
产线摄像头 ──▶ 工厂边缘集群（K3s）
                │
                ├─ 视频流处理（GStreamer + GPU）
                ├─ 缺陷检测模型（ONNX Runtime / TensorRT）
                ├─ 规则引擎（良品/次品/报警）
                ├─ 本地时序库（存储近 7 天检测结果）
                └─ 本地消息队列（缓冲异常样本）
                │
                │ 云边通道（KubeEdge）
                │ - 仅回传异常样本 + 聚合统计
                ▼
              云端平台
                ├─ 跨工厂数据汇总、BI
                ├─ 模型训练（收集的异常样本回流）
                ├─ 模型注册与版本管理
                └─ OTA 下发新模型到边缘
```

### 关键决策

- **视频不出厂**：仅上传异常图片 + 统计数据，带宽从 Gbps 降到 Mbps
- **边缘自治**：云端断网时，本地仍能完成检测、报警、产线控制
- **模型闭环**：异常样本回流云端 → 重训练 → 灰度下发新模型到边缘
- **容灾**：边缘集群双节点冗余，单节点故障产线不停
- **安全**：工厂网络与云网络 VPN 专线 + 双向 mTLS

## 🔗 相关概念

- **云原生**：边缘 K8s（KubeEdge、OpenYurt）是云原生向边缘的延伸
- **微服务**：边缘侧同样采用微服务架构，但更强调资源约束与自治
- **AI 原生架构**：边缘推理是 AI 原生架构的一种部署形态
- **可观测性**：边缘节点离散部署，观测数据需要先本地聚合再回传
- **WebAssembly**：Wasm 是边缘函数的重要运行时选择（见下一节）
