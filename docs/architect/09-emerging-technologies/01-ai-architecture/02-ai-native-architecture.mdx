# AI 原生架构

> **版本**：v1.0
> **最后更新**：2026-04-24

## 📖 概述

AI 原生（AI-Native）架构是指将模型、特征、数据流水线作为一等公民进行设计的系统架构。它不是在传统架构上"加一个模型"，而是围绕模型的生命周期（训练、评估、部署、推理、监控）重新组织服务边界、资源调度和发布流程。本文从 AI 微服务设计、模型服务化、特征工程平台、MLOps/LLMOps 四个维度讲解 AI 原生架构的设计方法。

## 🎯 学习目标

- 理解 AI 微服务与传统微服务的差异，掌握拆分原则
- 掌握模型服务化（Model Serving）的部署与推理优化方案
- 了解特征工程平台在训练/推理一致性中的作用
- 掌握 MLOps 和 LLMOps 的核心实践与流水线设计

## 🧩 AI 微服务设计

### 与传统微服务的差异

| 维度 | 传统微服务 | AI 微服务 |
|------|----------|----------|
| **资源需求** | CPU、内存为主 | GPU/TPU/NPU 密集，显存敏感 |
| **响应时间** | P99 毫秒级 | 秒级推理，LLM 场景需流式返回 |
| **部署单元** | 代码包 + 配置 | 代码 + 模型权重 + tokenizer + 配置 |
| **版本管理** | 代码版本 | 代码 × 模型 × 数据 × 特征四元组版本 |
| **扩缩容** | 秒级水平扩展 | 冷启动分钟级（受限于模型加载与 GPU 资源） |
| **可观测性** | 日志、Trace、指标 | 再加上数据漂移、模型精度、Token 消耗 |
| **失败语义** | HTTP 5xx 重试即可 | 需要处理"模型输出不符合约束"的逻辑失败 |

### 服务拆分原则

按照"模型生命周期阶段"和"流量特征"拆分，常见分层：

```
┌─────────────────────────────────────────────────┐
│  业务应用层（Business Apps）                     │
│  - 对话、推荐、搜索、风控等具体业务              │
└────────────────┬────────────────────────────────┘
                 │ 业务语义 API
┌────────────────▼────────────────────────────────┐
│  AI 编排层（AI Orchestration）                   │
│  - Prompt 模板、Agent 编排、RAG 流程             │
│  - 路由、降级、缓存、多模型回退                  │
└────────────────┬────────────────────────────────┘
                 │ 标准化推理 API
┌────────────────▼────────────────────────────────┐
│  模型服务层（Model Serving）                     │
│  - LLM / Embedding / Rerank / CV / ASR 等        │
│  - 批处理、动态批、KV Cache 管理                 │
└────────────────┬────────────────────────────────┘
                 │ 特征查询 / 写入
┌────────────────▼────────────────────────────────┐
│  特征与数据层（Feature Store / Vector DB）       │
│  - 在线特征、离线特征、向量检索                  │
└─────────────────────────────────────────────────┘
```

### 关键设计点

- **无状态推理服务**：模型权重只读加载，请求上下文随调用传递，便于水平扩缩
- **编排与推理解耦**：编排层轻量（CPU 即可），推理层重（GPU），独立扩缩
- **统一推理协议**：对外暴露 OpenAI 兼容接口或 [KServe v2 协议](https://kserve.github.io/website/latest/modelserving/data_plane/v2_protocol/)，便于模型替换
- **流式优先**：LLM 场景默认 SSE/WebSocket 流式返回，降低首 Token 延迟（TTFT）

## 🚀 模型服务化（Model Serving）

### 主流推理框架

| 框架 | 定位 | 适用场景 |
|------|------|---------|
| **Triton Inference Server** | 通用多后端推理服务 | 混合框架（TensorRT/ONNX/PyTorch）部署 |
| **vLLM** | 高吞吐 LLM 推理引擎 | 大语言模型在线服务，PagedAttention |
| **TGI (Text Generation Inference)** | HuggingFace 出品 LLM 推理 | HF 模型快速上线 |
| **SGLang** | 结构化生成推理 | 复杂 Prompt、Agent、约束生成 |
| **TorchServe** | PyTorch 原生服务化 | 以 PyTorch 为主的非 LLM 模型 |
| **KServe** | Kubernetes 上的模型服务标准 | 云原生统一编排 |

### 推理优化手段

- **动态批处理（Dynamic Batching）**：将到达时间相近的请求合批，提高 GPU 利用率
- **连续批处理（Continuous Batching）**：vLLM 的核心特性，按 Token 粒度调度，吞吐提升数倍
- **KV Cache 管理**：PagedAttention 将 KV Cache 分页，减少显存碎片
- **量化（Quantization）**：INT8/INT4/FP8，显存占用降至 1/2 ~ 1/4
- **投机解码（Speculative Decoding）**：小模型先生成草稿，大模型并行验证
- **张量并行 / 流水线并行**：超大模型跨多卡部署

### 部署拓扑示例（Kubernetes + KServe）

```yaml
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: llama3-chat
spec:
  predictor:
    minReplicas: 2
    maxReplicas: 16
    scaleTarget: 70      # GPU 利用率目标
    scaleMetric: concurrency
    model:
      modelFormat:
        name: huggingface
      runtime: kserve-vllm
      storageUri: "oss://models/llama-3-8b-instruct"
      resources:
        limits:
          nvidia.com/gpu: "1"
          memory: 32Gi
    containerConcurrency: 32
```

关键点：
- `scaleMetric: concurrency` 基于并发度扩缩，比 QPS 更贴合 LLM 场景
- `storageUri` 指向对象存储的模型仓库，启动时拉取并缓存
- GPU 资源按卡分配，避免多服务抢占同一张卡

## 🧱 特征工程平台（Feature Store）

### 要解决的核心问题

- **训练/推理一致性**：离线训练使用的特征口径，必须和在线推理一致，否则会出现"特征漂移"
- **特征复用**：同一特征被多个模型使用，避免重复计算
- **特征溯源**：任一线上预测，能回溯到所用的特征版本与数据源
- **低延迟读取**：在线推理要求特征查询 P99 < 10ms

### 典型架构

```
离线数据源 (Hive / Iceberg)
         │
         │ 批处理 (Spark / Flink Batch)
         ▼
  特征定义 (Feature Registry)  ◀── 统一 DSL 定义
         │
    ┌────┴────┐
    │         │
    ▼         ▼
离线特征     在线特征
(Parquet)  (Redis / HBase)
    │         │
    ▼         ▼
模型训练    在线推理
```

### 代表项目

- **Feast**：开源 Feature Store，轻量、Kubernetes 友好
- **Tecton**：商业化 Feature Platform
- **阿里云 PAI-FeatureStore**：云厂商托管方案

## 🔁 MLOps / LLMOps

### MLOps 生命周期

```
[数据采集] ─▶ [数据验证] ─▶ [特征工程] ─▶ [模型训练]
                                              │
                                              ▼
[线上监控] ◀─ [流量路由] ◀─ [模型部署] ◀─ [模型评估与注册]
     │                                        ▲
     └────── 反馈回流（标注/重训练触发） ────┘
```

### 关键组件

| 组件 | 作用 | 代表工具 |
|------|------|---------|
| **实验跟踪** | 记录训练参数、指标、产物 | MLflow、Weights & Biases |
| **模型注册表** | 版本化管理模型产物 | MLflow Registry、Vertex AI Model Registry |
| **流水线编排** | 串联训练/评估/部署步骤 | Kubeflow Pipelines、Airflow、Argo Workflows |
| **在线监控** | 数据漂移、预测偏差检测 | Evidently、Arize、WhyLabs |

### LLMOps 的增量关注点

相比传统 MLOps，LLMOps 增加了以下维度：

- **Prompt 版本管理**：Prompt 即代码，需要版本化、A/B 测试、回滚
- **评测集（Eval Set）**：替代传统的准确率指标，使用人工打分 + LLM-as-Judge
- **Token 成本管理**：按请求、按用户、按业务线统计与限额
- **安全与合规**：提示词注入防护、输出内容审核、PII 脱敏
- **RAG 质量治理**：检索召回率、上下文相关性、幻觉率

### LLMOps 流水线示例

```
┌─ 数据准备 ──────────────────────────────────────────┐
│  原始文档 → 清洗 → 切分 → Embedding → 向量库        │
└───────────────────────┬─────────────────────────────┘
                        ▼
┌─ Prompt 工程 ──────────────────────────────────────┐
│  Prompt 模板 → 版本化 → 评测集 → 离线评估          │
└───────────────────────┬─────────────────────────────┘
                        ▼
┌─ 发布与路由 ────────────────────────────────────────┐
│  金丝雀 5% → A/B 对比 → 全量 → 在线监控             │
└───────────────────────┬─────────────────────────────┘
                        ▼
┌─ 运行时治理 ────────────────────────────────────────┐
│  限流、缓存、降级、成本归因、内容审核               │
└─────────────────────────────────────────────────────┘
```

## 📝 实际应用示例：企业级智能客服系统

### 业务场景

构建一个支持多轮对话、可检索企业知识库、具备工单能力的智能客服，日均对话量 50 万次，要求：

- 首 Token 延迟 P95 < 1.5s
- 知识库召回准确率 > 90%
- 月度 LLM 成本可控并可按业务线归因

### 架构设计

```
用户 ─▶ 网关 ─▶ 对话编排服务（CPU 集群）
                    │
        ┌───────────┼────────────┬─────────────┐
        ▼           ▼            ▼             ▼
   Prompt 服务  RAG 检索     LLM 网关      工单 API
   （模板管理） （向量库+    （多模型路由）  （业务系统）
                重排序）          │
                            ┌─────┴──────┐
                            ▼            ▼
                       vLLM 集群    第三方 API
                       （自建大模型）（GPT/Claude）
```

### 关键设计决策

- **对话编排与模型推理分离**：编排层无状态、CPU 密集，独立扩缩；推理层按 GPU 资源独立扩缩
- **多模型路由**：简单 FAQ 走小模型（自建 7B），复杂问题走大模型（第三方 API），降低成本
- **缓存层**：对高频 Query + 上下文做 Embedding 语义缓存，命中率约 20%
- **可观测性**：对话链路 Trace、Token 消耗 Metric、对话满意度反馈闭环
- **成本归因**：网关层按租户 / 业务线打标签，聚合到 FinOps 系统

## 🔗 相关概念

- **微服务架构**：AI 原生架构是微服务的延伸，但在资源、版本、可观测性上有特殊要求
- **云原生**：KServe、Kubeflow 等都依赖 Kubernetes 作为底座
- **DDD**：AI 编排层的业务建模仍然适用 DDD 的限界上下文划分
- **可观测性**：AI 服务需要在传统三大支柱之外增加"模型维度"的观测
- **FinOps**：Token 成本是 LLM 服务的主要成本项，需要专门的治理手段
