# FinOps

> **版本**：v1.0
> **最后更新**：2026-04-24

## 📖 概述

FinOps（Cloud Financial Operations）是一套将财务责任引入云计算可变支出模型的管理实践，通过跨职能协作（工程、财务、业务）让团队在速度、成本、质量之间做出数据驱动的权衡。它不是简单的"省钱"，而是让每一分云支出都产生对应的业务价值。作为架构师，理解 FinOps 意味着你必须把**成本**作为和性能、可用性同等重要的架构质量属性。本文讲解 FinOps 三阶段模型、成本优化策略、资源利用率分析、成本归因与治理。

## 🎯 学习目标

- 理解 FinOps 的核心理念和三阶段模型（Inform / Optimize / Operate）
- 掌握云成本的主要构成与常见浪费点
- 掌握计算、存储、网络、数据库的核心优化手段
- 掌握资源利用率分析方法与成本归因机制
- 能够为组织建立 FinOps 运营体系

## 📐 FinOps 三阶段模型

FinOps Foundation 定义的三阶段是一个迭代循环，而非一次性完成：

```
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│    Inform       │ ───▶ │    Optimize     │ ───▶ │    Operate      │
│  （可见性）      │      │  （优化）        │      │  （运营）        │
├─────────────────┤      ├─────────────────┤      ├─────────────────┤
│ 成本归因         │      │ 预留实例/节省计划 │      │ 预算管控         │
│ 标签治理         │      │ 弹性伸缩         │      │ 持续优化         │
│ 看板与报表       │      │ 资源回收         │      │ 文化与考核       │
│ 分摊模型         │      │ 架构重构         │      │ 跨团队协作       │
└─────────────────┘      └─────────────────┘      └─────────────────┘
         ▲                                                  │
         └──────────────────────────────────────────────────┘
                       持续反馈与迭代
```

### Inform（可见性）

没有可见性就没有管理。核心产出：**每一笔云支出能归到具体的业务单元、应用、团队**。

- **标签策略**：强制打标（Team、App、Env、CostCenter 等），无标签资源拒绝或自动回收
- **看板建设**：从"公司总成本"逐层下钻到"团队 / 应用 / 实例"
- **分摊模型**：共享资源（K8s 集群、数据库）按实际用量分摊给使用方
- **异常检测**：日同比、周同比突增自动告警

### Optimize（优化）

有了可见性后的动作层。优化手段分为**架构级**（长期效果好）和**运维级**（见效快）。

### Operate（运营）

把优化动作嵌入日常流程：预算、评审、考核，让优化不是一次性运动。

## 💰 云成本的主要构成

### 典型云成本分布

| 大类 | 占比（典型） | 核心驱动 |
|------|-----------|---------|
| **计算** | 40%~60% | EC2 / K8s / Lambda |
| **数据库与缓存** | 15%~25% | RDS、Redis、DynamoDB |
| **存储** | 10%~20% | 对象存储、块存储、归档 |
| **网络** | 5%~15% | 公网出流量、跨可用区、CDN |
| **数据分析/AI** | 10%~20% | 大数据集群、GPU 实例 |
| **其他服务** | 5%~10% | LB、API 网关、托管服务 |

### 常见浪费点

- **僵尸资源**：未挂载的磁盘、未绑定的 IP、孤儿快照
- **过度配置**：CPU/内存长期利用率 < 10%
- **测试环境 7×24 运行**：开发环境夜间和周末无人使用
- **未启用生命周期**：日志/备份永久保留
- **架构缺陷**：跨 AZ/Region 不必要的数据传输
- **定价策略错配**：长期稳定负载仍使用按需实例
- **GPU 独占**：单张 GPU 只跑一个轻量模型

## 🎯 核心优化策略

### 1. 计算资源优化

#### 购买模式组合

| 模式 | 折扣 | 适用 |
|------|------|------|
| **按需（On-Demand）** | 0% | 突发、短时、不确定负载 |
| **预留实例（RI）** | 30%~50% | 稳定基线负载，1~3 年确定性消费 |
| **节省计划（Savings Plans）** | 30%~70% | 承诺一定计算花费，实例类型灵活 |
| **Spot / 竞价实例** | 70%~90% | 可中断的无状态、批处理、数据分析 |

**推荐组合**：基线用 RI/SP 锁价，弹性峰值用按需，批处理/AI 训练用 Spot。

#### 规格右调（Rightsizing）

```
基于实际使用数据推荐规格，而非"拍脑袋"
│
├─ CPU P95 < 40% → 降规格
├─ CPU P95 > 80% → 升规格
├─ 内存持续高但 CPU 低 → 换内存优化型
└─ 持续空载 → 考虑回收
```

规格右调是一个持续过程，应纳入季度评审。

#### Kubernetes 成本优化

Kubernetes 场景是多数现代架构的重灾区，核心手段：

- **合理设置 Requests/Limits**：Requests 决定调度和账单，Limits 决定上限
- **装箱优化（Bin Packing）**：通过合适的节点规格和调度策略提高节点利用率
- **HPA + VPA + Cluster Autoscaler 三板斧**：应用横向扩缩 + 规格纵向调整 + 节点弹性
- **Karpenter / Cluster Autoscaler**：按 Pod 需求动态选择最便宜的节点类型
- **Spot 节点组 + 容错设计**：无状态工作负载跑在 Spot

```yaml
# HPA + 合理 Requests 示例
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  template:
    spec:
      containers:
      - name: app
        resources:
          requests:   # 基于 P95 使用率，不要过度预留
            cpu: "500m"
            memory: "1Gi"
          limits:
            cpu: "2"
            memory: "2Gi"
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 3      # 保最小可用
  maxReplicas: 30
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 65
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 防止抖动
```

### 2. 存储优化

#### 对象存储分层

```
热数据 (Standard)        访问频繁     最贵
   │
   │ 30 天未访问
   ▼
温数据 (Infrequent Access)             中等
   │
   │ 90 天未访问
   ▼
冷数据 (Archive / Glacier)            便宜
   │
   │ 合规归档
   ▼
深度归档 (Deep Archive)                最便宜（取回时间长）
```

通过**生命周期规则**自动迁移，是投入产出比最高的优化之一：

```json
{
  "Rules": [
    {
      "ID": "log-lifecycle",
      "Filter": { "Prefix": "logs/" },
      "Status": "Enabled",
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 90, "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 365 }
    }
  ]
}
```

#### 其他存储优化

- **块存储**：选对类型（gp3 / io2），监控 IOPS 实际使用
- **快照**：定期清理过期快照、无主快照
- **日志/指标**：合理设置保留期，重要数据采样
- **去重压缩**：大数据场景使用列式格式（Parquet/ORC）+ 压缩

### 3. 网络优化

网络成本常被低估，但增长最快：

| 场景 | 优化 |
|------|------|
| **公网出流量** | CDN 分流、响应压缩、图片 WebP/AVIF |
| **跨 AZ 流量** | 同 AZ 亲和调度、客户端就近路由 |
| **跨 Region 流量** | 缓存、异步复制、只同步必要数据 |
| **NAT 网关** | 对高吞吐服务用 VPC Endpoint 替代 |
| **LB 选型** | ALB / NLB / 自建 Nginx 按场景选 |

### 4. 数据库优化

- **读写分离 + 缓存**：减少主库压力，降低规格
- **分层存储**：历史数据归档到更便宜的存储
- **Serverless 数据库**：流量波动大的场景（Aurora Serverless、DynamoDB 按需）
- **连接池**：减少连接数，降低数据库实例规格
- **查询优化**：慢查询、N+1、无索引是三大成本杀手

## 📊 资源利用率分析

### 衡量指标

| 维度 | 指标 | 目标参考值 |
|------|------|----------|
| **计算** | CPU 利用率（P95） | 生产 50%~70%，测试 30%+ |
| | 内存利用率（P95） | 60%~80% |
| **存储** | 磁盘容量利用率 | 60%~80% |
| | IOPS 利用率 | 40%~70% |
| **K8s 集群** | Requests 分配率 | > 70% |
| | 实际使用率 / Requests | > 50% |
| **成本效率** | 单位业务指标的成本 | 持续下降或维持 |

### 分析工作流

```
采集原始数据（云账单 + 监控指标）
         │
         ▼
打标与归因（Team / App / Env）
         │
         ▼
生成可视化看板
  ├─ 成本 Top N 应用
  ├─ 利用率 Bottom N 应用
  ├─ 浪费识别（僵尸资源、低负载资源）
  └─ 同比环比趋势
         │
         ▼
生成优化建议（人工 / 自动）
         │
         ▼
跟踪优化执行与节省金额
```

### 工具选型

| 工具 | 定位 |
|------|------|
| **云厂商原生**（AWS Cost Explorer、阿里云费用中心） | 基础账单分析 |
| **Kubecost / OpenCost** | K8s 专用成本归因 |
| **CloudHealth、Apptio Cloudability** | 企业级 FinOps 平台 |
| **Vantage、Finout** | 多云统一成本可见性 |
| **自建 + 数据仓库** | 深度定制、与 CMDB 打通 |

## 🏷️ 成本归因与治理

### 标签治理

标签（Tag / Label）是成本归因的基石。常见必填标签：

| 标签 | 作用 |
|------|------|
| `team` / `owner` | 谁拥有这个资源 |
| `app` / `service` | 属于哪个应用 |
| `env` | 开发/测试/预发/生产 |
| `cost-center` | 财务成本中心 |
| `project` | 业务项目（便于按项目核算） |

治理手段：

- **创建时强制**：通过 IaC 模板、云厂商策略、K8s Admission Webhook 拦截无标签资源
- **合规扫描**：定期扫描无标签/错标签资源
- **分摊默认策略**：找不到标签的资源按默认规则分摊给"平台团队"

### 分摊模型（Showback vs Chargeback）

- **Showback**：让团队看到自己的成本，不实际结算
- **Chargeback**：实际从团队预算中扣除

大部分企业从 Showback 起步，成熟后再过渡到 Chargeback。

### 共享资源分摊

K8s 集群、中间件等共享资源需要分摊：

| 分摊方式 | 说明 |
|---------|------|
| **按使用量** | 按实际 CPU/内存/流量精确分摊（推荐） |
| **按 Requests** | 按资源申请量分摊（K8s 常用） |
| **均摊** | 参与团队平均分摊（简单但不公平） |
| **混合** | 固定部分均摊，可变部分按用量 |

### 预算与告警

```
年度预算 ──▶ 季度/月度预算 ──▶ 团队预算
                                   │
                                   ├─ 50% → 通知
                                   ├─ 80% → 告警 + 评审
                                   └─ 100% → 冻结新增资源
```

## 🧑‍🤝‍🧑 Operate：FinOps 文化建设

### 角色与协作

FinOps 是跨职能运动，至少涉及：

- **FinOps 团队**：方法论、工具、看板、指导
- **业务/研发团队**：成本最终责任方，做具体优化
- **财务团队**：预算、对账、商务谈判
- **采购/运维**：RI/SP 购买、合约管理
- **管理层**：设置目标、考核、资源支持

### 度量文化

- 把"单位业务指标的成本"作为架构评审的必看指标
  - 例：**每单交易成本、每条消息处理成本、每请求 LLM 成本**
- 架构评审模板加入"成本影响分析"章节
- 年度/季度举办"节省之星"评选，鼓励优化行为

## 📝 实际应用示例：SaaS 公司 FinOps 落地

### 背景

一家中型 SaaS 公司，年云支出 2000 万，最近两年年增长 60%+，高于业务收入增速。

### 第一阶段（1~3 月）：建立可见性

- 梳理标签体系，出台《云资源标签规范》，未打标资源一周内必须整改
- 搭建统一成本看板：公司 → 团队 → 应用三级下钻
- 发现 Top 5 浪费：
  1. 测试环境 7×24 运行，预计每年浪费 80 万
  2. 某大数据集群夜间利用率 < 5%
  3. 过期快照与孤儿磁盘合计 200 TB
  4. 跨 Region 同步流量 30 万/月
  5. RI 覆盖率仅 20%

### 第二阶段（4~9 月）：优化执行

| 动作 | 预计年节省 |
|------|---------|
| 测试环境夜间/周末自动关停 | 60 万 |
| 大数据集群 Spot 化 + 分时伸缩 | 120 万 |
| 存储生命周期策略 + 僵尸清理 | 50 万 |
| 跨 Region 改为异步批量同步 | 20 万 |
| 提升 RI/SP 覆盖到 70% | 180 万 |
| K8s Requests 右调 + Karpenter | 150 万 |
| **总计** | **~580 万** |

### 第三阶段（10+ 月）：运营常态化

- 设立 FinOps 团队（3 人），嵌入平台部门
- 架构评审模板加入"成本影响分析"
- 年度预算按团队分解，月度对账
- 架构师 KPI 增加"单位业务成本"
- 季度"节省之星"评选，发布内部月报

**结果**：在业务继续增长的背景下，云支出绝对值下降 20%，单位业务指标成本下降 40%。

## 🔗 相关概念

- **可观测性**：成本可见性是 FinOps 的基础，复用监控体系
- **云原生 / K8s**：K8s 是 FinOps 优化的主战场
- **平台工程**：IDP 是 FinOps 落地的天然载体（成本可视化、预算内建）
- **可持续架构**：成本优化与碳排放优化方向高度一致
- **架构评估**：成本应作为架构质量属性之一参与权衡
