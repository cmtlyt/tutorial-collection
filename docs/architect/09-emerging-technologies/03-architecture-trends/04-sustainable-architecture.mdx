# 可持续架构

> **版本**：v1.0
> **最后更新**：2026-04-24

## 📖 概述

可持续架构（Sustainable Architecture）把**碳排放**作为和性能、可用性、成本同等重要的架构质量属性。数字基础设施已占全球碳排放的约 2%~4%，随着 AI 训练与推理的爆发，预计还会显著增长。作为架构师，我们不仅要让系统跑得快、跑得稳、跑得省钱，还要让它跑得"绿色"。本文讲解绿色计算的理念、碳感知架构的设计方法、节能优化的技术手段，以及如何把可持续性落地为工程实践。

## 🎯 学习目标

- 理解可持续架构的业务价值与监管背景
- 掌握绿色软件基金会（GSF）的核心原则与 SCI 指标
- 理解碳感知架构的设计模式
- 掌握应用层、基础设施层、数据层的节能优化手段
- 能够将可持续性嵌入架构评审流程

## 🌱 为什么要关注可持续架构

### 三重驱动力

1. **环境责任**：全球碳中和趋势，企业 ESG 已成为必选项
2. **监管合规**：欧盟 CSRD、中国双碳目标、各国碳税政策逐步落地
3. **经济收益**：碳优化与成本优化高度正相关——**更少能耗 = 更低成本**

### 数字系统的碳排放来源

```
一个应用的碳足迹
      │
      ├─ 运营碳（Operational Carbon）── 系统运行时的电力消耗
      │     ├─ 计算（CPU/GPU/内存）
      │     ├─ 存储
      │     ├─ 网络传输
      │     └─ 冷却与供配电（PUE）
      │
      ├─ 隐含碳（Embodied Carbon）── 硬件制造、运输、报废
      │     ├─ 服务器、芯片
      │     ├─ 终端设备
      │     └─ 数据中心基础设施
      │
      └─ 用户侧碳（User Carbon）── 终端运行与传输
            ├─ 手机 / PC 电量消耗
            └─ 家庭/移动网络能耗
```

### 碳与成本的关系

| 优化动作 | 降成本 | 降碳 |
|---------|-------|------|
| 规格右调、回收僵尸资源 | ✅ | ✅ |
| Spot / 低优先级实例 | ✅ | ✅ |
| 代码性能优化 | ✅ | ✅ |
| 存储分层与生命周期 | ✅ | ✅ |
| **选碳排放低的区域部署** | ⚪（略） | ✅ |
| **工作负载跟随绿色能源** | ⚪ | ✅ |

大多数 FinOps 措施天然也是减碳措施，但少部分"碳感知"动作需要以碳为目标做专门设计。

## 📐 绿色软件原则（GSF）

绿色软件基金会（Green Software Foundation）提出的 [核心原则](https://learn.greensoftware.foundation/)：

### 三大支柱

```
1. Carbon Efficiency（碳效率）
   做同样的事，排放更少

2. Energy Efficiency（能源效率）
   用更少的能源完成工作

3. Hardware Efficiency（硬件效率）
   让硬件在生命周期内被充分利用
```

### 关键设计原则

| 原则 | 含义 | 实践 |
|------|------|------|
| **碳感知（Carbon Awareness）** | 不同时间、不同地点的电网碳强度不同 | 把工作负载调度到"低碳时段 / 低碳区域" |
| **电网强度（Energy Proportionality）** | 空闲服务器仍耗电，利用率越高能效比越好 | 高密度部署、整合工作负载 |
| **需求塑造（Demand Shaping）** | 在碳强度高时降级服务质量 | 视频降码率、图片降质量 |
| **测量 > 估算** | 先能测量，才能优化 | 建立碳排放看板 |

### SCI（软件碳强度）指标

SCI（Software Carbon Intensity）是 ISO 认证的度量标准：

```
SCI = (E × I) + M
      ─────────
          R

E = 能耗（kWh）
I = 电网碳强度（gCO2/kWh）
M = 隐含碳（硬件生命周期分摊，gCO2）
R = 功能单位（每请求、每用户、每事务）

单位：gCO2e/unit（每单位功能的碳排放）
```

SCI 的特性：

- **比率**而非绝对值：鼓励提升单位效率，而非简单减少总量
- **单位明确**：便于跨服务比较
- 应与"单位业务指标成本"并列，作为架构的核心效率指标

## 🗺️ 碳感知架构

### 核心理念

电网碳强度不是常数：

- **时间维度**：风光发电高峰时段（如中午）碳强度低，凌晨依赖火电时碳强度高
- **区域维度**：北欧水电/地热为主，碳强度可低于 50 gCO2/kWh；依赖煤电的区域可能超过 800 gCO2/kWh

**碳感知架构就是让计算"跟着绿色电力走"。**

### 典型模式

#### 1. 时间平移（Time Shifting）

可延迟的工作负载（报表、训练、备份、ETL）调度到低碳时段：

```
实时负载（必须立即处理）─▶ 立即执行
可延迟负载（非紧急）   ─┐
                        │
                        ▼
                 碳强度感知调度器
                        │
                        │ 查询电网碳强度预测
                        ▼
                 等待低碳窗口
                        │
                        ▼
                    批量执行
```

对延迟容忍度 >= 数小时的批处理作业，时间平移可降低 10%~30% 碳排放。

#### 2. 空间平移（Location Shifting）

工作负载路由到当前碳强度最低的区域：

- 全球 CDN 的请求路由可考虑碳因素
- 多 Region 的批处理任务优先跑在低碳 Region
- 存在数据合规约束时需权衡（如欧盟数据必须在欧盟内）

#### 3. 需求塑造（Demand Shaping）

在碳强度高时主动降级：

| 服务 | 低碳时段 | 高碳时段 |
|------|---------|---------|
| 视频平台 | 1080P 默认 | 降为 720P |
| 图片 CDN | PNG/原图 | WebP/AVIF 压缩 |
| 搜索 | 调用 LLM 精排 | 降级为传统排序 |
| 邮件推送 | 立即发送 | 合并延迟发送 |

### 电网碳强度数据源

- **[ElectricityMaps](https://www.electricitymaps.com/)**：全球实时电网碳强度 API
- **[WattTime](https://www.watttime.org/)**：边际碳排放强度，更适合优化决策
- **[Grid Intensity GO / C# SDK](https://github.com/thegreenwebfoundation)**：绿色网络基金会 SDK
- 云厂商碳排放报告：AWS、Azure、GCP、阿里云均有区域级数据

### 碳感知调度示例（概念代码）

```javascript
// 根据电网碳强度选择执行区域
async function selectGreenRegion(candidates) {
  const intensities = await Promise.all(
    candidates.map(async (region) => {
      const response = await fetch(
        `https://api.electricitymap.org/v3/carbon-intensity/latest?zone=${region}`,
        { headers: { 'auth-token': process.env.EM_TOKEN } }
      )
      const data = await response.json()
      return { region, gCO2PerKWh: data.carbonIntensity }
    })
  )

  intensities.sort((a, b) => a.gCO2PerKWh - b.gCO2PerKWh)
  return intensities[0].region
}

// 批处理任务调度：在碳强度低于阈值时触发
async function carbonAwareBatchRunner(job) {
  const region = await selectGreenRegion(['cn-hangzhou', 'eu-west-1', 'us-west-2'])
  const { gCO2PerKWh } = await getCurrentIntensity(region)

  if (gCO2PerKWh < 300 || job.deadlineReached()) {
    await runJobInRegion(job, region)
  } else {
    await scheduleRetry(job, { after: '30m' })
  }
}
```

## 🔧 节能优化的工程实践

### 1. 应用层

- **算法选择**：O(n²) → O(n log n) 带来的能耗下降非常可观
- **缓存**：重复计算的数据一次就好，缓存命中率直接等于减排
- **减少数据传输**：API 响应字段按需返回，减少序列化与网络能耗
- **高效语言与框架**：Rust、Go 相较解释型语言能效比优势明显（注意要结合场景）
- **异步与流式**：避免无意义的轮询和全量加载

### 2. 基础设施层

- **高利用率优先**：装箱、混部、弹性伸缩，让硬件"忙起来"
- **Serverless / FaaS**：空闲即零消耗
- **ARM 架构实例**：AWS Graviton、阿里云 YiTian 等 ARM 服务器相比 x86 能效提升 20%~40%
- **高 PUE 效率的数据中心**：优先选择 PUE < 1.3 的数据中心
- **硬件生命周期延长**：避免"过度升级"，使用再制造设备

### 3. 数据层

- **数据最小化**：只采集真正用得上的数据
- **分层存储**：热温冷三层自动流转
- **压缩与列存**：Parquet/ORC + Zstd 可减少 70%+ 存储
- **采样**：指标、日志合理降采样
- **生命周期**：超过保留期自动销毁，不仅合规，也减少存储能耗

### 4. 前端与传输

- **图片现代格式**：WebP、AVIF 比 JPEG 省 30%~50% 流量
- **按需加载**：首屏关键资源优先，其余延迟加载
- **CDN 合理缓存**：避免重复回源
- **减少第三方 JS**：每一个脚本都是能耗
- **暗色模式**：OLED 屏幕下明显降低终端能耗

### 5. AI 场景专项

AI 训练与推理是能耗大户，需要特别对待：

| 优化 | 效果 |
|------|------|
| **模型蒸馏 / 小模型化** | 参数减少 1 个数量级，能耗显著降低 |
| **量化（INT8/INT4/FP8）** | 显存与计算量降低 50%+ |
| **投机解码、连续批处理** | 吞吐提升带来的能效比提升 |
| **请求缓存（语义缓存）** | 命中即零推理能耗 |
| **分级模型路由** | 简单任务走小模型，大模型专攻难题 |
| **关机空闲 GPU** | GPU 闲置不降频时能耗依然很高 |

## 📏 如何在组织中落地

### 嵌入架构评审

在架构评审模板中加入"可持续性分析"章节：

```markdown
## 可持续性评估
- 预估 SCI：___ gCO2e/请求
- 运营碳占比：___ %
- 隐含碳占比：___ %
- 优化手段：
  - [ ] 高利用率设计
  - [ ] 分层存储 + 生命周期
  - [ ] 缓存与语义复用
  - [ ] 碳感知调度（如适用）
- 与同类系统基线对比：___
```

### 建立碳排放看板

复用 FinOps 的数据管线，增加"碳排放"维度：

```
成本看板 ──▶ 补充"碳系数"
              │
              ▼
          碳排放看板
              │
              ├─ 公司总排放趋势
              ├─ 按团队 / 应用归因
              ├─ 单位业务的 SCI
              └─ 减排项目跟踪
```

### 文化与机制

- **绿色架构师角色**：平台团队中设立绿色工程师，负责方法论与度量
- **年度碳预算**：与财务预算并行，按团队下发
- **标杆共建**：与云厂商、行业联盟共建行业基线
- **用户沟通**：在 ESG 报告中对外披露减排成果，形成正向循环

## 📝 实际应用示例：视频平台的绿色改造

### 背景

一家视频平台月活 5000 万，年碳排放约 8 万吨 CO2e，希望在 2 年内减排 30%。

### 评估：碳来源结构

```
年碳排放 80,000 吨 CO2e
├─ CDN / 边缘节点     45%    (流量大户)
├─ 视频转码           20%    (GPU 密集)
├─ 推荐系统（AI）     15%    (GPU 推理)
├─ 存储（视频库）     10%
├─ 数据库 / 业务服务   7%
└─ 其他                3%
```

### 减排措施组合

| 措施 | 预估年减排 | 说明 |
|------|----------|------|
| **AV1 编码全面替换 H.264** | 12,000 吨 | 码率降低 ~40%，CDN 流量显著减少 |
| **推荐系统小模型 + 语义缓存** | 6,000 吨 | 推理能耗降 50% |
| **转码任务碳感知调度** | 4,000 吨 | 非实时转码跑在绿电时段 |
| **热冷视频分层存储 + ARM 实例** | 3,000 吨 | 冷视频归档，计算迁 ARM |
| **前端需求塑造（智能码率）** | 2,500 吨 | 弱网时主动降码率 |
| **数据中心切换到高效站点** | 3,500 吨 | 选 PUE < 1.2 的绿色数据中心 |
| **CDN 厂商选择含绿电比例** | 2,000 吨 | 绿电占比 > 70% 的节点优先 |
| **合计** | **~33,000 吨** | **约 41%，超过目标** |

### 工程落地关键点

- **双指标并行**：`$/观看分钟` 与 `gCO2e/观看分钟` 并列 KPI
- **渐进发布**：AV1 替换按地区灰度 6 个月，监控终端兼容性
- **数据真实可信**：关键数据如 CDN 碳排放需要向供应商索取并审计
- **对外披露**：ESG 报告公开减排成果，提升品牌与资本市场认可

## 🔗 相关概念

- **FinOps**：方法论、数据管线、组织模式高度相似，可共建
- **可观测性**：碳排放度量是可观测性的新维度
- **云原生 / K8s**：高利用率、弹性伸缩天然减碳
- **边缘计算**：边缘可以减少回源流量，但也需评估边缘节点能效
- **AI 原生架构**：AI 是减排的重点治理对象，也是辅助优化的工具
- **架构评估**：SCI 应成为架构决策的核心质量属性
