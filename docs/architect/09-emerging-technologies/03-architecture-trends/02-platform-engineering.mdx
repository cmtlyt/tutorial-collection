# 平台工程

> **版本**：v1.0
> **最后更新**：2026-04-24

## 📖 概述

平台工程（Platform Engineering）是近几年最受关注的组织与架构范式演进之一。核心主张是：通过构建**内部开发者平台（Internal Developer Platform, IDP）**，把重复的基础设施能力产品化，让业务开发者以自服务的方式高效交付软件。它不是否定 DevOps，而是解决"每个团队都要会一点 K8s、监控、CI/CD 才能干活"的认知负担问题。本文讲解平台工程的理念、IDP 的架构设计、以及"平台即产品"的运营方法。

## 🎯 学习目标

- 理解平台工程的核心理念、与 DevOps 的关系
- 掌握内部开发者平台（IDP）的分层架构和关键能力
- 理解"平台即产品"的产品思维与运营方法
- 掌握自服务基础设施的设计模式
- 能够为组织制定平台工程落地路径

## 🧭 平台工程的理念

### 为什么出现

"You build it, you run it" 理想状态下很美好，但现实中：

- **认知负担过重**：Kubernetes、Terraform、Prometheus、Istio…业务开发要懂十几项技术才能把代码跑起来
- **重复造轮子**：每个团队各自搭建 CI/CD、监控、日志、灰度
- **不一致**：相同目的的基础设施能力在不同团队有不同实现，难以治理
- **运维倾斜**：真正"会搞基础设施"的人成为组织瓶颈

平台工程的解法：**沉淀可复用的平台能力，通过自服务界面把复杂度隐藏在平台内部。**

### 与相关理念的关系

```
DevOps（理念）
  │ "开发运维一体化"
  │
  ├─ SRE（实践）
  │   "用工程方法解决运维问题"
  │
  ├─ GitOps（实践）
  │   "Git 作为唯一真相来源"
  │
  └─ 平台工程（实践）★
      "构建平台产品降低开发者认知负担"
```

平台工程不是取代 DevOps，而是 DevOps 在大规模组织中的工程化落地。

### 核心原则

1. **平台是产品，开发者是用户**：用产品思维做平台，而不是堆功能
2. **铺设黄金路径（Golden Path）**：提供"最佳默认路径"，而非强制约束
3. **自服务（Self-Service）**：开发者无需开工单，按钮/CLI/API 直接拿到资源
4. **抽象而非屏蔽**：隐藏复杂度但保留"逃生舱（Escape Hatch）"
5. **持续演进**：根据使用数据和用户反馈迭代

## 🏗️ 内部开发者平台（IDP）架构

### 分层模型

```
┌──────────────────────────────────────────────────┐
│  开发者界面层（Developer Interface）              │
│  - Portal（Backstage 等）                        │
│  - CLI、VS Code 插件、ChatOps                    │
└─────────────────────┬────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────┐
│  能力编排层（Orchestration）                      │
│  - 应用模板（Scaffolder）                         │
│  - 环境管理、密钥管理                             │
│  - 工作流编排（CI/CD、数据库申请、灰度）           │
└─────────────────────┬────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────┐
│  能力抽象层（Capability API）                     │
│  - 统一的"应用"、"环境"、"服务"、"资源"模型        │
│  - 基于 K8s CRD / Crossplane / KCL 等             │
└─────────────────────┬────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────┐
│  基础设施层（Infrastructure）                     │
│  - Kubernetes 集群、数据库、消息队列、对象存储    │
│  - 云厂商 / 自建机房                              │
└──────────────────────────────────────────────────┘
```

### 关键能力矩阵

IDP 通常需要覆盖以下能力（不必一次都建，按阶段推进）：

| 类别 | 能力 | 说明 |
|------|------|------|
| **应用生命周期** | 脚手架 | 一键创建新应用（含代码仓库、CI、部署清单） |
| | 部署 | 自动化 CD、蓝绿、金丝雀 |
| | 环境 | 开发/测试/预发/生产环境一键创建 |
| **基础资源** | 数据库申请 | 自服务申请 MySQL/Redis/MQ |
| | 域名证书 | 域名绑定、TLS 自动签发 |
| | 密钥管理 | Vault / KMS 集成 |
| **可观测性** | 日志 | 日志采集、查询、告警 |
| | 指标 | 默认 Dashboard、SLO 模板 |
| | 链路 | Trace 自动接入 |
| **质量与安全** | 质量门禁 | 代码扫描、覆盖率、依赖漏洞 |
| | 合规 | 安全基线、合规扫描 |
| **协作治理** | 服务目录 | 谁拥有哪个服务、依赖关系 |
| | 技术雷达 | 技术栈推荐/淘汰 |
| | 文档门户 | 统一的技术文档入口 |

### 代表工具生态

| 类别 | 代表工具 |
|------|---------|
| **IDP Portal** | Backstage（Spotify 开源，事实标准）、Port、Cortex |
| **基础设施抽象** | Crossplane、KCL、Pulumi、Terraform |
| **工作流编排** | Argo Workflows、Tekton、GitHub Actions |
| **GitOps 部署** | ArgoCD、Flux |
| **环境管理** | vCluster、Kubernetes Namespace Hierarchy |
| **服务目录** | Backstage Catalog、Cortex |

### 统一应用模型示例

用 Kubernetes CRD 定义一个面向开发者的"应用"抽象，屏蔽底层 Deployment/Service/Ingress 等细节：

```yaml
apiVersion: platform.company.io/v1
kind: Application
metadata:
  name: order-service
  namespace: team-trade
spec:
  owner: team-trade
  tier: high                        # 高保级别：影响 SLO 与资源配额
  runtime:
    language: java
    version: "21"
    image: order-service:1.4.2
  resources:
    cpu: 2
    memory: 4Gi
    replicas: { min: 3, max: 20 }
  exposure:
    http:
      - path: /api/orders
        domain: api.company.com
        auth: oauth2
  dependencies:
    - type: mysql
      name: order-db
      size: standard-2c8g
    - type: redis
      name: order-cache
      size: standard-4g
  observability:
    slo:
      availability: "99.9%"
      latencyP99: "200ms"
```

平台内部将上述 YAML 展开为 Deployment、Service、Ingress、HPA、ServiceMonitor、数据库实例申请、DNS 记录、Secret 注入等一系列底层资源，开发者完全感知不到。

## 🎁 平台即产品（Platform as a Product）

### 产品思维的关键动作

| 传统"基础设施团队" | 产品化平台团队 |
|------------------|---------------|
| 工单驱动 | 自服务驱动 |
| 成功 = 系统稳定 | 成功 = 用户（开发者）效率提升 |
| 按需求做功能 | 做用户调研、OKR、路线图 |
| 没有明确客户 | 明确的内部"客户" |

### 产品运营节奏

```
用户研究 ──▶ 产品路线图 ──▶ 迭代开发 ──▶ 发布 ──▶ 度量与反馈
   ▲                                                    │
   └────────────────────────────────────────────────────┘
```

具体手段：

- **用户画像**：把开发者分群（初级/资深、前端/后端、业务/基础）
- **NPS 调查**：定期收集开发者满意度
- **使用数据**：哪些能力被高频使用、哪些被冷落
- **支持工单分析**：高频问题揭示产品缺陷
- **发布公告**：新能力发布要写 Release Notes，像产品对外发版一样

### 度量指标（DORA + 开发者体验）

- **部署频率（Deployment Frequency）**
- **变更前置时间（Lead Time for Changes）**
- **变更失败率（Change Failure Rate）**
- **故障恢复时间（MTTR）**
- **开发者 NPS / SPACE 指标**
- **新服务从 0 到上线所需时长**
- **80% 场景的自服务覆盖率**

## 🛠️ 自服务基础设施

### 设计模式

#### 1. 模板化脚手架

开发者选择"应用类型模板"一键创建，包含：

- 标准目录结构与规范代码
- 预配置的 CI 流水线
- 默认的 Dockerfile、Helm Chart / Kustomize
- 默认的监控/告警规则
- README 和新人引导

#### 2. 基础设施即代码（IaC）抽象

用 Crossplane 或 KCL 把云资源"CRD 化"：

```yaml
# 开发者视角：只需关心"我要一个 MySQL"
apiVersion: database.platform.company.io/v1
kind: MySQLInstance
metadata:
  name: order-db
spec:
  size: standard-2c8g
  ha: true
  backup:
    schedule: "0 3 * * *"
    retention: 14d

# 平台内部：Crossplane 自动翻译成 RDS/AuroraDB/自建 Operator 的具体资源
```

#### 3. 逃生舱（Escape Hatch）

平台抽象无法覆盖 100% 场景，必须允许高级用户绕过：

- 允许 `kubectl apply` 直接操作（受 RBAC 约束）
- 允许自定义 Helm Chart、Terraform 模块
- 允许 hook 平台流水线的特定阶段

### 开发者门户（Backstage 示例）

Backstage 事实上已经成为 IDP Portal 的默认选择，核心能力：

- **软件目录（Software Catalog）**：服务、API、资源、所有者
- **脚手架（Scaffolder）**：从模板创建新服务
- **TechDocs**：代码仓库中的 Markdown 自动渲染为统一文档站
- **插件系统**：接入 CI、K8s、云资源、安全扫描等

```yaml
# Backstage catalog-info.yaml：每个服务描述自身
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: order-service
  description: 订单服务
  annotations:
    github.com/project-slug: company/order-service
    backstage.io/kubernetes-id: order-service
spec:
  type: service
  lifecycle: production
  owner: team-trade
  system: trading-system
  dependsOn:
    - component:payment-service
    - resource:order-db
```

## 📝 实际应用示例：中型技术团队的平台工程落地

### 背景

一家 500 人研发规模的 SaaS 公司，分 20 多个业务小组，当前痛点：

- 每个小组自己写 CI/CD，质量参差不齐
- 申请一个 MySQL 要走 3 天工单流程
- 线上故障定位难，指标/日志/Trace 标准不统一
- 新人上手一个服务要 2 周

### 三阶段路线图

#### 阶段一（0~3 月）：平台底座与最小可用

目标：**打通一条黄金路径，让 1~2 个试点团队用起来**

- 部署 Backstage 作为门户
- 沉淀 2~3 个语言的应用模板（Java、Node.js、Go）
- 接入 GitLab + ArgoCD，一键部署到预发/生产
- 统一可观测性基座（Prometheus + Loki + Tempo）
- 试点团队：按高级开发者 5 人 + 2 个业务团队试运行

**成功标准**：新服务从 0 到生产部署时间从 2 周降到 1 天。

#### 阶段二（3~9 月）：扩大覆盖 + 能力深化

目标：**覆盖 60% 团队，完善自服务基础设施**

- 数据库、缓存、消息队列自服务申请
- 环境管理（基于 vCluster 的按需环境）
- 质量门禁统一化（SAST、SCA、单测覆盖率）
- 平台内部 SLO：门户可用性 99.9%、部署成功率 > 98%

**关键动作**：成立"平台产品委员会"，由核心业务团队技术 Leader 参与，季度评审路线图。

#### 阶段三（9~18 月）：产品化运营 + 高阶能力

目标：**平台像产品一样运营，持续创造差异化价值**

- 开发者 NPS 调查常态化
- 成本可视化与自助优化（接 FinOps）
- AI 能力接入（代码生成、故障诊断）
- 多云/多集群统一管理

**退出标准**：80% 的业务服务运行在平台黄金路径上，开发者 NPS > 40。

### 常见陷阱与规避

| 陷阱 | 规避 |
|------|------|
| **技术驱动，不关心开发者体验** | 先做用户研究，再定能力 |
| **一次建大而全** | 分阶段交付，先黄金路径跑通 |
| **强制推行** | 先用"胡萝卜"让团队自愿迁移，而非大棒 |
| **平台团队变成新瓶颈** | 能力要 API 化、自服务化，而非"我们帮你搞" |
| **只有平台没有治理** | 平台与治理并行，否则"劣币驱逐良币" |

## 🔗 相关概念

- **DevOps / SRE**：平台工程是 DevOps 在大规模组织中的工程化实现
- **GitOps**：平台的部署能力几乎都以 GitOps 为底座
- **云原生**：IDP 绝大多数构建在 Kubernetes 之上
- **FinOps**：平台是成本治理的天然载体
- **AI 辅助架构**：平台是 AI 能力对业务开发者赋能的最佳入口
- **服务治理**：服务目录 + 所有权模型是服务治理的前提
