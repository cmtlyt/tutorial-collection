# Docker

> **版本**：v1.1
> **最后更新**：2026-04-28

## 📚 概念介绍

Docker 是容器化技术的代表，它通过镜像分层、资源隔离和标准化打包，解决了"在我的机器上能运行"的经典问题。本节将深入讲解 Docker 的核心概念和最佳实践。

### 核心概念

- **镜像（Image）**：只读的应用运行环境模板，采用分层存储
- **容器（Container）**：镜像的运行实例，拥有独立的文件系统、网络和进程空间
- **分层存储**：镜像由多层只读层组成，启动容器时添加可写层
- **多阶段构建**：分离构建环境和运行环境，减小最终镜像体积

## 🧠 容器到底是什么？一句话定义

> **容器 = 被 Namespace 隔离、被 Cgroups 限制、以 UnionFS 打包的普通 Linux 进程。**

它不是虚拟机，没有独立内核，也没有"Docker Engine 运行时模拟层"。容器就是运行在宿主机内核上的**普通进程**，只是看不见/摸不到其他进程和资源。

### 容器 vs 虚拟机：架构本质差异

```
┌──────────────────────────┐    ┌──────────────────────────┐
│   App A  │   App B       │    │  Container A │ Container B│
├──────────┼───────────────┤    ├──────────────┴───────────┤
│ Bins/Libs│   Bins/Libs   │    │  Bins/Libs   │ Bins/Libs │
├──────────┼───────────────┤    ├──────────────┴───────────┤
│ Guest OS │   Guest OS    │    │    Docker Engine         │
├──────────┴───────────────┤    ├──────────────────────────┤
│       Hypervisor         │    │      Host OS Kernel      │
├──────────────────────────┤    ├──────────────────────────┤
│        Host OS           │    │        Hardware          │
├──────────────────────────┤    └──────────────────────────┘
│       Hardware           │
└──────────────────────────┘
         VM 架构                          容器架构
```

| 维度 | 虚拟机 | 容器 |
|------|-------|------|
| **隔离层级** | 硬件级（Hypervisor） | 进程级（内核特性） |
| **操作系统** | 每个 VM 独立 Guest OS | 共享宿主机内核 |
| **启动时间** | 分钟级 | 毫秒-秒级 |
| **资源开销** | GB 级（含 OS） | MB 级 |
| **隔离强度** | 强（独立内核） | 相对弱（共享内核，靠 Namespace） |
| **密度** | 单机数十个 | 单机数百至数千个 |
| **启动快慢的根因** | 要启动完整 OS | 只是 `fork + exec` |

关键结论：**容器牺牲了一部分隔离强度，换取了极致的启动速度和密度。** 这也是为什么安全敏感场景（多租户、金融）会用 Kata Containers、gVisor 等"安全容器"在容器外再套一层轻量虚拟化。

## ⚙️ 底层原理：容器的三大支柱

容器不是 Docker 发明的，它是 Linux 内核多项技术的组合应用。Docker 的贡献是把这些技术**包装成易用的工具链**。

### 支柱一：Namespace —— 视图隔离（看不见别人）

Namespace 把全局系统资源包装起来，让进程**认为自己独占**。Linux 提供 8 种 Namespace：

| Namespace | 隔离内容 | 类比 |
|-----------|---------|------|
| **PID** | 进程 ID | 每个容器都以为自己的应用是 PID 1 |
| **NET** | 网络设备/端口/路由 | 每个容器有独立网卡、独立 IP |
| **MNT** | 挂载点 | 每个容器看到不同的文件系统结构 |
| **UTS** | 主机名/域名 | 每个容器可以有自己的 hostname |
| **IPC** | 信号量/消息队列 | 进程间通信隔离 |
| **USER** | 用户/组 ID | 容器内的 root 映射到宿主机的普通用户 |
| **CGROUP** | cgroup 视图 | 看到的 cgroup 层级隔离 |
| **TIME** | 系统时间 | 可有独立的时钟（较新特性） |

创建 Namespace 的底层系统调用是 `unshare(2)` 和 `clone(2)`，Docker 只是对它们的调用者。

### 支柱二：Cgroups —— 资源限制（抢不走别人的）

Cgroups（Control Groups）负责**资源配额与计量**，回答三个问题：能用多少（limit）、优先级多高（weight）、用了多少（accounting）。

- **Cgroups v1**：每个资源一个层级（cpu、memory、blkio、net_cls 各自独立），灵活但复杂
- **Cgroups v2**：统一层级（2016 年主线内核，2019 年普及），更简洁、支持更好的 IO 限制

常见限制维度：CPU 时间片、内存上限（触及则 OOM Kill）、磁盘 IO、网络带宽、PID 数量、文件描述符。

**Namespace 管"你看见什么"，Cgroups 管"你能用多少"**，二者缺一不可。

### 支柱三：UnionFS —— 分层文件系统（镜像的魔法）

UnionFS（联合文件系统）让多个目录"叠加挂载"成一个视图，主流实现是 **OverlayFS**（内核 3.18+ 原生支持）：

```
Upper Layer (可写层，容器独有)   ← 容器运行时写入这里
──────────────────────────────
Lower Layer N (只读，镜像层 N)
──────────────────────────────
Lower Layer ... (只读)
──────────────────────────────
Lower Layer 0 (只读，基础镜像)
```

核心机制 **Copy-on-Write（写时复制）**：
- 读文件：从最上层开始往下找，命中就返回
- 写文件：先把文件从只读层复制到可写层，再修改

带来的三大好处：
1. **镜像共享**：10 个容器共用一份 Ubuntu 基础层，只有可写层各自独立
2. **秒级启动**：不需要复制整个文件系统
3. **高效分发**：`docker pull` 只下载本地缺失的层

这也解释了为什么要把 `COPY package.json` 和 `COPY .` 分两步写——利用**层缓存**加速构建。

## 📦 镜像：不只是"打包"，而是"标准化交付单元"

### OCI 规范：容器的"集装箱标准"

2015 年由 Docker、Google、CoreOS 等牵头成立 **OCI（Open Container Initiative）**，发布两个规范：

- **Image Spec**：镜像的文件组织格式（manifest、config、layers）
- **Runtime Spec**：容器的运行时契约（`runc` 是参考实现）

这让容器生态**摆脱了 Docker 单一厂商锁定**：
- 构建工具：Docker、Buildah、Kaniko、BuildKit
- 运行时：runc、crun、gVisor、Kata
- 编排调度：Kubernetes（通过 CRI 接口对接任意 OCI 运行时）

**Docker ≠ 容器**，Docker 只是其中一套最流行的工具链实现。

### 镜像的内部结构

一个镜像 = **一个 manifest.json + 一个 config.json + 若干 tar.gz 层文件**，所有内容按**内容寻址（content-addressable）**用 SHA256 校验。这意味着：
- **镜像不可篡改**：改一个字节，hash 就变了
- **天然去重**：同样内容的层全网唯一

## 🏛️ 设计哲学：不可变基础设施（Immutable Infrastructure）

Docker 推广的不仅是技术，更是一种**运维哲学变革**：

### 传统方式（可变基础设施 / Snowflake Server）

一台服务器跑了几年，经历过 N 次手工升级、补丁、调参。没人敢动，没人说得清它现在到底是什么状态。出问题只能"救火"，故障恢复靠运维老师傅的记忆。

### 容器方式（不可变基础设施 / Phoenix Server）

- **构建一次，到处运行**：镜像在 CI 流水线里固化，打完 tag 就冻结
- **要变更？重建镜像、销毁容器、启新容器**，绝不在运行的容器里改配置
- **环境一致性**：dev/test/prod 用完全相同的镜像，只注入不同的配置

这种思想的好处：
1. **可复现性**：随时可以精确还原某个版本的运行环境
2. **快速恢复**：出问题直接销毁重建，而不是诊断修复
3. **灰度/回滚简单**：就是切换镜像 tag
4. **审计友好**：每次变更都有版本，不存在"偷偷改配置"

## 🧭 容器安全的三个真相

1. **容器共享内核**：内核漏洞（如 Dirty Pipe CVE-2022-0847）能逃逸出容器，VM 则不会
2. **默认 root 是隐患**：容器内 root 可能通过 Namespace 映射成宿主机 root（需开启 user namespace 缓解）
3. **镜像即攻击面**：一个被污染的基础镜像会感染整个 CI 流水线（典型案例：2018 年 Docker Hub 的挖矿镜像事件）

所以生产环境要遵守：
- 非 root 用户运行（`USER` 指令）
- 最小镜像（distroless、alpine）减少攻击面
- 镜像扫描（Trivy、Clair、Snyk）纳入 CI
- 运行时只读（`--read-only`）

## 🎯 镜像构建与优化

### 基础 Dockerfile

```dockerfile
# 使用官方 Node.js 镜像作为基础镜像
FROM node:18-alpine

# 设置工作目录
WORKDIR /app

# 复制 package.json 和 package-lock.json
COPY package*.json ./

# 安装依赖
RUN npm ci --only=production

# 复制应用代码
COPY . .

# 暴露端口
EXPOSE 3000

# 启动应用
CMD ["node", "index.js"]
```

### 多阶段构建优化

多阶段构建是 2025 年的 Docker 最佳实践，可以显著减小镜像体积并提高安全性。

```dockerfile
# ==================== 构建阶段 ====================
FROM node:18-alpine AS builder

WORKDIR /app

# 复制依赖文件
COPY package*.json ./

# 安装所有依赖（包括开发依赖）
RUN npm ci

# 复制源代码
COPY . .

# 构建应用（TypeScript 示例）
RUN npm run build

# ==================== 运行阶段 ====================
FROM node:18-alpine AS runtime

# 安装 dumb-init 以正确处理信号
RUN apk add --no-cache dumb-init

# 创建非 root 用户
RUN addgroup -g 1001 -S nodejs && \
    adduser -S nodejs -u 1001

WORKDIR /app

# 从构建阶段复制依赖文件
COPY --from=builder --chown=nodejs:nodejs /app/node_modules ./node_modules

# 从构建阶段复制构建产物
COPY --from=builder --chown=nodejs:nodejs /app/dist ./dist

# 切换到非 root 用户
USER nodejs

# 使用 dumb-init 启动
ENTRYPOINT ["dumb-init", "--"]

# 启动应用
CMD ["node", "dist/index.js"]
```

### 镜像层优化技巧

```dockerfile
FROM node:18-alpine

WORKDIR /app

# ✅ 好的做法：先复制依赖文件，利用 Docker 层缓存
COPY package*.json ./
RUN npm ci --only=production

# ✅ 好的做法：只复制需要的文件
COPY src/ ./src/
COPY tsconfig.json ./

# ❌ 避免：复制整个项目导致缓存失效
# COPY . .

# ✅ 好的做法：合并 RUN 命令减少层数
RUN npm run build && \
    npm prune --production && \
    rm -rf src tsconfig.json

# ✅ 好的做法：使用 .dockerignore 排除不需要的文件
# .dockerignore 内容：
# node_modules
# npm-debug.log
# .git
# .env
# *.md
```

### .dockerignore 配置

```dockerignore
# 依赖目录
node_modules
npm-debug.log
yarn-error.log

# 版本控制
.git
.gitignore
.svn

# 环境配置
.env
.env.local
.env.*.local

# 测试和文档
*.md
test
coverage
.vscode
.idea

# 构建产物（如果使用多阶段构建）
dist
build

# 其他
.DS_Store
```

## 🌐 容器网络

### Docker 网络模式对比

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **bridge** | 默认模式，容器通过 veth pair 连接到 docker0 网桥 | 单机多容器通信 |
| **host** | 容器使用宿主机网络栈 | 高性能网络需求 |
| **overlay** | 跨主机通信网络 | Docker Swarm / Kubernetes |
| **none** | 无网络配置 | 自定义网络配置 |
| **macvlan** | 容器拥有独立 MAC 地址 | 需要容器直接接入物理网络 |

### 创建和使用自定义网络

```bash
# 创建自定义 bridge 网络
docker network create --driver bridge --subnet 172.20.0.0/16 my-app-network

# 查看网络详情
docker network inspect my-app-network

# 连接容器到网络
docker run -d --name app1 --network my-app-network -p 8080:8080 my-app:latest
docker run -d --name app2 --network my-app-network my-app:latest

# 容器间通过容器名互相访问
# 在 app1 中可以 ping app2
docker exec app1 ping app2
```

### Docker Compose 网络配置

```yaml
version: '3.8'

services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    networks:
      - frontend

  api:
    build: ./api
    networks:
      - frontend
      - backend
    depends_on:
      - db

  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_PASSWORD: example
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - backend

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true  # 内部网络，无法访问外网

volumes:
  db-data:
```

## 💾 存储卷管理

### 卷类型对比

| 类型 | 说明 | 生命周期 | 适用场景 |
|------|------|---------|---------|
| **bind mount** | 挂载宿主机目录 | 由宿主机管理 | 开发环境、配置文件 |
| **volume** | Docker 管理的存储 | 由 Docker 管理 | 数据持久化、数据共享 |
| **tmpfs** | 内存文件系统 | 容器生命周期 | 临时数据、敏感信息 |

### 使用 Volume 持久化数据

```bash
# 创建命名卷
docker volume create my-app-data

# 查看卷详情
docker volume inspect my-app-data

# 使用卷启动容器
docker run -d \
  --name postgres \
  -v my-app-data:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=example \
  postgres:15-alpine

# 清理卷（谨慎操作）
docker volume rm my-app-data
```

### Docker Compose 卷配置

```yaml
version: '3.8'

services:
  app:
    build: .
    volumes:
      # 命名卷 - 数据持久化
      - app-data:/app/data
      
      # bind mount - 开发环境代码热更新
      - ./src:/app/src:ro
      
      # tmpfs - 临时缓存
      - cache:/tmp/cache:rw,noexec,nosuid,size=100m

  redis:
    image: redis:alpine
    volumes:
      - redis-data:/data

volumes:
  app-data:
    driver: local
  redis-data:
    driver: local
```

## 📝 实际应用示例

### 完整的 Node.js 应用 Docker 化

**项目结构：**
```
my-app/
├── src/
│   ├── index.ts
│   └── utils.ts
├── package.json
├── tsconfig.json
├── Dockerfile
├── .dockerignore
└── docker-compose.yml
```

**Dockerfile：**
```dockerfile
# 构建阶段
FROM node:18-alpine AS builder

WORKDIR /app

# 复制依赖文件
COPY package*.json ./

# 安装所有依赖
RUN npm ci

# 复制源代码
COPY . .

# 构建应用
RUN npm run build

# 运行阶段
FROM node:18-alpine AS runtime

# 安装生产环境依赖
RUN apk add --no-cache dumb-init curl

# 创建非 root 用户
RUN addgroup -g 1001 -S nodejs && \
    adduser -S nodejs -u 1001

WORKDIR /app

# 从构建阶段复制依赖
COPY --from=builder --chown=nodejs:nodejs /app/node_modules ./node_modules

# 从构建阶段复制构建产物
COPY --from=builder --chown=nodejs:nodejs /app/dist ./dist

# 健康检查
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1

# 切换用户
USER nodejs

# 使用 dumb-init
ENTRYPOINT ["dumb-init", "--"]

# 启动应用
CMD ["node", "dist/index.js"]
```

**docker-compose.yml：**
```yaml
version: '3.8'

services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
      - PORT=3000
    networks:
      - app-network
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data
    networks:
      - app-network
    restart: unless-stopped
    command: redis-server --appendonly yes

networks:
  app-network:
    driver: bridge

volumes:
  redis-data:
```

**启动应用：**
```bash
# 构建并启动
docker-compose up -d

# 查看日志
docker-compose logs -f app

# 停止服务
docker-compose down

# 停止并删除数据卷
docker-compose down -v
```
