# Kubernetes

## 📚 概念介绍

Kubernetes（K8s）是目前最流行的容器编排平台，它提供了自动部署、扩展和管理容器化应用的能力。本节将系统讲解 Kubernetes 的核心概念和高级特性。

### 核心架构

```
┌─────────────────────────────────────────────────────────┐
│                    Control Plane                        │
├─────────────────────────────────────────────────────────┤
│  API Server  │  etcd  │  Scheduler  │  Controller Mgr  │
└─────────────────────────────────────────────────────────┘
                           ↕
┌─────────────────────────────────────────────────────────┐
│                    Worker Nodes                         │
├─────────────────────────────────────────────────────────┤
│  kubelet  │  kube-proxy  │  Container Runtime          │
└─────────────────────────────────────────────────────────┘
```

### 核心概念

- **Pod**：Kubernetes 最小的调度单元，包含一个或多个容器
- **Deployment**：管理无状态应用的部署和滚动更新
- **Service**：提供稳定的网络访问入口和服务发现
- **ConfigMap/Secret**：配置管理和敏感信息存储
- **Ingress**：HTTP/HTTPS 路由规则

## 🧬 K8s 的前世今生：从 Borg 到 Kubernetes

K8s 并非凭空设计，它是 Google **十多年大规模集群调度经验的开源提炼**。

- **2003-2014**：Google 内部用 **Borg** 管理全球数据中心，跑过搜索、Gmail、YouTube 所有核心业务
- **2013**：Google 发布 Omega 论文，阐述"共享状态、乐观并发"的调度器设计
- **2014**：Joe Beda、Brendan Burns、Craig McLuckie 发起 Kubernetes 项目（希腊语"舵手"）
- **2015**：Borg 论文终于解密公开，印证了 K8s 的设计理念
- **2017**：K8s 赢得编排之战（击败 Docker Swarm、Mesos）
- **2020**：K8s 弃用 Docker 作为运行时，转向 CRI（Container Runtime Interface）标准

**K8s 最大的创新不是技术细节，而是把 Borg 的运维经验沉淀成了一套通用的 API 抽象**，让任何公司都能拥有"Google 级别"的调度能力。

## 🏛️ 核心设计哲学（理解 K8s 的钥匙）

### 哲学一：声明式 API（Declarative API）

这是 K8s 与传统运维工具（shell 脚本、Ansible 命令式 playbook）的**本质分野**。

| 命令式 | 声明式 |
|-------|-------|
| "请在 A 节点启动 3 个 Nginx 容器" | "我要 3 个 Nginx 实例" |
| 关注**执行步骤（HOW）** | 关注**期望状态（WHAT）** |
| 出错要人工介入 | 系统自动收敛到期望状态 |
| 可重入性差 | 天然幂等 |

你对 K8s 说的话永远是：**"我想要什么"**。至于怎么到达那个状态、中途哪个 Pod 挂了要不要重启、节点宕机怎么迁移——那是 K8s 的事。

### 哲学二：控制循环（Control Loop / Reconciliation）

K8s 的所有 Controller 都遵循同一个模式，像**恒温空调**一样工作：

```
┌──────────────────────────────────────────┐
│                                          │
│    ┌──────────────┐    ┌──────────────┐  │
│    │ Desired State│    │Current State │  │
│    │  (期望状态)  │    │  (实际状态)  │  │
│    └──────┬───────┘    └──────┬───────┘  │
│           │                   │          │
│           └────────┬──────────┘          │
│                    ↓                     │
│             对比差异 (Diff)              │
│                    ↓                     │
│             执行调整动作                  │
│                    ↓                     │
│             更新实际状态                  │
│                    │                     │
│                    └──────(循环)────────┐│
└──────────────────────────────────────────┘
```

这种设计带来三个关键特性：

1. **最终一致性**：无论发生什么（网络分区、节点宕机、误操作），只要 desired state 还在，系统终会收敛
2. **自愈能力**：Pod 挂了？Deployment Controller 会创建新的。节点故障？Pod 会被迁移
3. **可组合性**：每个 Controller 只管一件事，组合起来形成复杂行为

### 哲学三：万物皆资源（Everything is a Resource）

K8s 把一切抽象成 **RESTful 资源对象**（Resource），可被 `kubectl get/apply/delete` 统一操作：

- 工作负载：Pod、Deployment、StatefulSet、DaemonSet、Job、CronJob
- 网络：Service、Ingress、NetworkPolicy、EndpointSlice
- 存储：PV、PVC、StorageClass
- 配置：ConfigMap、Secret
- RBAC：Role、RoleBinding、ServiceAccount

这种统一抽象使得**扩展机制**变得简单——你可以通过 CRD（CustomResourceDefinition）注册自己的资源类型，K8s 把它当作一等公民对待（这就是 Operator 的基础）。

## ⚙️ 集群架构深入剖析

### API Server：唯一的入口与真相源

所有组件（kubelet、Scheduler、Controller、kubectl）都**只能通过 API Server 交互**，从不直接访问 etcd 或彼此通信。这样做的好处：

- **统一鉴权**：RBAC、Admission Webhook 在这里一站式完成
- **审计可追溯**：所有变更有日志
- **版本化**：API 分组与版本（v1、apps/v1、networking.k8s.io/v1）让升级兼容

### etcd：分布式的"集群大脑"

- **存储内容**：所有资源对象的当前状态、集群元数据
- **一致性保证**：基于 **Raft 共识协议**（CP 系统，一致性优先于可用性）
- **集群规模**：奇数节点（3/5/7），能容忍 `(n-1)/2` 台故障
- **性能瓶颈**：etcd 的写性能直接决定 K8s 集群规模上限（通常单集群 Pod 数不超过 15 万）

### Scheduler：打分决策者

调度 Pod 分两个阶段：

1. **Filter（预选）**：排除不满足硬约束的节点（资源不足、亲和性不匹配、污点、节点选择器）
2. **Score（优选）**：对候选节点打分（资源均衡、镜像本地化、Pod 反亲和等），选最高分

自定义调度需求可通过 **Scheduling Framework**（扩展点）或多调度器共存实现。

### List-Watch 机制：K8s 通信核心

Controller 不轮询 API Server，而是用 **List（全量） + Watch（增量事件流）** 模式：

- 首次启动：List 一次所有相关资源作为本地缓存
- 之后：通过 Watch HTTP 长连接接收事件（Added/Modified/Deleted）
- 本地使用 **Informer + Indexer** 做缓存索引

这种设计比"定时轮询"高效得多，也是 K8s 能支撑上万节点的关键。

## 🎯 工作负载控制器：为什么要这么分？

K8s 不只给你一个"Deployment"就完事，而是提供一整套控制器。每种都对应一种典型的**应用模型**：

| 控制器 | 适用场景 | 关键特性 | 典型应用 |
|--------|---------|---------|---------|
| **Deployment** | 无状态服务 | 副本任意替换、滚动更新 | Web API、无状态微服务 |
| **StatefulSet** | 有状态服务 | 稳定网络 ID、有序部署、独立持久化 | MySQL、Kafka、Zookeeper |
| **DaemonSet** | 节点级守护进程 | 每个节点一份 | 日志采集、监控 Agent、CNI |
| **Job** | 一次性任务 | 跑完即退，失败重试 | 数据迁移、批处理 |
| **CronJob** | 定时任务 | 按 cron 表达式触发 Job | 定期报表、备份 |

为什么 StatefulSet 这么"重"？因为数据库类应用需要：
- **稳定的网络标识**：`mysql-0` 永远是 `mysql-0`，而不像 Deployment 的 Pod 名字随机生成
- **有序性**：启动时 `mysql-0 → mysql-1 → mysql-2`，缩容反向，保证主从关系
- **独立存储**：每个 Pod 一个 PVC，Pod 迁移带着数据走

## 🌐 Pod：K8s 为什么不用"容器"作为最小单元？

容器本身已经是隔离单元，K8s 为什么还要再包一层 Pod？答案是：**很多真实场景需要多个紧耦合容器共享资源**。

Pod 内的容器共享：
- **Network Namespace**（同一 IP，通过 localhost 通信）
- **IPC Namespace**、**UTS Namespace**
- **Volume**（共享存储）

典型 Pod 模式：
- **Sidecar 模式**：主容器 + 辅助容器（日志收集、配置热加载）
- **Ambassador 模式**：代理容器统一处理外部连接（如 Envoy）
- **Adapter 模式**：统一不同应用的输出格式

## 🔌 "三大接口"：K8s 的扩展性哲学

K8s 本身不关心"容器怎么跑、网络怎么通、存储怎么接"，它把这些**全部接口化**，让生态百花齐放。

### CRI（Container Runtime Interface）

K8s 不直接调用 Docker，而是通过 CRI 协议与运行时对话。实现者：
- **containerd**：Docker 的底层，现为主流
- **CRI-O**：RedHat 主推，最轻量
- **gVisor、Kata**：强隔离的"安全容器"

### CNI（Container Network Interface）

Pod 的网络由 CNI 插件负责。不同插件有不同模型：
- **Flannel**：Overlay 网络，简单
- **Calico**：BGP 路由，高性能，支持 NetworkPolicy
- **Cilium**：基于 eBPF，极致性能 + 可观测性
- **云厂商 CNI**：直接用 VPC 网络（AWS VPC CNI、阿里云 Terway）

K8s 的核心网络假设：
1. 所有 Pod 之间能**直接通信**（无 NAT）
2. 所有节点能和所有 Pod 通信
3. Pod 自己看到的 IP = 别人看到的 IP

### CSI（Container Storage Interface）

存储后端的接入协议。过去 K8s 自带一堆 in-tree 插件（AWS EBS、GCE PD、Ceph），维护成本巨大。CSI 让存储厂商独立开发插件，K8s 本体瘦身。

## 🎭 Service 与负载均衡的真相

Service 并不是一个"真实存在的东西"，而是 **kube-proxy 在每个节点维护的 iptables/IPVS 规则**。

- **ClusterIP**：一个虚拟 IP，节点内核劫持目标 IP 为该 ClusterIP 的包，随机转发到后端 Pod
- **NodePort**：在每个节点开同一个端口
- **LoadBalancer**：调用云厂商 API 创建外部 LB 并指向 NodePort
- **Headless Service**：`clusterIP: None`，DNS 直接返回后端 Pod IP 列表（StatefulSet 常用）

Pod 重启 IP 会变，但 Service 的 ClusterIP 稳定，这就是"服务发现"的基础。

## 🧩 Operator 模式：把运维知识编入软件

传统运维：DBA 凭经验维护 MySQL 集群，出问题靠手册。
Operator 模式：**用代码描述"一个合格 DBA 的操作逻辑"，让集群自己运维自己**。

Operator = **CRD（自定义资源）+ Controller（控制循环）**。

例子：MySQL Operator 接收一个 `Cluster` CRD，自动：
- 部署主从 StatefulSet
- 主节点挂了就选举新主
- 定期备份到 S3
- 应用新版本时滚动升级

这是 K8s 超越 Docker Swarm、Mesos 的**关键武器**——它不只是编排容器，它是**可编程的控制平面**。

### Pod 基础配置

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app-pod
  labels:
    app: my-app
    version: v1
spec:
  # 容器定义
  containers:
  - name: app-container
    image: my-app:1.0.0
    ports:
    - containerPort: 3000
      name: http
    # 资源限制
    resources:
      requests:
        cpu: "100m"
        memory: "128Mi"
      limits:
        cpu: "500m"
        memory: "512Mi"
    # 健康检查
    livenessProbe:
      httpGet:
        path: /health
        port: 3000
      initialDelaySeconds: 30
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /ready
        port: 3000
      initialDelaySeconds: 5
      periodSeconds: 5
    # 环境变量
    env:
    - name: NODE_ENV
      value: "production"
    - name: DATABASE_URL
      valueFrom:
        secretKeyRef:
          name: app-secrets
          key: database-url
    # 挂载配置
    volumeMounts:
    - name: config-volume
      mountPath: /app/config
      readOnly: true
  # 卷定义
  volumes:
  - name: config-volume
    configMap:
      name: app-config
  # 重启策略
  restartPolicy: Always
```

### Pod 亲和性与反亲和性

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cache-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: cache
  template:
    metadata:
      labels:
        app: cache
    spec:
      # 亲和性规则
      affinity:
        # Pod 亲和性 - 调度到相同节点的 Pod
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - web
            topologyKey: kubernetes.io/hostname
        # Pod 反亲和性 - 调度到不同节点的 Pod
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchExpressions:
                - key: app
                  operator: In
                  values:
                  - cache
              topologyKey: kubernetes.io/hostname
      containers:
      - name: redis
        image: redis:7-alpine
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
```


## 🔧 Operator 模式

### Operator 概念

Operator 是一种使用 Kubernetes 自定义资源（CRD）和控制器来管理应用的方法。它将运维知识编码到软件中，实现应用的自动化管理。

### 简单的 CRD 定义

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.myapp.example.com
spec:
  group: myapp.example.com
  versions:
  - name: v1alpha1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              replicas:
                type: integer
              storage:
                type: string
              version:
                type: string
  scope: Namespaced
  names:
    plural: databases
    singular: database
    kind: Database
    shortNames:
    - db
```

### 自定义资源示例

```yaml
apiVersion: myapp.example.com/v1alpha1
kind: Database
metadata:
  name: my-database
spec:
  replicas: 3
  storage: 10Gi
```

## 📝 实际应用示例

### 完整的应用部署清单

**deployment.yaml：**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  labels:
    app: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web-app
        image: web-app:1.0.0
        ports:
        - containerPort: 3000
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5
        env:
        - name: NODE_ENV
          value: "production"
        - name: REDIS_HOST
          value: "redis-service"
        volumeMounts:
        - name: config
          mountPath: /app/config
      volumes:
      - name: config
        configMap:
          name: web-app-config
```

**service.yaml：**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app-service
spec:
  type: ClusterIP
  selector:
    app: web-app
  ports:
  - port: 80
    targetPort: 3000
```

**configmap.yaml：**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-app-config
data:
  config.json: |
    {
      "logLevel": "info",
      "features": {
        "featureA": true,
        "featureB": false
      }
    }
```

**ingress.yaml：**
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: web-app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-app-service
            port:
              number: 80
```

**部署命令：**
```bash
# 应用所有配置
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f configmap.yaml
kubectl apply -f ingress.yaml

# 查看部署状态
kubectl get deployments
kubectl get pods
kubectl get services
kubectl get ingress

# 查看日志
kubectl logs -f deployment/web-app

# 扩缩容
kubectl scale deployment web-app --replicas=5

# 滚动更新
kubectl set image deployment/web-app web-app=web-app:1.1.0

# 查看更新状态
kubectl rollout status deployment/web-app

# 回滚
kubectl rollout undo deployment/web-app
```
