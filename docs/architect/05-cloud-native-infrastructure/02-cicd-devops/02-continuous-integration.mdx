# 持续集成

> **版本**：v1.1
> **最后更新**：2026-04-28

## 📚 概念介绍

持续集成（Continuous Integration，CI）是一种开发实践，要求开发人员频繁地（通常每天多次）将代码集成到共享仓库中。每次集成都通过自动化的构建和测试来验证，尽早发现集成错误。

### 核心原则

- **频繁集成**：开发人员每天至少提交一次代码
- **自动化构建**：每次提交都触发自动构建
- **自动化测试**：构建后自动运行测试套件
- **快速反馈**：构建失败时立即通知团队
- **保持构建绿色**：构建失败时优先修复

### CI 流程

```
代码提交 → 触发构建 → 代码检查 → 单元测试 → 集成测试 → 构建产物 → 部署到测试环境
    ↓
    失败 → 通知开发者 → 修复 → 重新构建
```

## 🧠 CI 到底在解决什么问题？

### 历史痛点：集成地狱（Integration Hell）

在 CI 出现前（~2000 年前），软件开发流程长这样：

- 开发团队分若干组，各自维护一条长期分支，开发周期以**月**为单位
- 每个组完成后，合并到主干
- 合并时爆发大量冲突，调试、解决冲突、回归测试，又花费数周
- 经常发现"两个功能单独都 OK，合到一起就崩"

这种痛苦被 Martin Fowler 形象地称为 **"集成地狱（Integration Hell）"**。

### Kent Beck 与极限编程（XP）

**2000 年**，Kent Beck 在《Extreme Programming Explained》中首次系统描述了 CI 实践。核心洞见：

> **集成的痛苦与集成的频率成反比。** 合并得越频繁，冲突越小；合并得越少，冲突越大。

因此**把"大爆炸合并"变成"持续小步合并"**——CI 的本质就这么简单。Fowler 后来在 2006 年整理出著名的《Continuous Integration》一文，给出 10 条准则，至今仍是业界金标准。

## 🏛️ CI 的三大基石原则

### 基石一：唯一代码源（Single Source Repository）

所有代码（含构建脚本、配置、测试）在一个可版本化的仓库里。**没有"本地 jar 包"、"某个工程师电脑上的脚本"、"神秘的 FTP 目录"**。

推论：构建必须能在全新机器上从零开始成功完成，这就是 Trivial Build 原则。

### 基石二：构建即代码（Build as Code）

构建脚本（Makefile、`package.json` 里的 scripts、`.github/workflows/*.yml`）必须：
- **版本化**：和代码一起被 Git 管理
- **声明式**：描述"怎么构建"而非"在哪台机器上构建"
- **自包含**：只依赖代码仓库 + 明确声明的外部依赖

### 基石三：构建可重现（Reproducible Builds）

同一份源代码，不同时间、不同机器构建出来的**产物应该完全一致**（理想状态下二进制相同）。
破坏可重现性的三大杀手：
- **隐式依赖**：没锁版本的依赖（`npm install` 不带 lockfile）
- **构建时间污染**：把构建时刻、主机名等写进产物
- **外部状态**：构建过程中访问"今天可用明天就没了"的资源

对策：lockfile、容器化构建环境、制品签名（sigstore、provenance）。

## 🔄 从 CI 看分支模型：Trunk-Based vs GitFlow

分支模型不是"选个风格"，而是**决定了 CI 能走多远**的战略性选择。

### GitFlow（2010，Vincent Driessen 提出）

```
main ───────────●──────●────●──── (生产环境)
                │      │    │
release ────────●──●───●────        (发布准备)
                │  │   │
develop ────●──●──●───●──●──●──     (集成分支)
            │      │      │
feature1 ───●──────●               (功能开发)
feature2 ──────────●────●          (长期存活)
```

优点：分支角色明确、发布节奏清晰
缺点：
- **分支寿命长**，集成延迟到"merge to develop"时才发生 → **集成地狱回归**
- **自动化部署困难**：`develop` 不等于可上线状态
- **不适合连续部署**

### Trunk-Based Development（主干开发）

```
main ────●──●──●──●──●──●──●──●──●─── (唯一长期分支)
         │  │           │  │
short1 ──●  │           │  │        (短命分支，<1 天)
short2 ─────●───────────●           (快速合入 main)
short3 ──────────────────●
```

核心实践：
- **所有人直接在 main 分支或极短分支上工作**（生命周期 \<1 天）
- 未完成的功能用 **Feature Toggle（特性开关）** 隐藏，而不是藏在分支里
- **CI 对 main 每次提交全量运行**，main 随时可发布

DORA 研究证实：**Trunk-Based Development 是精英团队的共同特征**。原因很简单——分支越短，集成痛苦越小，DORA 四指标自然全面优于 GitFlow。

### 选型建议

| 场景 | 推荐模型 |
|------|---------|
| 需要严格版本发布（如 SaaS 独立版本、固件） | GitFlow / Release Branch |
| 持续部署的云原生应用 | Trunk-Based + Feature Flag |
| 开源项目（外部贡献者多） | GitHub Flow（轻量版 Trunk-Based） |

## 🚀 CI 流水线的阶段哲学：快速反馈金字塔

好的 CI 流水线**按"跑得越快越靠前"排列**，构成反馈金字塔：

```
        ┌─────────────────────┐
        │   部署/E2E 测试      │  慢（分钟-小时），贵
        ├─────────────────────┤
        │     集成测试         │  中（分钟）
        ├─────────────────────┤
        │     单元测试         │  快（秒）
        ├─────────────────────┤
        │   Lint / 类型检查    │  极快（秒内）
        └─────────────────────┘
              更快更多
```

设计原则：
1. **Fail Fast（快速失败）**：便宜的检查（lint、类型）先跑，1 秒内失败比 30 分钟后失败好得多
2. **并行化**：独立阶段并行（lint 和单元测试可同时跑）
3. **分层隔离**：昂贵的 E2E 测试只在合并主干前运行

这种结构下，开发者 **99% 的错误会在 5 分钟内得到反馈**，不必等半小时 CI 才发现拼错了变量名。

## 💾 构建缓存：CI 性能的最大杠杆

CI 慢不是计算慢，**95% 的时间花在重复做上次已经做过的事**：装依赖、编译未变化的文件、下载 Docker 层。

### 缓存层级（从浅到深）

1. **依赖缓存**：`node_modules`、`.m2`、`.gradle` 目录，基于 lockfile hash
2. **编译产物缓存**：增量编译器（Gradle Incremental、Turborepo、Bazel）
3. **Docker 层缓存**：Dockerfile 分层设计 + `--cache-from` 复用
4. **远程构建缓存**：Bazel Remote Cache、Nx Cloud 等分布式缓存

### 黄金法则

> **缓存失效的颗粒度应该等于决定构建产物的最小依赖集。**

比如修改 `package.json` 应该让依赖缓存失效，但改一个业务 `.ts` 文件不应该。Dockerfile 里先 `COPY package*.json` 再 `RUN npm ci`、最后才 `COPY . .` 就是这个道理的体现。

## 🛡️ 质量门禁：什么该拦、什么不该拦

质量门禁（Quality Gate）= 在 CI 中设置规则，不达标不让合并。常见门禁：

| 门禁 | 合理性 | 常见陷阱 |
|------|-------|---------|
| 单元测试全部通过 | ✅ 强烈推荐 | 测试不稳定（flaky）导致信任流失 |
| 代码覆盖率阈值 | ⚠️ 谨慎 | 为凑指标写无意义测试，变成"赎罪券" |
| Lint / 格式化 | ✅ 推荐 | 用 auto-fix，别让人工处理 |
| 安全漏洞扫描 | ✅ 推荐 | 区分 critical/high/medium，分级处理 |
| 代码审查通过 | ✅ 强烈推荐 | - |
| 性能基准不退化 | ⚠️ 高阶 | 需要稳定的基准环境 |

**反模式警告**：质量门禁过多会让开发者想方设法绕过（如加 `// eslint-disable`）。门禁是**辅助**，不是**审判**。文化先行，工具其次。

## 🎯 GitHub Actions

### 基础工作流配置

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    
    strategy:
      matrix:
        node-version: [18.x, 20.x]
    
    steps:
    - name: 检出代码
      uses: actions/checkout@v4
    
    - name: 设置 Node.js ${{ matrix.node-version }}
      uses: actions/setup-node@v4
      with:
        node-version: ${{ matrix.node-version }}
        cache: 'npm'
    
    - name: 安装依赖
      run: npm ci
    
    - name: 代码检查
      run: npm run lint
    
    - name: 单元测试
      run: npm run test:unit
    
    - name: 集成测试
      run: npm run test:integration
    
    - name: 代码覆盖率
      run: npm run test:coverage
    
    - name: 上传覆盖率报告
      uses: codecov/codecov-action@v4
      with:
        files: ./coverage/lcov.info
        flags: unittests
        name: codecov-umbrella
```

### 多阶段构建流水线

```yaml
name: Multi-Stage CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  # 阶段1：代码质量检查
  quality:
    name: 代码质量检查
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    
    - name: 设置 Node.js
      uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm'
    
    - name: 安装依赖
      run: npm ci
    
    - name: ESLint 检查
      run: npm run lint
    
    - name: Prettier 检查
      run: npm run format:check
    
    - name: TypeScript 类型检查
      run: npm run type-check

  # 阶段2：单元测试
  test:
    name: 单元测试
    runs-on: ubuntu-latest
    needs: quality
    steps:
    - uses: actions/checkout@v4
    
    - name: 设置 Node.js
      uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm'
    
    - name: 安装依赖
      run: npm ci
    
    - name: 运行单元测试
      run: npm run test:unit -- --coverage
    
    - name: 上传覆盖率
      uses: codecov/codecov-action@v4

  # 阶段3：构建
  build:
    name: 构建应用
    runs-on: ubuntu-latest
    needs: test
    steps:
    - uses: actions/checkout@v4
    
    - name: 设置 Node.js
      uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm'
    
    - name: 安装依赖
      run: npm ci
    
    - name: 构建应用
      run: npm run build
    
    - name: 上传构建产物
      uses: actions/upload-artifact@v4
      with:
        name: build-artifacts
        path: dist/
        retention-days: 7

  # 阶段4：Docker 镜像构建
  docker:
    name: 构建 Docker 镜像
    runs-on: ubuntu-latest
    needs: build
    steps:
    - uses: actions/checkout@v4
    
    - name: 设置 Docker Buildx
      uses: docker/setup-buildx-action@v3
    
    - name: 登录到 Docker Hub
      uses: docker/login-action@v3
      with:
        username: ${{ secrets.DOCKER_USERNAME }}
        password: ${{ secrets.DOCKER_PASSWORD }}
    
    - name: 构建并推送镜像
      uses: docker/build-push-action@v5
      with:
        context: .
        push: true
        tags: |
          my-registry/my-app:${{ github.sha }}
          my-registry/my-app:latest
        cache-from: type=gha
        cache-to: type=gha,mode=max
```

### 代码质量门禁

```yaml
name: Quality Gates

on:
  pull_request:
    branches: [ main ]

jobs:
  quality-gate:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0  # 获取完整历史用于 SonarQube
    
    - name: 设置 Node.js
      uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm'
    
    - name: 安装依赖
      run: npm ci
    
    - name: 运行测试并生成覆盖率
      run: npm run test:coverage
    
    - name: SonarQube 扫描
      uses: SonarSource/sonarqube-scan-action@master
      env:
        SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
        SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}
    
    - name: 质量门禁检查
      run: |
        if [ $? -ne 0 ]; then
          echo "❌ 质量门禁检查失败"
          exit 1
        fi
        echo "✅ 质量门禁检查通过"
```

## 🔧 GitLab CI

### GitLab CI 配置

```yaml
# .gitlab-ci.yml
stages:
  - quality
  - test
  - build
  - deploy

variables:
  NODE_VERSION: "20"
  CACHE_KEY: "${CI_COMMIT_REF_SLUG}"

# 缓存配置
cache:
  key: ${CACHE_KEY}
  paths:
    - node_modules/

# 代码质量检查
code_quality:
  stage: quality
  image: node:${NODE_VERSION}
  before_script:
    - npm ci
  script:
    - npm run lint
    - npm run format:check
    - npm run type-check
  only:
    - branches
    - merge_requests

# 单元测试
unit_test:
  stage: test
  image: node:${NODE_VERSION}
  before_script:
    - npm ci
  script:
    - npm run test:unit -- --coverage
  coverage: '/All files[^|]*\|[^|]*\s+([\d\.]+)/'
  artifacts:
    reports:
      coverage_report:
        coverage_format: cobertura
        path: coverage/cobertura-coverage.xml
  only:
    - branches
    - merge_requests

# 集成测试
integration_test:
  stage: test
  image: node:${NODE_VERSION}
  services:
    - postgres:15-alpine
    - redis:7-alpine
  variables:
    POSTGRES_DB: test_db
    POSTGRES_USER: test_user
    POSTGRES_PASSWORD: test_pass
    REDIS_HOST: redis
  before_script:
    - npm ci
  script:
    - npm run test:integration
  only:
    - branches
    - merge_requests

# 构建应用
build:
  stage: build
  image: node:${NODE_VERSION}
  before_script:
    - npm ci
  script:
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 week
  only:
    - main
    - develop

# 部署到开发环境
deploy_dev:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s)
    - echo "$SSH_PRIVATE_KEY" | tr -d '\r' | ssh-add -
    - mkdir -p ~/.ssh
    - chmod 700 ~/.ssh
    - ssh-keyscan $DEPLOY_HOST >> ~/.ssh/known_hosts
    - chmod 644 ~/.ssh/known_hosts
  script:
    - scp -r dist/* $DEPLOY_USER@$DEPLOY_HOST:/var/www/dev/
    - ssh $DEPLOY_USER@$DEPLOY_HOST "cd /var/www/dev && pm2 restart all"
  only:
    - develop
  when: manual

# 部署到生产环境
deploy_prod:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s)
    - echo "$SSH_PRIVATE_KEY" | tr -d '\r' | ssh-add -
    - mkdir -p ~/.ssh
    - chmod 700 ~/.ssh
    - ssh-keyscan $DEPLOY_HOST >> ~/.ssh/known_hosts
    - chmod 644 ~/.ssh/known_hosts
  script:
    - scp -r dist/* $DEPLOY_USER@$DEPLOY_HOST:/var/www/prod/
    - ssh $DEPLOY_USER@$DEPLOY_HOST "cd /var/www/prod && pm2 restart all"
  only:
    - main
  when: manual
```

## 📝 实际应用示例

### 完整的 GitHub Actions CI/CD 流水线

```yaml
name: Complete CI/CD Pipeline

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]
  release:
    types: [ created ]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # 代码质量检查
  quality:
    name: 代码质量检查
    runs-on: ubuntu-latest
    steps:
    - name: 检出代码
      uses: actions/checkout@v4
      with:
        fetch-depth: 0
    
    - name: 设置 Node.js
      uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm'
    
    - name: 安装依赖
      run: npm ci
    
    - name: ESLint 检查
      run: npm run lint
    
    - name: Prettier 检查
      run: npm run format:check
    
    - name: TypeScript 类型检查
      run: npm run type-check
    
    - name: 安全审计
      run: npm audit --audit-level=moderate

  # 测试
  test:
    name: 测试
    runs-on: ubuntu-latest
    needs: quality
    services:
      postgres:
        image: postgres:15-alpine
        env:
          POSTGRES_DB: test_db
          POSTGRES_USER: test_user
          POSTGRES_PASSWORD: test_pass
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
        ports:
          - 5432:5432
      redis:
        image: redis:7-alpine
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
        ports:
          - 6379:6379
    
    steps:
    - name: 检出代码
      uses: actions/checkout@v4
    
    - name: 设置 Node.js
      uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm'
    
    - name: 安装依赖
      run: npm ci
    
    - name: 运行测试
      run: npm run test:ci
      env:
        DATABASE_URL: postgresql://test_user:test_pass@localhost:5432/test_db
        REDIS_URL: redis://localhost:6379
    
    - name: 上传覆盖率
      uses: codecov/codecov-action@v4
      with:
        files: ./coverage/lcov.info
        flags: unittests
        name: codecov-umbrella

  # 构建
  build:
    name: 构建
    runs-on: ubuntu-latest
    needs: test
    steps:
    - name: 检出代码
      uses: actions/checkout@v4
    
    - name: 设置 Node.js
      uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm'
    
    - name: 安装依赖
      run: npm ci
    
    - name: 构建应用
      run: npm run build
    
    - name: 上传构建产物
      uses: actions/upload-artifact@v4
      with:
        name: build-artifacts
        path: dist/
        retention-days: 7

  # Docker 镜像构建和推送
  docker:
    name: Docker 镜像构建
    runs-on: ubuntu-latest
    needs: build
    permissions:
      contents: read
      packages: write
    steps:
    - name: 检出代码
      uses: actions/checkout@v4
    
    - name: 设置 Docker Buildx
      uses: docker/setup-buildx-action@v3
    
    - name: 登录到容器注册表
      uses: docker/login-action@v3
      with:
        registry: ${{ env.REGISTRY }}
        username: ${{ github.actor }}
        password: ${{ secrets.GITHUB_TOKEN }}
    
    - name: 提取元数据
      id: meta
      uses: docker/metadata-action@v5
      with:
        images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
        tags: |
          type=ref,event=branch
          type=ref,event=pr
          type=semver,pattern={{version}}
          type=semver,pattern={{major}}.{{minor}}
          type=sha,prefix={{branch}}-
    
    - name: 构建并推送镜像
      uses: docker/build-push-action@v5
      with:
        context: .
        push: true
        tags: ${{ steps.meta.outputs.tags }}
        labels: ${{ steps.meta.outputs.labels }}
        cache-from: type=gha
        cache-to: type=gha,mode=max

  # 部署到开发环境
  deploy_dev:
    name: 部署到开发环境
    runs-on: ubuntu-latest
    needs: docker
    if: github.ref == 'refs/heads/develop'
    environment:
      name: development
      url: https://dev.example.com
    steps:
    - name: 部署到开发环境
      run: |
        echo "部署到开发环境..."
```
