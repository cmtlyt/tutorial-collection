# 持续部署

> **版本**：v1.1
> **最后更新**：2026-04-28

## 📚 概念介绍

持续部署（Continuous Deployment，CD）是持续集成的延伸，它将通过所有测试的代码自动部署到生产环境。本节将讲解各种部署策略和 GitOps 实践。

### 核心原则

- **自动化部署**：所有部署都通过自动化流程完成
- **零停机部署**：部署过程中不影响用户访问
- **快速回滚**：出现问题能够快速回滚到上一版本
- **渐进式发布**：逐步向用户推送新版本，降低风险

### 部署策略对比

| 策略 | 停机时间 | 回滚速度 | 资源成本 | 复杂度 | 适用场景 |
|------|---------|---------|---------|-------|---------|
| **蓝绿部署** | 无 | 极快 | 2x | 中 | 关键业务、需要快速回滚 |
| **金丝雀发布** | 无 | 快 | 1.x | 高 | 需要验证的变更、A/B测试 |
| **滚动更新** | 无 | 中 | 1x | 低 | 常规变更、无状态服务 |
| **灰度发布** | 无 | 快 | 1.x | 高 | 按用户群验证、渐进式发布 |

## 🧠 为什么需要部署策略？—— 风险与速度的权衡艺术

部署的本质是**把变更推向用户**。但任何变更都有风险，所以每种部署策略都在回答同一个问题：

> **如何以最小的"爆炸半径"，最快地验证一个变更在真实流量下的表现？**

"爆炸半径"（Blast Radius）是部署策略的核心概念：**一次糟糕的部署能伤害到多少用户、多少流量、多少数据？**

```
风险   │ 蓝绿 (切换瞬间 100%) ┐
高     │                      │
       │  滚动更新 (逐步替换)  │  传统方式
       │                      │
       │  金丝雀 (从 1% 起)    ┘  渐进式交付
低     │  特性开关 (可随时关闭)
       └───────────────────────────────→ 时间/粒度
         粗粒度              细粒度
```

### 部署 ≠ 发布（Deployment ≠ Release）

一个容易忽视的概念区分：

- **Deployment（部署）**：把代码/二进制送到生产服务器上运行
- **Release（发布）**：把新功能开放给用户使用

**好的架构让这两件事解耦**——你可以先**部署**新代码（对所有用户无感），再通过特性开关/流量控制**发布**给特定用户群。这意味着"部署"是低风险的技术动作，"发布"才是可控的业务动作。

## 🎭 四种核心策略的底层思想

### 滚动更新（Rolling Update）：原地渐进

**思想**：一次替换一部分旧 Pod 为新版本，直到全部替换完。

**本质权衡**：
- ✅ 资源占用小（无需额外一套环境）
- ✅ K8s 默认策略，复杂度低
- ❌ 回滚慢（要再滚一次）
- ❌ 中间状态存在新旧版本共存（需要应用兼容"N 和 N-1 版本同时运行"）

**关键参数**：
- `maxSurge`：可超出期望副本数的 Pod 数（控制资源峰值）
- `maxUnavailable`：可不可用的 Pod 数（控制服务容量下限）

### 蓝绿部署（Blue-Green）：整组切换

**思想**：维护两套**完全独立**的生产环境，新版本部署到"绿"环境验证后，通过**路由器/LB 切换**流量。

**本质权衡**：
- ✅ 回滚瞬间完成（路由改回去即可）
- ✅ 新旧版本完全隔离，无"中间状态"
- ❌ 资源成本 **2 倍**
- ❌ 切换瞬间是 100% 流量，如果新版本有缺陷，爆炸半径最大
- ❌ 数据库 schema 变更等"有状态"变更仍是难题

**适用场景**：变更影响大、需要完整冒烟验证、对回滚速度要求极高的关键业务。

### 金丝雀发布（Canary）：先让"金丝雀"去试毒

名字来源：19 世纪矿工带金丝雀下矿井——鸟对瓦斯敏感，鸟先死，矿工赶紧跑。

**思想**：先把新版本推给一小部分（如 1%、5%）用户/流量，观察指标无异常再逐步放大（10% → 50% → 100%）。

**本质权衡**：
- ✅ 爆炸半径最小（1% 用户受影响）
- ✅ 能真实收集指标数据决定是否推进
- ❌ 需要**精细化流量控制**（Service Mesh、Ingress 权重）
- ❌ 需要强可观测性（否则你无法判断 1% 数据是否有问题）
- ❌ 整体发布周期更长

**金丝雀的灵魂是"自动化判决"**：Flagger、Argo Rollouts 等工具会自动根据指标（错误率、延迟 P99、业务 KPI）决定是进、是退、还是保持。没有自动判决的金丝雀只是"人工盯屏"。

### A/B 测试：面向业务而非技术

与金丝雀"随机挑流量"不同，A/B 测试按**业务维度**划分人群（新用户/老用户、某地区、某渠道），验证**业务效果**（转化率、停留时长）而非**技术正确性**。

常见错误：用 A/B 工具来做技术灰度。A/B 关注"方案 A 和方案 B 哪个收入更高"，灰度关注"新代码会不会崩"。工具可能一样，目的不同。

## 🌊 渐进式交付（Progressive Delivery）：CD 的下一代形态

由 James Governor（RedMonk）在 2018 年提出，是金丝雀发布的"加强版"和系统化：

```
传统部署    →  CI/CD  →  持续部署  →  渐进式交付
人工发布     自动化     全自动      自动化 + 观测 + 决策
```

渐进式交付的四大支柱：
1. **可观测性优先**：没有指标就没有资格渐进
2. **自动化判决**：基于指标的 promote/rollback 决定
3. **特性开关解耦**：部署和发布分离
4. **实验能力**：A/B 测试、影子流量（Shadow Traffic）

代表工具：**Flagger**（Weaveworks）、**Argo Rollouts**（Intuit）、**Spinnaker**（Netflix）。

## 🌿 GitOps：Git 作为唯一真相源

GitOps 由 **Alexis Richardson（Weaveworks 创始人）于 2017 年提出**，本质是**把 K8s 的声明式思想延伸到整个交付流程**。

### GitOps 四大原则（OpenGitOps 规范）

1. **声明式（Declarative）**：系统期望状态必须以声明式方式表达
2. **版本化且不可变（Versioned and Immutable）**：期望状态存在 Git，完整历史、可回滚
3. **自动拉取（Pulled Automatically）**：Agent 自动从 Git 拉取期望状态应用
4. **持续协调（Continuously Reconciled）**：Agent 持续监控实际 vs 期望，自动修正漂移

### Push vs Pull：两种模式的本质差异

传统 CI/CD 是 **Push 模式**：CI 工具（如 GitHub Actions）**主动推送** `kubectl apply` 到集群。
GitOps 是 **Pull 模式**：集群内的 Agent（ArgoCD、Flux）**主动拉取** Git 中的配置。

| 维度 | Push（传统 CD） | Pull（GitOps） |
|------|----------------|---------------|
| **凭证流向** | CI 需要持有集群凭证（泄露风险） | 集群持有 Git 只读凭证 |
| **多集群** | 每个集群一套 CD 流水线 | 一套 Agent 管多集群 |
| **漂移检测** | 需要额外监控 | 原生支持（持续协调） |
| **审计** | 依赖 CI 日志 | Git 历史即审计日志 |

GitOps 的根本优势：**安全边界正确**——生产集群凭证永远不出集群。CI 只管把新的镜像 tag 写进 Git，不接触生产环境。

### GitOps 典型工作流

```
开发者 push code
       │
       ↓
  App Repo (应用代码)
       │
       │ CI 构建镜像并推送 + 更新 Config Repo
       ↓
  Config Repo (K8s 清单)
       │
       │ ArgoCD/Flux 持续拉取
       ↓
  Kubernetes Cluster
       │
       │ 持续 Reconcile
       ↓
   实际运行状态 ← 偏离自动修正
```

两个 Repo 分离是最佳实践：**应用代码**和**部署配置**的变更速率与权限模型不同。

## 🎯 部署策略

### 蓝绿部署

蓝绿部署维护两套完全相同的生产环境（蓝色和绿色），新版本部署到空闲环境，验证通过后切换流量。

```yaml
# Kubernetes 蓝绿部署配置
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app-blue
  labels:
    app: my-app
    version: blue
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
      version: blue
  template:
    metadata:
      labels:
        app: my-app
        version: blue
    spec:
      containers:
      - name: app
        image: my-app:1.0.0
        ports:
        - containerPort: 3000

---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app-green
  labels:
    app: my-app
    version: green
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
      version: green
  template:
    metadata:
      labels:
        app: my-app
        version: green
    spec:
      containers:
      - name: app
        image: my-app:1.1.0
        ports:
        - containerPort: 3000

---
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  selector:
    app: my-app
    version: blue  # 切换到 blue 或 green
  ports:
  - port: 80
    targetPort: 3000
```

**蓝绿部署脚本：**
```bash
#!/bin/bash

# 部署新版本到绿色环境
kubectl apply -f my-app-green.yaml

# 等待绿色环境就绪
kubectl rollout status deployment/my-app-green

# 健康检查
kubectl get pods -l version=green

# 切换流量到绿色环境
kubectl patch service my-app-service -p '{"spec":{"selector":{"version":"green"}}}'

# 验证新版本
sleep 30
curl http://my-app-service/health

# 如果出现问题，回滚到蓝色环境
# kubectl patch service my-app-service -p '{"spec":{"selector":{"version":"blue"}}}'
```

### 金丝雀发布

金丝雀发布将新版本先部署给少量用户，验证通过后逐步扩大范围。

```yaml
# 使用 Istio 进行金丝雀发布
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-app
spec:
  hosts:
  - my-app
  http:
  - match:
    - headers:
        x-canary:
          exact: "true"
    route:
    - destination:
        host: my-app
        subset: v2  # 新版本
      weight: 100
  - route:
    - destination:
        host: my-app
        subset: v1  # 旧版本
      weight: 90
    - destination:
        host: my-app
        subset: v2  # 新版本
      weight: 10  # 10% 流量到新版本

---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: my-app
spec:
  host: my-app
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
```

**渐进式金丝雀发布脚本：**
```bash
#!/bin/bash

# 阶段1：5% 流量

    "op": "replace",

    "value": 5
  },
  {
    "op": "replace",
    "path": "/spec/http/1/route/0/weight",
    "value": 95

echo "等待 5 分钟..."

# 检查错误率

# 阶段2：25% 流量

  {
    "op": "replace",
    "path": "/spec/http/1/route/1/weight",
    "value": 25
  },
  {
    "op": "replace",
    "path": "/spec/http/1/route/0/weight",
    "value": 75
  }
]'

echo "等待 10 分钟..."
sleep 600

# 阶段3：50% 流量
kubectl patch virtualservice my-app --type=json -p='[
  {
    "op": "replace",
    "path": "/spec/http/1/route/1/weight",
    "value": 50
  },
  {
    "op": "replace",
    "path": "/spec/http/1/route/0/weight",
    "value": 50
  }
]'

echo "等待 15 分钟..."

# 阶段4：100% 流量

  {
    "op": "replace",

    "value": 100
  },

    "op": "replace",

  }
]'

echo "金丝雀发布完成"
```

### 滚动更新

滚动更新是 Kubernetes Deployment 的默认更新策略，逐步替换旧版本的 Pod。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2        # 最多可以多创建 2 个 Pod
      maxUnavailable: 0  # 最多可以不可用 0 个 Pod
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: my-app:1.0.0
        ports:
        - containerPort: 3000
        # 健康检查确保新 Pod 就绪后才继续
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5
```

**滚动更新命令：**
```bash
# 更新镜像版本
kubectl set image deployment/my-app app=my-app:1.1.0

# 查看更新状态
kubectl rollout status deployment/my-app

# 查看更新历史
kubectl rollout history deployment/my-app

# 暂停更新
kubectl rollout pause deployment/my-app

# 恢复更新
kubectl rollout resume deployment/my-app

# 回滚到上一版本
kubectl rollout undo deployment/my-app

# 回滚到指定版本
kubectl rollout undo deployment/my-app --to-revision=2
```

## 🔧 GitOps

### GitOps 核心原则

GitOps 是一种使用 Git 作为单一事实来源的持续部署方法：

1. **声明式**：整个系统状态通过代码声明
2. **版本化**：所有变更都通过 Git 提交
3. **自动化**：自动将 Git 状态同步到集群
4. **持续协调**：持续监控并确保期望状态

### ArgoCD 配置

**Application 配置：**
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
spec:
  project: default
  
  source:
    repoURL: https://github.com/myorg/my-app-k8s
    targetRevision: main
    path: manifests/
  
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  
  syncPolicy:
    automated:
      prune: true      # 自动删除不再需要的资源
      selfHeal: true   # 自动修复配置漂移
    syncOptions:
    - CreateNamespace=true
    - PrunePropagationPolicy=foreground
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
```

**AppProject 配置：**
```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: default
  namespace: argocd
spec:
  description: Default project
  
  sourceRepos:
  - https://github.com/myorg/*
  
  destinations:
  - namespace: '*'
    server: https://kubernetes.default.svc
  
  clusterResourceWhitelist:
  - group: ''
    kind: Namespace
  
  orphanedResources:
    warn: false
```

### ArgoCD 工作流

```bash
# 安装 ArgoCD
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# 访问 ArgoCD UI
kubectl port-forward svc/argocd-server -n argocd 8080:443

# 初始密码
argocd admin initial-password -n argocd

# 创建应用
argocd app create my-app \
  --repo https://github.com/myorg/my-app-k8s \
  --path manifests \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace production

# 同步应用
argocd app sync my-app

# 查看应用状态
argocd app get my-app

# 查看应用日志
argocd app logs my-app

# 回滚应用
argocd app rollback my-app
```


## 📝 实际应用示例

### 完整的 GitOps 工作流

**目录结构：**
```
my-app-k8s/
├── apps/
│   ├── base/
│   │   ├── deployment.yaml
│   │   ├── service.yaml
│   │   └── kustomization.yaml
│   ├── overlays/
│   │   ├── development/
│   │   │   ├── kustomization.yaml
│   │   │   └── values.yaml
│   │   └── production/
│   │       ├── kustomization.yaml
│   │       └── values.yaml
└── argocd/
    ├── application.yaml
    └── project.yaml
```

**base/deployment.yaml：**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: my-registry/my-app:$(IMAGE_TAG)
        ports:
        - containerPort: 3000
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 512Mi
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5
```

**base/kustomization.yaml：**
```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: my-app

resources:
  - deployment.yaml
  - service.yaml

images:
  - name: my-registry/my-app
    newName: my-registry/my-app
    newTag: latest
```

**overlays/production/kustomization.yaml：**
```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: production

resources:
  - ../../base

images:
  - name: my-registry/my-app
    newName: my-registry/my-app
    newTag: v1.0.0

replicas:
  - name: my-app
    count: 10

patchesStrategicMerge:
  - values.yaml
```

**argocd/application.yaml：**
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
  finalizers:
  - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  
  source:
    repoURL: https://github.com/myorg/my-app-k8s
    targetRevision: main
    path: apps/overlays/production
  
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
    - CreateNamespace=true
```

**部署流程：**
```bash
# 1. 更新镜像标签
cd apps/overlays/production
sed -i 's/newTag: .*/newTag: v1.1.0/' kustomization.yaml

# 2. 提交并推送
git add .
git commit -m "Update my-app to v1.1.0"
git push origin main

# 3. ArgoCD 自动同步
# 查看同步状态
argocd app get my-app

# 4. 手动触发同步（如果需要）
argocd app sync my-app

# 5. 如果出现问题，回滚
git revert HEAD
git push origin main
argocd app sync my-app
```
