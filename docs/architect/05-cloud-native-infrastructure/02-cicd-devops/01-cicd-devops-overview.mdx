## 🌱 DevOps 的起源与本质

### 历史脉络：从"部门墙"到"共担责任"

DevOps 不是工具，是一场**文化变革**。要理解它，得先理解它解决的痛点。

**前 DevOps 时代（~2008）**，软件行业普遍存在一面"部门墙"：

- **Dev（开发）** KPI：多发版、快迭代、多交付功能
- **Ops（运维）** KPI：少故障、保稳定、拒绝变更

两边目标相互冲突：开发天天想上线，运维天天想不变。结果是：
- 代码在开发机上跑得好，到生产环境就挂
- 出故障时互相甩锅（"代码没问题，是你环境问题" vs "环境没问题，是你代码问题"）
- 上线像做手术，要走复杂审批流程，周期以月计

**2008 年**，Andrew Shafer 在 Agile 2008 大会提出"敏捷基础设施"概念；
**2009 年**，比利时工程师 Patrick Debois 组织了第一届 **DevOpsDays** 大会（根特），"DevOps"一词正式诞生；
**2010 年**，Flickr 工程师 John Allspaw 发表著名演讲《每天部署 10+ 次：Dev 与 Ops 在 Flickr 的协作》，成为 DevOps 运动的里程碑；
**2013 年**，Gene Kim 等人出版《凤凰项目》（小说体），让 DevOps 理念在企业高管中广泛传播。

### DevOps 的核心公式：CALMS

业界公认的 DevOps 五大支柱（CALMS 模型，由 Jez Humble 提出）：

| 字母 | 含义 | 说明 |
|------|------|------|
| **C** | Culture（文化） | 打破部门墙，共同承担交付责任 |
| **A** | Automation（自动化） | 能自动化的绝不手动（构建、测试、部署、监控） |
| **L** | Lean（精益） | 持续减少浪费（等待、返工、库存） |
| **M** | Measurement（度量） | 一切决策基于数据，关键指标被追踪 |
| **S** | Sharing（共享） | 知识、工具、责任在团队间流动 |

**文化是第一位**。只买 Jenkins、搭 ArgoCD，不改变协作模式，只是把低效的流程自动化了一遍，这叫"昂贵的瀑布"，不是 DevOps。

## 📊 DORA 指标：衡量交付能力的黄金标准

Google 的 DevOps 研究团队 **DORA（DevOps Research and Assessment）** 从 2014 年起发布年度《DevOps 状态报告》，总结出**四个能精准预测企业软件交付效能的关键指标**：

| 指标 | 含义 | 精英团队水平 | 低效团队水平 |
|------|------|-------------|-------------|
| **部署频率** (Deployment Frequency) | 生产环境部署次数 | 按需部署（每天多次） | 每月一次以下 |
| **变更前置时间** (Lead Time for Changes) | 代码提交到生产上线的时间 | 少于 1 天 | 1-6 个月 |
| **变更失败率** (Change Failure Rate) | 导致生产故障的变更占比 | 0-15% | 46-60% |
| **恢复时间** (Mean Time to Recovery) | 故障平均恢复时长 | 少于 1 小时 | 1 周以上 |

DORA 研究的颠覆性结论：**速度和稳定性不是对立的，高绩效团队两者都好**。精英团队比低效团队部署频率高 **973 倍**，恢复速度快 **6570 倍**，同时故障率还更低。

这 4 个指标今天仍是 **CTO 问责"DevOps 转型成效"时唯一靠得住的尺子**。

## 🔍 CI / CD / CD：三个名字，四个概念，经常混淆

"CI/CD" 看似一个词，实际是三个逐级递进的概念。真正容易混淆的是两个不同的 "CD"：

```
代码提交 ──→ CI ──→ Continuous Delivery ──→ Continuous Deployment
(持续集成)    (持续交付)                    (持续部署)
```

| 概念 | 英文 | 关键动作 | 终点 | 需要人工吗？ |
|------|------|---------|------|-------------|
| **持续集成** | Continuous Integration | 代码合并、构建、测试 | 通过测试的构建产物 | 不需要 |
| **持续交付** | Continuous Delivery | + 自动部署到类生产环境 | "随时可以上线"的状态 | **上生产需人工按钮** |
| **持续部署** | Continuous Deployment | + 自动部署到生产环境 | 代码自动生效于用户 | 完全自动 |

关键区分点：
- **持续交付 vs 持续部署**：只差"最后一公里"——生产环境是**人工点击**还是**自动触发**
- **业务现实**：大多数企业做到"持续交付"就已经很强了；真正全自动的持续部署，需要极高的测试覆盖率和自动回滚能力作为底气

## 🔄 价值流动：为什么叫"流水线"？

DevOps 强调 **软件的"价值流"（Value Stream）** 视角——一行代码从写下到为用户创造价值，中间经历多少环节？

```
想法 → 设计 → 编码 → 构建 → 测试 → 部署 → 发布 → 运行 → 反馈
  ↑                                                        │
  └──────────────── 反馈循环（Feedback Loop）──────────────┘
```

每个环节都可能出现 **三种浪费**（精益思想）：
1. **等待**：等审批、等环境、等测试
2. **返工**：发现 bug 退回上游重做
3. **交接**：换人、换工具带来的上下文丢失

流水线的目标不是"自动化"本身，而是**压缩价值流动的时间**。这也是为什么衡量 DevOps 成熟度用"变更前置时间"这个指标——它直接反映了从 idea 到 production 的延迟。

## 🔑 核心概念

### 部署策略对比

| 策略 | 停机时间 | 回滚速度 | 资源成本 | 适用场景 |
|------|---------|---------|---------|---------|
| **蓝绿部署** | 无 | 极快 | 2x | 关键业务 |
| **金丝雀发布** | 无 | 快 | 1.x | 需要验证的变更 |
| **滚动更新** | 无 | 中 | 1x | 常规变更 |
| **灰度发布** | 无 | 快 | 1.x | 按用户群验证 |
