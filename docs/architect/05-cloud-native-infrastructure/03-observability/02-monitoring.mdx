# 监控体系

> **版本**：v1.1
> **最后更新**：2026-04-28

## 📚 概念介绍

监控是可观测性的三大支柱之一，通过收集和分析系统指标，帮助我们了解系统的运行状态、发现问题和优化性能。本节将讲解如何构建完整的监控体系。

### 核心概念

- **指标（Metrics）**：数值化的时间序列数据，反映系统的状态
- **PromQL**：Prometheus 查询语言，用于查询和分析指标
- **SLI（Service Level Indicator）**：服务级别指标，衡量服务质量的具体指标
- **SLO（Service Level Objective）**：服务级别目标，SLI 的目标值
- **SLA（Service Level Agreement）**：服务级别协议，与服务提供商达成的协议

### RED 与 USE 方法

**RED 方法**（面向服务）：
- **Rate（请求速率）**：每秒请求数
- **Errors（错误率）**：请求失败的比例
- **Duration（延迟）**：请求处理时间

**USE 方法**（面向资源）：
- **Utilization（利用率）**：资源使用百分比
- **Saturation（饱和度）**：资源负载程度
- **Errors（错误数）**：资源错误数量

## 🧠 为什么是时序数据？指标的本质

### 指标 = 时间序列（Time Series）

监控数据的核心数学模型是**时间序列**：

```
(timestamp, value, labels)
1714291200, 42.3, {method="GET", status="200", path="/api/users"}
1714291215, 43.1, {method="GET", status="200", path="/api/users"}
1714291230, 45.7, {method="GET", status="200", path="/api/users"}
```

一条时间序列 = **一个指标名 + 一组 label 的唯一组合**，随时间产生 (timestamp, value) 的数据点流。

这种数据结构的性质决定了监控系统的所有技术选型：
- **写多读少**：每秒写入海量数据点，查询频率远低于写入
- **追加不修改**：历史数据一旦落盘就不再变
- **局部性强**：最近的数据查得最多（最近 1 小时 >> 30 天前）
- **降采样友好**：旧数据可合并为更低精度（1s → 1min → 1h）

这些特性催生了专门的 **TSDB（时序数据库）**——用通用关系数据库存指标是大坑。

## 🏛️ Prometheus 的设计哲学

Prometheus 源自 **SoundCloud（2012 年）**，受 Google 内部 Borgmon 启发，**2016 年成为 CNCF 第二个毕业项目**（仅次于 K8s）。它有几个反直觉但极为关键的设计决策：

### 决策一：Pull 模型（拉取），不是 Push（推送）

传统监控（StatsD、Graphite、InfluxDB 早期）是 Push：应用主动把指标推送到监控系统。
Prometheus 反其道而行——**监控系统主动去目标 `/metrics` 端点拉取**。

| 维度 | Push 模型 | Pull 模型 |
|------|----------|----------|
| **目标发现** | 需要每个目标知道监控地址 | 监控服务器维护目标列表 |
| **负载控制** | 应用可能压垮监控系统 | 监控决定抓取频率，背压天然 |
| **健康检查** | 推不来可能是挂了也可能是网络问题 | 拉不到直接认定目标不健康 |
| **调试便利** | 只能看接收到的 | 手动 `curl /metrics` 即可 |
| **批作业适配** | 适合 | **不适合**（作业快速结束，没机会被拉取） |

Prometheus 的取舍：**牺牲短生命周期任务的支持，换取简单可靠**。短任务用 **Pushgateway** 作为中间 buffer，prom 再从 Pushgateway 拉。

### 决策二：多维数据模型（Label-Based）

传统监控（Graphite）用**层级命名**：`web.server1.http.request.200.count`。
Prometheus 用**多维 label**：`http_requests_total{server="web1", status="200"}`。

多维模型的优势：**查询时可任意切片**——按 status 聚合、按 server 筛选、按 path 分组，都是一个 PromQL 搞定。层级命名只能按固定顺序钻取，扩展就要改名字。

### 决策三：本地存储 + 单机架构

Prometheus 每个实例**独立运行、本地存储、不共享**。这看起来落后，实际：
- **部署简单**：一个二进制文件，无外部依赖
- **查询快**：本地 SSD >> 网络存储
- **故障隔离**：一个 Prom 挂了不影响其他

扩展性怎么办？**分片 + 联邦 + 远程存储**。Thanos、Cortex、VictoriaMetrics、Mimir 在 Prom 之上构建了长时间、跨集群的分布式层。

## 🔢 四类指标类型：分清用哪个

Prometheus 定义了 4 种指标类型，**选错会导致数据永远错**。

### Counter（计数器）：只增不减

代表一个**累计值**，只会增加（重启归零）。例子：
- `http_requests_total`：总请求数
- `node_cpu_seconds_total`：CPU 占用总秒数

**永远不要直接看 Counter 的值**——它只是一个永远上涨的大数。用 `rate()` 或 `increase()` 看变化率：

```
rate(http_requests_total[5m])  # 5分钟内平均每秒请求数
```

### Gauge（仪表）：可升可降

代表一个**瞬时值**，可以任意变化。例子：
- `node_memory_used_bytes`：当前内存用量
- `queue_length`：当前队列深度

直接看值就行，或 `avg_over_time`、`max_over_time` 做聚合。

### Histogram（直方图）：分桶统计分布

用于统计**数据分布**（延迟、包大小）。Prometheus 的 Histogram 存储方式是**预定义桶（bucket）**：

```
http_request_duration_seconds_bucket{le="0.1"}   3400   # ≤ 100ms 的请求数
http_request_duration_seconds_bucket{le="0.5"}   4200   # ≤ 500ms 的请求数
http_request_duration_seconds_bucket{le="1"}     4500   # ≤ 1s 的请求数
http_request_duration_seconds_bucket{le="+Inf"}  4530   # 所有请求数
http_request_duration_seconds_sum                1245.3 # 总耗时
http_request_duration_seconds_count              4530   # 总次数
```

客户端只需**累加桶计数**（很便宜），分位数在查询时由 `histogram_quantile()` 算。

### Summary（摘要）：客户端算分位数

和 Histogram 类似，但**分位数在客户端计算**后直接暴露。适合确切需要某几个分位数的场景。

### Histogram vs Summary 的核心差异

| 维度 | Histogram | Summary |
|------|-----------|---------|
| **分位数计算** | 查询时（灵活） | 客户端（固定） |
| **服务端聚合** | ✅ 可以（跨实例合并桶） | ❌ 不能（分位数不可加） |
| **客户端成本** | 低（只增桶） | 高（滑动窗口算法） |
| **桶精度权衡** | 桶设置错了估算不准 | 精度固定 |

**90% 的场景选 Histogram**，Summary 只在"跨节点聚合不重要 + 客户端便宜"时用。

## 🧮 PromQL：指标的"代数系统"

PromQL 不是 SQL，它是一套**向量代数**：每次查询返回的要么是 **Instant Vector**（某一时刻各序列的值）要么是 **Range Vector**（一段时间内的值序列），要么是标量/字符串。

```
instant vector:  http_requests_total
range vector:    http_requests_total[5m]
scalar:          2.718281828
```

理解这一点就理解了所有"奇怪"操作：
- `rate(...[5m])`：Range Vector → Instant Vector（算变化率）
- `sum(...) by (job)`：Instant Vector → Instant Vector（分组聚合）
- `instant_a / instant_b`：按相同 label 集做匹配相除

这套代数的威力在于**组合任意查询而无需预建仪表盘**——这也是 Prometheus 能胜出的关键：它提供了"数据原语 + 语言"，而不只是"预定义面板"。

### 常见陷阱

- **`rate(counter[5m])` 范围要 ≥ scrape_interval × 4**，否则容易采到 0
- **Counter 重启归零**：PromQL 的 `rate()` 内部处理了重启检测，不用担心
- **高基数 label 爆炸**：给 `user_id` 加 label，几秒就撑爆 Prom。Label 只用低基数字段

## 🗄️ TSDB 存储原理：为什么它写得这么快

Prometheus 的本地存储引擎自研（2017 年 v2.0 从 LevelDB 迁走），核心是**块存储 + 倒排索引 + 压缩**：

1. **内存 Block（WAL）**：最新 2 小时的数据写内存，同时 WAL 落盘防丢失
2. **持久化 Block**：每 2 小时把内存块刷成磁盘 Block（目录结构）
3. **倒排索引**：每个 label 值 → 匹配的序列 ID 列表（类似搜索引擎）
4. **双 Delta 编码 + Gorilla 压缩**：相邻两点的差的差 + 位压缩，压缩比可达 1.37 bytes/sample（Facebook Gorilla 论文 2015）

这套架构的性能数据：**单机每秒数百万样本**，同时磁盘占用极小。这就是为什么"每个 Prom 只管自己的数据"是可行的。

## 🚨 告警的哲学：少就是多

### 关于告警，SRE 界最重要的两条原则

**原则一：告警要指向"有人必须立即处理"**

如果一条告警响了但没人行动，它就不该存在。典型反模式：
- CPU > 80% 就告警（然后呢？谁去降 CPU？是自己能恢复还是真要介入？）
- 每天一堆告警没人看，真故障时信号被淹没 = **Alert Fatigue（告警疲劳）**

**原则二：告警面向症状（Symptom），不面向原因（Cause）**

坏例子：**数据库连接池用了 90%** → 告警
好例子：**API P99 延迟 > 1s 持续 5 分钟** → 告警

前者可能只是背景噪音，后者真正代表用户受影响。具体原因留给故障排查时查，告警只告用户可感知的"坏"。

### 多窗口多燃烧率告警（Multi-Window Multi-Burn-Rate）

Google SRE 工作手册推荐的高级告警模式。对同一个 SLO 同时监控：

- **短窗口（5m）+ 高燃烧率**：早期发现故障（快）
- **长窗口（1h）+ 低燃烧率**：防止假阳性（稳）

两个条件都满足才告警。这种模式比"单纯的错误率 > 5%"精准得多，几乎无误报。

### 告警分级

| 级别 | 处理时限 | 处理方式 | 例子 |
|------|---------|---------|------|
| **P0 Page** | 立即（\<5min） | 打电话叫醒人 | 核心服务 5xx 大面积 |
| **P1 Ticket** | 小时级 | 发工单 | 某节点故障，已自愈但需复盘 |
| **P2 Log** | 次日 | 记录不打扰 | 某个慢请求 |

**"半夜把人叫醒"是极度昂贵的动作**，只留给真正紧急的事。

### 应用指标暴露

**Node.js 应用示例：**
```javascript
const express = require('express');
const promClient = require('prom-client');

const app = express();
const register = new promClient.Registry();

// 添加默认指标（CPU、内存等）
promClient.collectDefaultMetrics({ register });

// 自定义指标
const httpRequestDuration = new promClient.Histogram({
  name: 'http_request_duration_seconds',
  help: 'Duration of HTTP requests in seconds',
  labelNames: ['method', 'route', 'status_code'],
  buckets: [0.1, 0.5, 1, 2, 5]
});

const httpRequestsTotal = new promClient.Counter({
  name: 'http_requests_total',
  help: 'Total number of HTTP requests',
  labelNames: ['method', 'route', 'status_code']
});

const activeConnections = new promClient.Gauge({
  name: 'active_connections',
  help: 'Number of active connections'
});

// 注册指标
register.registerMetric(httpRequestDuration);
register.registerMetric(httpRequestsTotal);
register.registerMetric(activeConnections);

// 中间件
app.use((req, res, next) => {
  const start = Date.now();
  activeConnections.inc();
  
  res.on('finish', () => {
    const duration = (Date.now() - start) / 1000;
    const route = req.route ? req.route.path : req.path;
    
    httpRequestDuration
      .labels(req.method, route, res.statusCode)
      .observe(duration);
    
    httpRequestsTotal
      .labels(req.method, route, res.statusCode)
      .inc();
    
    activeConnections.dec();
  });
  
  next();
});

// 指标端点
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', register.contentType);
  res.end(await register.metrics());
});

// 健康检查
app.get('/health', (req, res) => {
  res.json({ status: 'healthy' });
});

app.listen(3000, () => {
  console.log('Server running on port 3000');
});
```

## 📊 PromQL 查询

### 基础查询

```text
# 查询所有指标
http_requests_total

# 查询特定标签的指标
http_requests_total{job="my-app", method="GET"}

# 正则匹配标签
http_requests_total{method=~"GET|POST"}

# 范围查询（最近5分钟）
http_requests_total[5m]

# 速率（每秒请求数）
rate(http_requests_total[5m])

# 增长量（总请求数）
increase(http_requests_total[5m])

# 百分位数
histogram_quantile(0.95, http_request_duration_seconds_bucket)
```

### 高级查询

```text
# 计算 P95 延迟
histogram_quantile(0.95, 
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le, job)
)

# 计算错误率
sum(rate(http_requests_total{status_code=~"5.."}[5m])) by (job)
/
sum(rate(http_requests_total[5m])) by (job)
* 100

# 计算可用性
1 - 
sum(rate(http_requests_total{status_code=~"5.."}[5m])) by (job)
/
sum(rate(http_requests_total[5m])) by (job)

# 计算平均延迟
rate(http_request_duration_seconds_sum[5m])
/
rate(http_request_duration_seconds_count[5m])

# 计算资源使用率
(node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100

# 预测磁盘空间使用
predict_linear(node_filesystem_avail_bytes[1h], 4*3600) < 0
```

## 🚨 告警规则

### 告警规则配置

**alerts/app.yml：**
```yaml
groups:
- name: app_alerts
  interval: 30s
  rules:
  # 高错误率告警
  - alert: HighErrorRate
    expr: |
      sum(rate(http_requests_total{status_code=~"5.."}[5m])) by (job)
      /
      sum(rate(http_requests_total[5m])) by (job)
      > 0.05
    for: 5m
    labels:
      severity: warning
      team: backend
    annotations:
      summary: "High error rate detected"
      description: "Job {{ $labels.job }} has error rate > 5% for 5 minutes"

  # 服务不可用告警
  - alert: ServiceDown
    expr: up{job="my-app"} == 0
    for: 1m
    labels:
      severity: critical
      team: backend
    annotations:
      summary: "Service is down"
      description: "Job {{ $labels.job }} has been down for more than 1 minute"

  # 高延迟告警
  - alert: HighLatency
    expr: |
      histogram_quantile(0.95, 
        sum(rate(http_request_duration_seconds_bucket[5m])) by (le, job)
      ) > 1
    for: 5m
    labels:
      severity: warning
      team: backend
    annotations:
      summary: "High latency detected"
      description: "Job {{ $labels.job }} has P95 latency > 1s for 5 minutes"

  # 资源使用率告警
  - alert: HighCPUUsage
    expr: |
      100 - (avg by(instance) (irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
    for: 10m
    labels:
      severity: warning
      team: ops
    annotations:
      summary: "High CPU usage"
      description: "Instance {{ $labels.instance }} has CPU usage > 80% for 10 minutes"

  # 磁盘空间告警
  - alert: DiskSpaceLow
    expr: |
      (node_filesystem_avail_bytes / node_filesystem_size_bytes) * 100 < 10
    for: 5m
    labels:
      severity: warning
      team: ops
    annotations:
      summary: "Disk space low"
      description: "Instance {{ $labels.instance }} has < 10% disk space available"

- name: kubernetes_alerts
  interval: 30s
  rules:
  # Pod 崩溃告警
  - alert: PodCrashLooping
    expr: |
      rate(kube_pod_container_status_restarts_total[1h]) > 0
    for: 5m
    labels:
      severity: warning
      team: k8s
    annotations:
      summary: "Pod is crash looping"
      description: "Pod {{ $labels.pod }} in namespace {{ $labels.namespace }} is crash looping"

  # Pod 未就绪告警
  - alert: PodNotReady
    expr: |
      kube_pod_status_ready{condition="false"} == 1
    for: 10m
    labels:
      severity: warning
      team: k8s
    annotations:
      summary: "Pod not ready"
      description: "Pod {{ $labels.pod }} in namespace {{ $labels.namespace }} is not ready"
```

## 📝 SLI/SLO 管理

### SLI 定义

```yaml
# sli/slos.yml
service: my-app
description: "My Application Service"

slos:
  # 可用性 SLO
  - name: availability
    description: "Service availability"
    target: 0.999
    window: 30d
    sli:
      name: request_success_rate
      query: |
        sum(rate(http_requests_total{status_code!~"5.."}[5m]))
        /
        sum(rate(http_requests_total[5m]))

  # 延迟 SLO
  - name: latency
    description: "Request latency"
    target: 0.95
    window: 30d
    sli:
      name: request_latency_p95
      query: |
        histogram_quantile(0.95,
          sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
        )

  # 错误率 SLO
  - name: error_rate
    description: "Error rate"
    target: 0.01
    window: 30d
    sli:
      name: request_error_rate
      query: |
        sum(rate(http_requests_total{status_code=~"5.."}[5m]))
        /
        sum(rate(http_requests_total[5m]))
```

### SLO 监控

```text
# 计算 SLO 合规率
# 可用性
avg_over_time(
  sum(rate(http_requests_total{status_code!~"5.."}[5m]))
  /
  sum(rate(http_requests_total[5m]))
  [30d:1d]
)

# 延迟
avg_over_time(
  1 - histogram_quantile(0.95,
    sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
  )
  [30d:1d]
)

# 错误率
avg_over_time(
  1 - (
    sum(rate(http_requests_total{status_code=~"5.."}[5m]))
    /
    sum(rate(http_requests_total[5m]))
  )
  [30d:1d]
)
```
