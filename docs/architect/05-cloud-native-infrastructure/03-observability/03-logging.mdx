# 日志管理

> **版本**：v1.1
> **最后更新**：2026-04-28

## 📚 概念介绍

日志是可观测性的三大支柱之一，记录了系统运行过程中发生的事件。本节将讲解如何构建企业级日志管理方案，实现日志的收集、存储、分析和可视化。

### 核心概念

- **结构化日志**：使用 JSON 等格式，便于机器解析和分析
- **日志级别**：DEBUG、INFO、WARN、ERROR、FATAL
- **日志聚合**：将分散的日志集中收集到统一的存储系统
- **日志分析**：通过搜索、过滤、聚合等操作提取有价值的信息

### ELK Stack 架构

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   Beats     │───→│  Logstash   │───→│ Elasticsearch│
│  (日志采集)  │    │  (日志处理)  │    │   (日志存储)  │
└─────────────┘    └─────────────┘    └──────┬──────┘
                                              ↓
                                      ┌─────────────┐
                                      │   Kibana    │
                                      │  (日志可视化) │
                                      └─────────────┘
```

## 🧠 日志的本质：不可变事件流

### 日志 ≠ 打印字符串

业余开发者眼里：日志就是 `console.log` / `printf`，方便调试。
生产系统眼里：**日志是系统最权威的"事件记录"，是事后还原现场的唯一依据**。

这种认知升级带来的后果：
- 日志必须**结构化**（否则无法高效查询）
- 日志必须**持久化**（不丢失，哪怕应用崩了）
- 日志必须**可关联**（多服务的日志能串联起来）
- 日志必须**有分级**（海量数据里得快速找到"重要的"）

### Twelve-Factor App 的日志哲学

Heroku 在 2011 年提出的 **12-Factor App 方法论**，第 11 条专门讲日志：

> **Treat logs as event streams**
> 应用**不应关心日志的存储和路由**，只需把日志作为事件流**写到 stdout**。
> 日志的收集、聚合、存储、查询**完全交给基础设施层**。

这个原则在容器时代至关重要：
- 容器内写文件是反模式（容器销毁日志就没了）
- 应用日志 → stdout → 容器运行时 → 日志驱动（Fluent Bit/Filebeat）→ 后端
- 应用**不感知**日志最终去哪（Elasticsearch？Loki？S3？）

## 📝 日志级别的语义约定

日志级别不是越多越好，而是**团队对"何时该在哪个级别打"的纪律**。业界通用定义（RFC 5424 syslog 级别的简化）：

| 级别 | 语义 | 应用场景 | 是否告警 |
|------|------|---------|---------|
| **TRACE** | 极细粒度执行路径 | 调试复杂逻辑，正式环境通常关闭 | 否 |
| **DEBUG** | 调试信息 | 开发/排障，生产可按需开启 | 否 |
| **INFO** | 正常业务流程的关键节点 | "用户 X 下单 Y"、"启动成功" | 否 |
| **WARN** | **非预期但可恢复**的情况 | "重试第 3 次终于成功"、"降级到备用服务" | 选择性 |
| **ERROR** | **操作失败**，但服务仍可继续 | "创建订单失败"、"调用 A 返回 500" | 视频率 |
| **FATAL** | **服务无法继续**运行 | "无法连接主数据库，进程将退出" | 立即告警 |

### 常见误用

- ❌ **所有东西都打 INFO**：日志量爆炸，真正重要的信息被淹没
- ❌ **catch 里打 ERROR 但业务是正常的**：例如用户登录失败属正常业务，不该 ERROR
- ❌ **循环里打日志**：一个 bug 让一秒打出 1GB 日志，直接把磁盘打满
- ✅ **原则**：**日志级别应该让"收到告警的工程师"判断严重性是对的**

## 🔤 结构化日志：从文本到数据

### 非结构化 vs 结构化

非结构化（传统）：
```
2026-04-28 10:23:45 INFO User admin logged in from 192.168.1.1, took 45ms
```

结构化（JSON）：
```js
{
  "timestamp": "2026-04-28T10:23:45Z",
  "level": "info",
  "message": "User logged in",
  "user_id": "admin",
  "source_ip": "192.168.1.1",
  "duration_ms": 45,
  "service": "auth-service",
  "trace_id": "abc-123"
}
```

### 结构化带来的质变

| 需求 | 非结构化 | 结构化 |
|-----|---------|-------|
| "统计 admin 用户登录次数" | grep + awk，脆弱 | 一条查询 `user_id:admin` |
| "按 source_ip 聚合" | 正则解析每行 | 原生聚合 |
| "找所有耗时 >100ms 的" | 无法直接做 | `duration_ms:>100` |
| **数据可被其他系统消费** | 需重新解析 | 直接用 |

**结构化日志是现代日志平台的前提**。ELK、Loki、Datadog 都要求或强烈建议 JSON 格式。

### 关键字段：必须包含的"元数据"

任何生产日志至少应包含：
- `timestamp`：ISO 8601 格式，带时区
- `level`：大小写统一
- `service`：哪个服务/应用
- `instance` / `hostname`：哪个实例
- `trace_id` / `request_id`：分布式追踪串联
- `message`：人类可读描述

## 🔗 MDC 与上下文传递：让一次请求的所有日志能串起来

单次请求穿过 N 个方法 / M 个服务，如何让相关日志"贴在一起"？

### MDC（Mapped Diagnostic Context）模式

在请求入口处把 `request_id`、`user_id`、`trace_id` 放进线程/上下文局部存储，之后**所有日志自动带上这些字段**，不用每次手动传参。

实现机制：
- Java：Log4j/SLF4J 的 MDC（基于 ThreadLocal）
- Node.js：AsyncLocalStorage（Node 12+）
- Go：context.Context 传递
- 跨服务：通过 HTTP header 或消息 header 透传（W3C Trace Context 标准）

**一个好的日志系统，你只要知道 `trace_id`，就能把一个请求在 20 个微服务里打的 200 条日志按时间顺序排成一列。**

## 📦 日志采集架构：三种主流模式

### 模式一：Daemon Set 模式（主流）

每个节点一个采集 Agent（Fluent Bit、Filebeat），**从节点上的容器日志文件读取**：

```
Pod A ─┐
Pod B ─┼──→ 节点日志目录 ──→ Fluent Bit (DaemonSet) ──→ 后端
Pod C ─┘
```

优点：应用零侵入、节点级配置、资源可控
缺点：依赖容器运行时的日志驱动

### 模式二：Sidecar 模式

每个 Pod 额外起一个日志采集容器，**通过共享 volume 读取应用日志**：

```
Pod {
  Application Container ──→ shared volume ──→ Log Sidecar ──→ 后端
}
```

优点：应用级配置灵活（不同应用可不同规则）
缺点：资源成本翻倍，管理复杂

### 模式三：直接上报（Library-Based）

应用代码里集成 SDK，**直接推日志到后端**（如 Sentry）：

优点：低延迟、富上下文
缺点：应用耦合 SDK，后端故障时可能影响应用

### 选型建议

| 场景 | 推荐 |
|------|-----|
| 通用微服务 | **DaemonSet（最优）** |
| 需要日志分级采集规则 | Sidecar |
| 错误监控、APM | 直接上报 + SDK |

## 🌊 流水线架构：采集 → 传输 → 处理 → 存储

生产级日志平台都是多阶段流水线：

```
[采集]     [缓冲]         [处理]        [存储]        [查询]
 Beats  →  Kafka    →   Logstash   →   ES/Loki   →   Kibana
          (削峰填谷)    (解析/富化)
```

### 为什么要引入 Kafka（或其他 MQ）

直接 Beats → Logstash → ES 会有问题：
- ES 抖动 / 慢 → Logstash 堵塞 → Beats 内存爆
- 要重启 Logstash → 日志丢失风险
- 不同时效性的日志混在一起

Kafka 作为**缓冲层**解决：
- **削峰填谷**：流量洪峰被 Kafka 吸收
- **多消费者**：同一份日志可以喂给 ES（搜索）、S3（归档）、告警引擎（实时分析）
- **解耦升级**：重启 Logstash 不影响采集

### 处理阶段的关键任务

- **解析（Parse）**：把非结构化文本转结构化（Grok 模式、正则）
- **富化（Enrich）**：补充 GeoIP、用户信息、服务 metadata
- **脱敏（Mask）**：移除 PII（手机号、身份证、Token）
- **路由（Route）**：根据内容发到不同的后端

## 🎚️ 采样与聚合：应对海量数据

日志成本和规模是生产系统永远的痛。一个中等规模服务每天可能产生 **TB 级日志**。

### 采样（Sampling）

对**高频、低价值**的日志抽样：
- **随机采样**：每 100 条留 1 条
- **速率限制**：每秒最多 10 条该类日志
- **动态采样**：正常时低采样率，异常时 100% 保留

### 聚合（Aggregation）

在采集端就把重复日志**压缩**：
- "1000 次相同的 DEBUG 日志" → "此类日志 1000 次，最新一条如下..."
- 适合**循环内的噪音日志**

### 冷热分层（Tiered Storage）

- **热数据**（近 7 天）：Elasticsearch SSD，快速查询
- **温数据**（7-30 天）：较便宜磁盘
- **冷数据**（30 天+）：S3/OSS 对象存储，按需下载

这种分层让日志成本降低 **5-10 倍**，同时满足合规保留要求。

## 🆚 ELK vs Loki：两种设计哲学

近年来 Grafana Loki 作为"轻量替代"崛起。二者设计哲学完全不同：

| 维度 | Elasticsearch | Loki |
|------|---------------|------|
| **索引策略** | **全文索引**（每个词建索引） | **只索引 label**（日志内容不索引） |
| **存储成本** | 高（索引 ≈ 原始数据） | 极低（原始压缩，无额外索引） |
| **查询性能** | 任意全文搜索很快 | 按 label 过滤快，全文扫描慢 |
| **适合场景** | 复杂查询、大而全 | 大规模、成本敏感、按标签查询为主 |
| **运维复杂度** | 高（JVM、分片、磁盘调优） | 低（几乎零运维） |

选型思路：**需要灵活全文搜索选 ES，需要海量低成本存储选 Loki**。

## 🔐 日志安全与合规

生产日志常是 **"数据泄露的头号源头"**：
- 打印了完整的 HTTP 请求（含密码字段）
- 错误堆栈泄露了数据库连接串
- 用户手机号、身份证出现在订单日志里

必须做的事：
- **脱敏（Redaction）**：采集端过滤敏感字段
- **访问控制**：Kibana/Grafana 做 RBAC，客服不能看到所有日志
- **审计日志单独存储**：合规要求（等保、GDPR）
- **保留期管理**：GDPR 要求用户注销后数据可删除

### 日志级别规范

```javascript
// 日志级别使用规范
const LogLevel = {
  DEBUG: 'debug',    // 调试信息，仅在开发环境使用
  INFO: 'info',      // 一般信息，记录正常的业务流程
  WARN: 'warn',      // 警告信息，不影响业务但需要关注
  ERROR: 'error',    // 错误信息，影响业务但可以恢复
  FATAL: 'fatal'     // 致命错误，导致服务不可用
};

// 日志记录最佳实践
function processPayment(paymentData) {
  logger.info('Payment processing started', {
    paymentId: paymentData.id,
    amount: paymentData.amount,
    currency: paymentData.currency
  });

  try {
    // 业务逻辑
    const result = await paymentService.process(paymentData);
    
    logger.info('Payment processed successfully', {
      paymentId: paymentData.id,
      transactionId: result.transactionId,
      duration: result.duration
    });
    
    return result;
  } catch (error) {
    logger.error('Payment processing failed', {
      paymentId: paymentData.id,
      error: error.message,
      code: error.code,
      stack: error.stack,
      retryable: error.retryable
    });
    
    throw error;
  }
}
```

### Logstash 配置

**logstash.conf：**
```conf
input {
  # 从 Beats 接收日志
  beats {
    port => 5044
  }
  
  # 从文件读取日志
  file {
    path => "/var/log/*.log"
    start_position => "beginning"
    sincedb_path => "/dev/null"
  }
}

filter {
  # 解析 JSON 日志
  if [message] =~ /^\{.*\}$/ {
    json {
      source => "message"
    }
  }
  
  # 添加时间戳
  date {
    match => ["timestamp", "ISO8601"]
    target => "@timestamp"
  }
  
  # 添加主机信息
  mutate {
    add_field => {
      "[host][name]" => "${HOSTNAME}"
      "[host][ip]" => "${HOST_IP}"
    }
  }
  
  # 根据日志级别添加标签
  if [level] == "error" or [level] == "fatal" {
    mutate {
      add_tag => ["error"]
    }
  }
  
  # 移除不需要的字段
  mutate {
    remove_field => ["message"]
  }
  
  # 用户代理解析
  if [userAgent] {
    useragent {
      source => "userAgent"
      target => "ua"
    }
  }
  
  # IP 地址地理位置解析
  if [ip] {
    geoip {
      source => "ip"
      target => "geo"
    }
  }
}

output {
  # 输出到 Elasticsearch
  elasticsearch {
    hosts => ["elasticsearch:9200"]
    index => "logs-%{+YYYY.MM.dd}"
    user => "elastic"
    password => "${ES_PASSWORD}"
  }
  
  # 输出到标准输出（调试用）
  stdout {
    codec => rubydebug
  }
}
```
