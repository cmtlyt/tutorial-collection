# 分布式追踪

> **版本**：v1.1
> **最后更新**：2026-04-28

## 📚 概念介绍

分布式追踪是可观测性的三大支柱之一，它通过跟踪请求在分布式系统中的流转路径，帮助我们理解系统行为、定位性能瓶颈和排查故障。本节将讲解分布式追踪的核心概念和实现方法。

### 核心概念

- **Trace（追踪）**：一个请求在分布式系统中的完整执行路径
- **Span（跨度）**：追踪中的一个基本工作单元，表示系统中的一个操作
- **Span Context（跨度上下文）**：在服务间传递的追踪信息，包含 Trace ID 和 Span ID
- **Baggage（行李）**：在服务间传递的键值对数据
- **OpenTelemetry**：云原生的可观测性框架，提供统一的 API 和 SDK

## 🧠 为什么需要分布式追踪？

### 微服务时代的"调试黑洞"

单体应用里，调用栈就是一切——抛异常时的 stacktrace 告诉你每一层函数在哪、为什么慢。

但到了微服务时代：

```
用户请求 → API Gateway → Auth Service → Order Service → Payment Service → Inventory Service → DB
                                              │
                                              └→ Notification Service → Email Service
```

一个请求可能穿越 **10+ 个服务**，每个服务独立进程、独立日志、独立监控。当用户抱怨"付款慢"时：
- 是哪个服务慢？
- 是服务内部慢，还是调用下游慢？
- 是这一个请求慢，还是所有请求都慢？
- 慢在具体哪一段代码/SQL/外部调用？

**光看单服务的 metrics 和 logs 无法回答**——你需要"串起来"看整条链路。这就是分布式追踪要解决的问题。

## 📜 起源：Google Dapper 论文（2010）

现代分布式追踪的所有实现，都是 Google **Dapper 论文**（2010 年发布，但系统 2004 年就在 Google 内部上线）的"学徒"：
- **Zipkin**（Twitter，2012）：第一个开源追踪系统，直接对标 Dapper
- **Jaeger**（Uber，2015）：CNCF 毕业项目，Dapper + Zipkin 的工程优化
- **SkyWalking**（华为/Apache，2015）：国人主导，APM 方向扩展
- **OpenTracing → OpenTelemetry**（2016→2019）：统一标准

Dapper 论文奠定了三个**核心抽象**，至今未变：

1. **Trace**：一次请求的完整因果链
2. **Span**：链路中的一个工作单元（一次函数调用、一次 RPC、一次 SQL）
3. **Context Propagation**：跨进程传递标识的机制

理解这三个抽象就理解了所有追踪系统。

## 🏛️ Span 模型：追踪的"原子"

### Span 的数据结构

一个 Span 记录：

```
Span {
  trace_id:       "abc123..."        ← 整条链路的唯一 ID
  span_id:        "def456..."        ← 本 span 的唯一 ID
  parent_span_id: "ghi789..."        ← 父 span（构造树形关系）
  operation_name: "GET /api/orders"  ← 人类可读的名字
  start_time:     1714291200.123
  end_time:       1714291200.246
  attributes:     { http.status_code: 200, user_id: "42" }
  events:         [ { timestamp, name, attributes } ]  ← 时间点标注
  status:         OK | ERROR
}
```

### Trace 是 Span 的树/DAG

多个 Span 通过 `parent_span_id` 关系，构成一棵以"根 Span（根请求）"为根的树：

```
Trace (trace_id = abc123)
│
└─ Span: GET /api/checkout      (100ms, 根 span)
   ├─ Span: auth-service.verify (10ms)
   ├─ Span: order-service.create (80ms)
   │  ├─ Span: db.insert_order  (20ms)
   │  └─ Span: payment.charge   (55ms)
   │     └─ Span: stripe.call   (50ms)
   └─ Span: notify.send_email   (5ms, 异步)
```

这棵树揭示了一切：
- **总耗时**：100ms
- **瓶颈**：`stripe.call` 占 50ms（外部调用是主要耗时）
- **并行机会**：notify 是异步的，可以和 db 并行
- **错误定位**：如果某个 span status=ERROR，一眼看出故障环节

### Span 的几种类型（SpanKind）

OpenTelemetry 规范定义了 5 种 SpanKind：

| 类型 | 含义 | 例子 |
|------|------|------|
| **SERVER** | 接收请求的服务端 | HTTP server 收到请求 |
| **CLIENT** | 发起外部调用 | HTTP client、RPC client |
| **PRODUCER** | 发消息到队列 | Kafka producer.send |
| **CONSUMER** | 从队列消费消息 | Kafka consumer.poll |
| **INTERNAL** | 服务内部操作 | 一个函数调用 |

## 🔄 上下文传播（Context Propagation）：最核心的技术挑战

### 问题的本质

Service A 调用 Service B，B 要知道"这次请求的 trace_id 是什么"，才能生成关联的 Span。

但 A 和 B 是不同进程，甚至不同机器——**trace_id 怎么过去的？**

答案：**通过协议 header 携带**。

### W3C Trace Context：终于统一的标准

早期每家系统有自己的 header 格式（Zipkin `X-B3-*`、Jaeger `uber-trace-id`），**跨厂商完全不通**。

**2020 年 2 月**，W3C 发布 **Trace Context 规范（W3C TR/trace-context）**，成为**正式 Web 标准**。核心是两个 HTTP header：

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │    │                                │                │
          version trace-id (16 字节)          parent-id (8 字节)  flags

tracestate: vendor1=value1,vendor2=value2     ← 厂商自定义附加信息
```

今天的所有主流追踪系统、Service Mesh、API Gateway **默认支持 W3C Trace Context**，分布式追踪的互操作性终于解决。

### Baggage：跨服务传递业务上下文

除了 trace_id，有时还需要**在链路上带业务数据**（比如"当前用户是 VIP"，后端日志都标上），这就是 **Baggage**。

它也通过 HTTP header 传递（W3C 定义了 `baggage` header），但要**谨慎使用**：
- Baggage 内容会出现在所有下游日志，泄露风险
- Baggage 会增加每个请求的网络开销
- 基数过高会让后端存储爆炸

## 🎚️ 采样（Sampling）：成本与价值的艺术

### 为什么必须采样

假设每个请求产生 50 个 Span，一个日 QPS 10 亿的系统：
- 500 亿个 Span/天
- 每个 Span 约 500 字节 = **25 TB/天**

**全采集既不经济也没必要**——99% 的请求都是正常的，看不出啥。采样策略决定了**留下哪些 trace**。

### 头部采样（Head-Based Sampling）

在**请求刚进入时**就决定"要不要采"。

```
请求到达 → 掷色子（1% 概率）→ 决定采 → 整条链路所有 Span 都采
                              → 决定不采 → 所有 Span 都不生成
```

优点：简单、成本可控、下游不用传 Span
缺点：**运气问题**——真正的异常请求可能刚好没被采到

### 尾部采样（Tail-Based Sampling）

等**整条链路完成**再决定采不采。

```
所有 Span 先缓存 → 链路完成 →  看整条情况
                              ├─ 有错误？ 100% 采
                              ├─ 慢请求？ 100% 采
                              └─ 正常且快？ 随机留 1%
```

优点：**真正有价值的 trace 不丢**（所有错误和慢请求都保留）
缺点：实现复杂，需要缓冲整条链路的数据

### 自适应采样（Adaptive Sampling）

根据流量和错误率**动态调整采样率**：
- 流量小时 100% 采
- 流量大时降到 0.1%
- 错误率升高时提高采样率

Jaeger、Tempo、Datadog 等现代系统都支持这种模式。

### 采样的哲学

> **采样不是"为了省钱不得已的妥协"，而是"把有限预算花在最有信息量的请求上"。**

头部采样适合"我想看大盘分布"；尾部采样适合"我想找问题根因"。成熟的追踪系统应该两者都支持。

## 🔧 埋点方式：从"手动" → "自动" → "无侵入"

### 手动埋点（Manual Instrumentation）

工程师在代码里显式创建 Span：

```js
const span = tracer.startSpan('process-order')
try {
  // 业务逻辑
} finally {
  span.end()
}
```

✅ 精确、可控
❌ 工作量巨大，容易遗漏

### 自动埋点（Auto Instrumentation）

框架级的自动插桩——**导入 SDK 后自动为 HTTP、DB、消息队列、Redis 等客户端生成 Span**。

- Java：JVM Agent（`javaagent` 参数）字节码织入
- Node.js：monkey patching（替换 http、mysql 等模块方法）
- Python：importhook + wrapt

✅ 开箱即用，覆盖 90% 场景
❌ 性能有轻微开销

### eBPF / Sidecar 无侵入埋点（前沿）

- **eBPF**：在内核层拦截系统调用，应用完全无感知（Cilium Tetragon、Pixie）
- **Service Mesh**：Envoy Sidecar 在 L7 层自动生成 Span（Istio 原生集成 Jaeger）

✅ 应用零改动
❌ 无法感知应用内部的业务语义

**现代最佳实践**：自动埋点覆盖通用基础设施，手动埋点标注关键业务节点（如"支付成功"、"库存扣减"），两者结合。

## 📊 追踪数据的后端架构

### 存储挑战

追踪数据的特征：**写多、读少、按 trace_id 查**。

| 后端 | 技术栈 | 特点 |
|------|-------|------|
| **Jaeger + Cassandra/ES** | 成熟、重量 | 灵活但运维复杂 |
| **Tempo**（Grafana） | 对象存储 + block | 极低成本，只支持 trace_id 查询 |
| **ClickHouse** | 列存 | 高基数任意维度查询 |
| **SkyWalking + OAP** | 自研存储 | APM 功能更全 |

### 查询模式

最常见的查询：
1. **按 trace_id 查整条链路**（从日志看到 id，跳转到追踪系统）
2. **按服务 + 延迟查 trace**（"过去 1 小时 payment-service 最慢的 10 个请求"）
3. **按错误查 trace**（"所有 status=ERROR 的请求"）
4. **链路对比**（"正常 vs 异常请求，差别在哪一步"）

## 🪢 三支柱的真正联动：关联查询（Correlated Observability）

可观测性的终极形态：**从 metrics → traces → logs 能够一路跳转**。

```
Grafana 看到 P99 异常抖动
    │
    │ [点击] 跳转到 Tempo，看该时间段的慢 traces
    ↓
Tempo 显示某个 trace 在 DB 查询上卡了 3s
    │
    │ [点击] 带着 trace_id 跳转到 Loki 查 DB 服务的日志
    ↓
Loki 显示 "deadlock detected on order table"
```

实现这种联动的关键：**所有三类数据都必须带 trace_id 标签**。这也是为什么业界强烈推荐：
- 日志里自动带 `trace_id` 字段（MDC 模式）
- Metrics 也支持 Exemplar（给时序数据点打 trace_id 标记）
- 统一 OpenTelemetry SDK 自动串起来

**统一的 trace_id 是把三大支柱编织成一张网的"针线"。**

## 🎯 OpenTelemetry

### OpenTelemetry 基础

OpenTelemetry（OTel）是可观测性的行业标准，提供统一的 API 和 SDK 来生成和收集遥测数据。

**核心组件：**
- **API**：定义接口，不依赖具体实现
- **SDK**：提供具体实现和配置
- **Collector**：接收、处理和导出遥测数据
- **Instrumentation**：自动或手动插桩库

### Node.js 集成示例

```javascript
const { trace } = require('@opentelemetry/api');
const { NodeTracerProvider } = require('@opentelemetry/sdk-trace-node');
const { Resource } = require('@opentelemetry/resources');
const { SemanticResourceAttributes } = require('@opentelemetry/semantic-conventions');
const { JaegerExporter } = require('@opentelemetry/exporter-jaeger');
const { BatchSpanProcessor } = require('@opentelemetry/sdk-trace-base');
const { ExpressInstrumentation } = require('@opentelemetry/instrumentation-express');
const { HttpInstrumentation } = require('@opentelemetry/instrumentation-http');
const { registerInstrumentations } = require('@opentelemetry/instrumentation');

// 创建资源
const resource = Resource.default().merge(
  new Resource({
    [SemanticResourceAttributes.SERVICE_NAME]: 'my-app',
    [SemanticResourceAttributes.SERVICE_VERSION]: '1.0.0',
    [SemanticResourceAttributes.DEPLOYMENT_ENVIRONMENT]: 'production'
  })
);

// 创建 Tracer Provider
const provider = new NodeTracerProvider({ resource });

// 配置 Jaeger Exporter
const jaegerExporter = new JaegerExporter({
  endpoint: 'http://jaeger-collector:14268/api/traces',
  maxPacketSize: 65000
});

// 添加 Span Processor
provider.addSpanProcessor(new BatchSpanProcessor(jaegerExporter));

// 注册全局 Tracer Provider
provider.register();

// 注册自动插桩
registerInstrumentations({
  instrumentations: [
    new HttpInstrumentation(),
    new ExpressInstrumentation()
  ]
});

// 获取 Tracer
const tracer = trace.getTracer('my-app', '1.0.0');

// 手动创建 Span
async function processOrder(orderId) {
  const span = tracer.startSpan('processOrder', {
    attributes: {
      'order.id': orderId,
      'order.type': 'purchase'
    }
  });

  try {
    // 添加事件
    span.addEvent('order-received', { orderId });
    
    // 处理订单
    const result = await orderService.process(orderId);
    
    // 添加事件
    span.addEvent('order-processed', { 
      orderId,
      status: result.status 
    });
    
    span.setStatus({ code: trace.SpanStatusCode.OK });
    return result;
  } catch (error) {
    span.recordException(error);
    span.setStatus({
      code: trace.SpanStatusCode.ERROR,
      message: error.message
    });
    throw error;
  } finally {
    span.end();
  }
}

// Express 中间件示例
const express = require('express');
const app = express();

app.use((req, res, next) => {
  const span = trace.getActiveSpan();
  if (span) {
    span.setAttribute('http.method', req.method);
    span.setAttribute('http.url', req.url);
    span.setAttribute('http.user_agent', req.get('user-agent'));
  }
  next();
});

app.get('/orders/:id', async (req, res) => {
  const span = tracer.startSpan('get-order');
  
  try {
    const order = await orderService.get(req.params.id);
    res.json(order);
    span.setStatus({ code: trace.SpanStatusCode.OK });
  } catch (error) {
    span.recordException(error);
    res.status(500).json({ error: error.message });
    span.setStatus({
      code: trace.SpanStatusCode.ERROR,
      message: error.message
    });
  } finally {
    span.end();
  }
});

app.listen(3000, () => {
  console.log('Server running on port 3000');
});
```

### 跨服务追踪

```javascript
// Service A
const axios = require('axios');
const { propagation } = require('@opentelemetry/api');

async function callServiceB(data) {
  const span = tracer.startSpan('call-service-b');
  
  try {
    // 创建 HTTP 请求头
    const headers = {};
    propagation.inject(trace.setSpan(context.active(), span), headers, {
      set: (carrier, key, value) => {
        carrier[key] = value;
      }
    });
    
    // 调用 Service B
    const response = await axios.post('http://service-b/api', data, {
      headers
    });
    
    return response.data;
  } finally {
    span.end();
  }
}

// Service B
app.use((req, res, next) => {
  // 从请求头中提取 Span Context
  const parentContext = propagation.extract(context.active(), req.headers, {
    get: (carrier, key) => {
      return carrier[key];
    }
  });
  
  // 创建子 Span
  const span = tracer.startSpan('handle-request', {
    parentContext
  });
  
  context.with(trace.setSpan(context.active(), span), () => {
    next();
  });
  
  res.on('finish', () => {
    span.end();
  });
});
```

## 🔍 链路分析

### 常见性能问题识别

**1. 慢查询识别：**
```javascript
// 在 Span 中记录查询时间
const span = tracer.startSpan('database-query');
const startTime = Date.now();

try {
  const result = await db.query('SELECT * FROM users WHERE id = ?', [userId]);
  const duration = Date.now() - startTime;
  
  span.setAttribute('db.statement', 'SELECT * FROM users WHERE id = ?');
  span.setAttribute('db.system', 'postgresql');
  span.setAttribute('db.user', 'app_user');
  span.setAttribute('db.duration_ms', duration);
  
  if (duration > 1000) {
    span.addEvent('slow-query', { duration });
  }
  
  return result;
} finally {
  span.end();
}
```

**2. 外部服务调用分析：**
```javascript
async function callExternalAPI(url, data) {
  const span = tracer.startSpan('external-api-call', {
    attributes: {
      'http.url': url,
      'http.method': 'POST',
      'http.scheme': 'https'
    }
  });

  try {
    const startTime = Date.now();
    const response = await axios.post(url, data);
    const duration = Date.now() - startTime;
    
    span.setAttribute('http.status_code', response.status);
    span.setAttribute('http.response_size', response.headers['content-length']);
    span.setAttribute('http.duration_ms', duration);
    
    return response.data;
  } catch (error) {
    span.recordException(error);
    span.setAttribute('http.status_code', error.response?.status || 0);
    throw error;
  } finally {
    span.end();
  }
}
```

**3. 缓存命中率分析：**
```javascript
async function getUser(userId) {
  const span = tracer.startSpan('get-user');
  
  try {
    // 尝试从缓存获取
    const cached = await cache.get(`user:${userId}`);
    if (cached) {
      span.setAttribute('cache.hit', true);
      span.addEvent('cache-hit', { userId });
      return JSON.parse(cached);
    }
    
    // 缓存未命中，从数据库获取
    span.setAttribute('cache.hit', false);
    span.addEvent('cache-miss', { userId });
    
    const user = await db.query('SELECT * FROM users WHERE id = ?', [userId]);
    
    // 写入缓存
    await cache.set(`user:${userId}`, JSON.stringify(user), 3600);
    
    return user;
  } finally {
    span.end();
  }
}
```

### 压测方案设计

**1. 压测标记：**
```javascript
// 在请求头中添加压测标记
app.use((req, res, next) => {
  const isLoadTest = req.headers['x-load-test'] === 'true';
  
  const span = trace.getActiveSpan();
  if (span) {
    span.setAttribute('load_test', isLoadTest);
  }
  
  // 压测数据写入独立的数据源
  if (isLoadTest) {
    req.loadTestDB = loadTestDB;
  } else {
    req.loadTestDB = null;
  }
  
  next();
});
```

**2. 数据隔离：**
```javascript
// 根据压测标记选择数据源
function getDatabase(req) {
  if (req.loadTestDB) {
    return req.loadTestDB;
  }
  return productionDB;
}

// 使用隔离的数据源
async function getUser(req, userId) {
  const db = getDatabase(req);
  return await db.query('SELECT * FROM users WHERE id = ?', [userId]);
}
```

**3. 压测脚本：**
```javascript
// 使用 k6 进行压测
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate } from 'k6/metrics';

// 自定义指标
const errorRate = new Rate('errors');

export const options = {
  stages: [
    { duration: '2m', target: 100 },   // 逐步增加到 100 用户
    { duration: '5m', target: 100 },   // 保持 100 用户
    { duration: '2m', target: 200 },   // 增加到 200 用户
    { duration: '5m', target: 200 },   // 保持 200 用户
    { duration: '2m', target: 0 },     // 逐步减少到 0
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],  // 95% 请求延迟 < 500ms
    errors: ['rate<0.01'],             // 错误率 < 1%
  },
};

const BASE_URL = 'http://my-app.example.com';

export default function () {
  // 添加压测标记
  const params = {
    headers: {
      'x-load-test': 'true',
      'Content-Type': 'application/json',
    },
  };

  // 测试 API
  const res = http.post(`${BASE_URL}/api/orders`, JSON.stringify({
    userId: `user_${__VU}`,
    amount: 100,
  }), params);

  // 检查响应
  const success = check(res, {
    'status is 200': (r) => r.status === 200,
    'response time < 500ms': (r) => r.timings.duration < 500,
  });

  errorRate.add(!success);

  sleep(1);
}
```
