## 📚 章节介绍

## 🌱 云计算的起源与演进

### 前云时代：自建数据中心的痛苦

1990-2005 年，企业 IT 基本都是"自建机房"模式：
- 买服务器、买存储、买网络设备
- 租机柜、布网络、拉专线
- 雇人 7×24 运维
- 采购周期以月计，容量规划要提前半年

问题不仅是成本——更根本的是**交付速度和资源弹性**的矛盾：
- 为了应对流量高峰买很多机器 → 平时利用率 10%
- 真遇到促销/爆款流量 → 机器还是不够
- 新业务立项 → 先等机器到货

### 云计算的三次浪潮

```
Wave 1 (2006-2012): IaaS 登场
    - 2006 AWS 推出 S3、EC2
    - 核心抽象：把硬件变成"按分钟租"的 API

Wave 2 (2013-2018): PaaS + 容器革命
    - Heroku 证明了 PaaS 价值
    - Docker 让 PaaS 标准化 (2013)
    - K8s 成为事实标准 (2017)

Wave 3 (2018-至今): Serverless + 云原生
    - AWS Lambda 开启 FaaS 时代 (2014 起势, 2018 成主流)
    - 关注点从"管理服务器"变成"管理事件与数据流"
    - 多云、混合云成为常态
```

### NIST 对云计算的权威定义

美国国家标准与技术研究院（NIST）在 **2011 年 SP 800-145** 给出云计算的五个基本特征、三种服务模型、四种部署模型，至今仍是**业界公认的黄金定义**：

**五个基本特征**：

| 特征 | 说明 |
|------|------|
| **按需自助（On-demand self-service）** | 不用打电话，自己通过 API/控制台开资源 |
| **广泛网络访问（Broad network access）** | 互联网可达，支持各种客户端 |
| **资源池化（Resource pooling）** | 多租户共享物理资源（虚拟化是关键） |
| **快速弹性（Rapid elasticity）** | 秒级扩缩，对外看起来资源"无限" |
| **可计量服务（Measured service）** | 用多少付多少，资源被精确度量 |

没有这五条的不是"云"，只是"托管"。

**三种服务模型（IaaS / PaaS / SaaS）** 和 **四种部署模型（公有云/私有云/混合云/社区云）** 将在"云服务"章节详细展开。

## 🏛️ 云服务三大模型的本质

理解 IaaS/PaaS/SaaS 的关键不是记名词，而是**看清"责任边界"在哪**。

```
          自建机房   IaaS    PaaS    SaaS
应用数据    你        你      你       云
应用代码    你        你      你       云
运行时      你        你      云       云
中间件      你        你      云       云
操作系统    你        你      云       云
虚拟化      你        云      云       云
服务器      你        云      云       云
存储        你        云      云       云
网络        你        云      云       云
─────────────────────────────────────────
自由度     最高     高      中        低
心智负担   最大     大      中        小
```

- **IaaS**（EC2、ECS）：云给你一台"虚拟服务器"，操作系统以上都你管
- **PaaS**（Heroku、App Engine、函数计算）：云给你一个"运行时"，推代码就跑
- **SaaS**（Gmail、钉钉、Salesforce）：云给你一个"软件"，开箱即用

选哪层？**取决于你愿意把多少控制权交出去换取多少便利**。

## 🤝 责任共担模型（Shared Responsibility Model）

这是**企业上云时最容易踩坑的安全话题**。AWS 最早用图说清楚：

```
┌─────────────────────────────────────┐
│  数据安全、身份认证、应用配置、      │  ← 客户责任
│  网络流量加密、操作系统补丁          │    (Security IN the Cloud)
├─────────────────────────────────────┤
│  物理设施、硬件、虚拟化层、          │  ← 云厂商责任
│  底层网络、存储设备                  │    (Security OF the Cloud)
└─────────────────────────────────────┘
```

**云不会自动让你的应用变安全**：
- S3 存储桶设置为公开读？你数据被扒光 = 你的责任
- 云厂商的机房被攻破？那是云厂商的责任

随服务层级上升（IaaS → PaaS → SaaS），**云厂商承担的责任越来越多，但"数据和访问控制"永远在客户手里**。

## 🌐 Region / Availability Zone：全球化架构的物理现实

云厂商全球基础设施分三级：

```
Region (区域)
  ├── AZ 1 (可用区)
  │    ├── 数据中心 A
  │    └── 数据中心 B
  ├── AZ 2
  │    └── 数据中心 C
  └── AZ 3
       └── 数据中心 D
```

- **Region**：地理区域（北京、上海、弗吉尼亚、东京），之间通过骨干网互联
- **AZ (Availability Zone)**：同一 Region 内的独立故障域，物理上隔离（不同供电、不同制冷、通常相距 10-100 km）
- **数据中心**：AZ 内的物理建筑

### 为什么这样设计？

这是"**故障域设计**"与"**延迟/成本权衡**"的共同产物：

| 层级 | 故障隔离 | AZ 间延迟 | 用途 |
|------|---------|---------|------|
| 同机房 | 最弱（停电一起挂） | \<0.1ms | 单机内 |
| 跨 AZ 同 Region | 强（独立供电/制冷） | 1-2ms | **生产主力**：高可用部署 |
| 跨 Region | 最强（独立地理） | 30-200ms | 灾备、合规、就近访问 |

### 高可用架构的黄金法则

- **单 AZ**：绝对不要生产用，任何机房级故障就挂
- **多 AZ（同 Region）**：业务主力，跨 2-3 个 AZ 部署实例
- **多 Region**：金融、全球业务、灾难恢复

"跨 AZ" 在云上几乎是免费的（网络费便宜、延迟低），**没理由省那点成本把生产放在单 AZ**。

## 🧭 云原生（Cloud Native）：什么才配叫"云原生"？

"上了云"≠"云原生"。把虚拟机代替物理机，应用一行不改——这叫 **Lift and Shift（搬迁上云）**，没利用云的真正价值。

CNCF 定义的云原生五大支柱：

1. **容器化** —— 应用的打包单元标准化
2. **微服务** —— 按业务能力拆分独立部署单元
3. **声明式 API** —— 描述期望状态，而非执行步骤
4. **不可变基础设施** —— 构建后不改，要变就换
5. **DevOps / 持续交付** —— 流程与文化的自动化

"云原生"意味着应用**假设自己运行在云环境里**：
- 单实例可能随时被销毁（接受 pod 被 kill）
- 资源可以按需扩缩（水平扩展优先于垂直）
- 状态要外置（对象存储、数据库、缓存都是外部服务）
- 配置来自环境变量 / ConfigMap（不是硬编码）

这本质是一种**反脆弱**（Antifragile）设计——假设故障必然发生，在故障中保持可用。

## 🔀 多云 / 混合云：现实中的复杂性

### 为什么不只用一朵云？

- **避免厂商锁定**：议价权、合规要求
- **地域覆盖**：国内业务用阿里云，海外用 AWS
- **多活容灾**：防止单一云厂商大面积宕机（AWS 2021 年 12 月断电、阿里云 2022 年香港断电都波及大量客户）
- **合规要求**：数据必须留在境内

### 三种部署模式

| 模式 | 含义 | 典型代表 |
|------|------|---------|
| **公有云**（Public Cloud） | 云厂商多租户共享 | AWS、阿里云 |
| **私有云**（Private Cloud） | 企业专属，自建或托管 | VMware、OpenStack |
| **混合云**（Hybrid Cloud） | 公有 + 私有组合 | AWS Outposts、阿里云混合云 |
| **多云**（Multi-Cloud） | 多个公有云并用 | AWS + Azure + GCP |

**现实中大型企业基本都是"混合云 + 多云"**——核心系统私有云保数据主权，弹性业务放公有云，不同业务分不同云厂商。

### 多云的代价

多云不是免费的：
- **技能栈翻倍**：每朵云的 API、工具、计费模式都不一样
- **网络成本高**：跨云流量贵且慢
- **功能最小公约数**：为了兼容各云，只能用"所有云都有"的基础能力

解决之道：**K8s + Terraform + OpenTelemetry** 这三大 CNCF 标准成为"云无关层"，应用写一次，各云都能跑。

## 🔑 核心概念

### 云服务模型

```
SaaS（软件即服务）    ← 用户直接使用
    ↑
PaaS（平台即服务）    ← 开发者部署应用
    ↑
IaaS（基础设施即服务） ← 运维管理基础设施
    ↑
物理硬件              ← 云厂商管理
```

### 服务网格架构

服务网格将网络通信能力从应用代码中剥离到基础设施层：

```
应用 A → Sidecar Proxy ↔ Sidecar Proxy → 应用 B
                    ↕
              Control Plane（Istio）
```
