# 主流云平台与服务

> **版本**：v1.1
> **最后更新**：2026-04-28

## 📚 概念介绍

云平台提供了弹性的计算、存储、网络等基础设施服务，帮助企业快速构建和部署应用。本节将讲解主流云平台的核心服务和 Serverless 平台。

### 云服务模型

```
SaaS（软件即服务）
    ↑
PaaS（平台即服务）
    ↑
IaaS（基础设施即服务）
    ↑
物理硬件
```

### 主流云平台对比

| 平台 | 优势 | 核心服务 | 适用场景 |
|------|------|---------|---------|
| **阿里云** | 国内市场领先、生态完善 | ECS、RDS、OSS、SLB | 国内业务、企业应用 |
| **AWS** | 全球覆盖、服务最全 | EC2、RDS、S3、Lambda | 全球业务、初创公司 |
| **Azure** | 企业级、微软生态 | VM、SQL Database、Blob | 企业应用、混合云 |
| **GCP** | 数据分析、AI 能力强 | Compute Engine、Cloud SQL、BigQuery | 数据分析、AI 应用 |

## 🧠 多租户（Multi-Tenancy）：云的经济学基础

所有公有云服务的成本优势都来自一个事实：**在同一份物理资源上，同时服务千家万户**。

### 多租户的三种隔离级别

```
      物理隔离          虚拟化隔离         进程隔离         逻辑隔离
┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ 每租户一套    │  │ 共享硬件      │  │ 共享 OS       │  │ 共享应用      │
│ 硬件          │  │ 独立 VM       │  │ 独立容器      │  │ 独立数据      │
│              │  │              │  │              │  │              │
│ Bare Metal   │  │ EC2, ECS     │  │ ECS 轻量版,  │  │ Serverless,  │
│              │  │              │  │ 函数计算      │  │ SaaS         │
└──────────────┘  └──────────────┘  └──────────────┘  └──────────────┘
   独占性 高                                            利用率 高
   成本  高                                             成本  低
```

**租户数量越多、隔离粒度越细，单位成本越低，但复杂度越高**。这是云厂商要同时提供多种产品形态的根本原因。

### 噪声邻居（Noisy Neighbor）问题

多租户共享资源的通病：**同主机上某个租户疯狂消耗 CPU/IO，别的租户被拖慢**。云厂商对抗手段：
- **硬资源隔离**：cgroups CPU quota、内存限制
- **IO 限制**：EBS/OSS 的 burst credit 机制
- **专属实例**（Dedicated Host）：花钱买独占物理机
- **置放组**（Placement Group）：保证你的实例不和竞争对手在同一物理机

## 🏛️ IaaS：把数据中心做成 API

### 核心抽象：从"硬件"到"API 对象"

传统数据中心里每个"服务器"是实物。IaaS 把它们抽象成**可 API 化的对象**：

| 实体 | IaaS 抽象 | 通过 API 可做什么 |
|------|----------|-----------------|
| 物理服务器 | 虚拟机（EC2 Instance、ECS） | 创建、销毁、扩缩容 |
| 硬盘 | 块存储（EBS、云盘） | 挂载、快照、克隆 |
| 交换机/路由器 | VPC、Subnet、Route Table | 软件定义网络 |
| 防火墙 | Security Group | 规则即代码 |
| 负载均衡器 | ALB/SLB | 健康检查、会话保持 |

### 虚拟机的底层演进

从 Xen（2003）→ KVM（2007）→ Firecracker（2018，Amazon 为 Lambda/Fargate 设计），虚拟化技术一直在**追求更低开销、更强隔离**。现代演进方向：

- **MicroVM**（Firecracker、Kata）：VM 级隔离 + 容器级启动速度（125 ms）
- **Nitro / 神龙**：把虚拟化从主 CPU offload 到专用硬件卡
- **Confidential Computing**（SGX、TDX）：连云厂商自己都看不见租户数据

### 计算实例类型为什么有这么多？

AWS 有上百种 EC2 实例类型，因为不同工作负载对资源比例的需求**差异极大**：

| 场景 | 需要 | 典型实例家族（AWS） |
|------|------|-------------------|
| Web 应用 | 均衡 CPU/内存 | M 系列（Balanced） |
| 计算密集 | CPU 强，内存少 | C 系列（Compute） |
| 内存数据库 | 内存大，CPU 够用 | R 系列（Memory） |
| AI 训练 | GPU | P、G 系列 |
| 大数据 | 本地 SSD 多 | I、D 系列 |
| 突发小应用 | 便宜、可突发 | T 系列（Burstable） |

**选对实例类型可省 30-60% 成本**，这是云成本治理的第一课。

## 💾 云存储的三种范式

云上的存储不是一种东西，而是**三大范式**，每种对应不同的访问模式：

| 范式 | 代表服务 | 访问方式 | 适合 | 不适合 |
|------|---------|---------|------|-------|
| **对象存储** | S3、OSS | HTTP API | 海量非结构化数据、静态资源 | 频繁修改、低延迟需求 |
| **块存储** | EBS、云盘 | 挂载为磁盘 | VM 的"硬盘"、数据库 | 跨机共享、海量文件 |
| **文件存储** | EFS、NAS | POSIX 文件系统 | 多 VM 共享目录 | 超大规模（贵） |

### 对象存储：云端最重要的发明

S3（AWS 2006 年发布的第一个服务）重新定义了"海量存储应该长什么样"：

- **扁平命名空间**：没有目录，只有 key（"/foo/bar/baz.jpg"也是一个 key 字符串）
- **API 访问**：HTTP GET/PUT/DELETE，没有 `seek` 没有 `append`
- **极致持久性**：S3 宣称 **11 个 9（99.999999999%）**——100 亿个对象每年可能丢 1 个
- **无限容量**：对用户可见的容量是"无限"
- **事件驱动**：对象写入可触发 Lambda、消息队列

对象存储的经济性：**每 GB 每月约 ¥0.1**，冷归档可低至 ¥0.01。这直接让"保留一切数据"变成默认策略。

### 一致性模型的演进

S3 最初是**最终一致性**（写完马上读可能读不到），大量应用为此加了复杂的重试逻辑。
**2020 年 12 月** AWS 宣布 S3 **强一致性（strong read-after-write）**，这是对象存储的一大里程碑。

## 🗄️ 托管数据库：为什么贵还要用

自建 MySQL vs 托管 RDS，价格可能差 3-5 倍。为什么大部分企业还是选 RDS？

| 维度 | 自建 | 托管 RDS |
|------|------|---------|
| 实例搭建 | 几天（采购、安装、调优） | 分钟（一键创建） |
| 主从部署 | 手工配置 | 勾选"高可用"即可 |
| 备份恢复 | 写脚本、存 S3、恢复预案 | 自动，PITR 任意时间点恢复 |
| 版本升级 | 敢升吗？停机窗口？ | 维护窗口自动 |
| 监控告警 | 自搭 | 原生集成 |
| 扩容 | 分库分表重构 | 点点鼠标 |
| 出故障 | 半夜起来救 | 云厂商 SRE 救 |

托管的本质**不是卖资源，而是卖 SRE 团队**。这些事情自建也要做，找顶级 DBA 可能还做不到云厂商水平。

### NoSQL 与托管 Redis

NoSQL 产品同样受益于托管化：
- **托管 Redis**（ElastiCache、阿里云 Redis）：集群、主从、持久化一键搞定
- **DynamoDB**：无限扩展的键值存储，按 API 调用计费
- **MongoDB Atlas**：跨云托管

趋势：**从"买硬件"转为"买能力"**，这是云时代数据库的最大变革。

## 🌐 云网络的软件定义革命

### VPC（Virtual Private Cloud）：私有网络的软件实现

云上每个租户都有自己的 VPC——一张**完全软件定义的虚拟网络**：
- 自定义 CIDR（如 10.0.0.0/16）
- 划分子网（Subnet），按 AZ 划分
- 配置路由表、NAT 网关
- 安全组（SG）作实例级防火墙
- 网络 ACL 作子网级防火墙

所有这些原本需要网络工程师+物理设备的工作，**现在几行 Terraform 就搞定**。

### 负载均衡的层级选择

| 层级 | 典型产品 | 特征 | 用途 |
|------|---------|------|------|
| **L4** | NLB、SLB TCP | 转发 TCP/UDP，性能极高 | 游戏、TCP 协议 |
| **L7** | ALB、SLB HTTP | 基于 HTTP 规则路由 | Web 应用、API |
| **全球** | CloudFront、CDN | 边缘就近接入 | 静态资源、动态加速 |

### 网络成本：云最容易爆雷的地方

- 同 AZ 流量：免费
- 跨 AZ：低成本但有（约 0.01 元/GB）
- 跨 Region：贵（0.1-0.5 元/GB）
- 出云（到公网）：**最贵**（0.5-1 元/GB，且入云通常免费）

典型事故：**日志全量往 Internet 传到第三方 SaaS，一个月账单几十万**。Egress 成本是企业云账单最大的意外来源。

## ⚡ Serverless：没有服务器，真的吗？

### 定义的两个维度

Serverless 不是真的"没有服务器"，而是**从用户角度"完全不用管服务器"**。核心特征：

1. **不用预置实例**（No provisioning）
2. **按执行付费，而非预留时长**（Pay-per-execution）
3. **自动弹性伸缩，包括缩到零**（Scale to zero）
4. **事件驱动**（Event-driven）

Serverless = **FaaS（Function as a Service）+ BaaS（Backend as a Service）**：

- **FaaS**：运行代码的托管运行时（AWS Lambda、阿里云函数计算、Vercel Functions）
- **BaaS**：第三方提供的后端服务（Auth0 认证、Firebase 数据库、SendGrid 邮件）

### 事件驱动：Serverless 的灵魂

FaaS 不是"另一种部署方式"，而是**以事件为中心的编程模型**：

```
对象存储上传文件 → 触发 Lambda → 生成缩略图 → 写入新桶
消息队列消息     → 触发 Lambda → 处理订单   → 写入 DB
API 网关请求     → 触发 Lambda → 业务逻辑   → 返回响应
定时器           → 触发 Lambda → 定期任务
```

每个事件触发一次函数执行，函数执行完就销毁。

### 冷启动（Cold Start）：Serverless 的阿喀琉斯之踵

FaaS 的函数不是一直跑着的，**长时间没流量就被销毁**。下次请求来：

```
请求到达 → 分配实例 → 拉取代码 → 启动运行时 → 初始化应用 → 执行函数 → 返回
         ─────── 冷启动（几百毫秒到几秒） ─────── │ 执行（毫秒级）│
```

冷启动对延迟敏感的场景是灾难。解决思路：

- **预留实例**（Provisioned Concurrency）：付钱保留 N 个实例常驻
- **更小运行时**：Go/Rust 冷启动快过 JVM
- **MicroVM 优化**：Firecracker 125ms 启动 → Lambda SnapStart 更快
- **保持温热**：定时触发保活（简单但有代价）

### Serverless 适合什么、不适合什么

| 适合 | 不适合 |
|------|-------|
| 事件驱动、偶发任务（文件处理、异步通知） | 长连接（WebSocket 服务器） |
| API 后端（配合 API Gateway） | 需要本地状态的长期运行 |
| 数据流水线（配合消息队列） | 对冷启动极敏感的低延迟 |
| 流量波峰波谷极大的业务 | 稳态高 QPS（反而贵） |
| 初创快速 MVP | 对供应商锁定敏感 |

### 经济学：什么时候该用 Serverless？

单次执行成本 Serverless 比常驻贵，但**当流量稀疏、时段不均匀时反而便宜**。粗略计算：

> **当平均 CPU 利用率 < 20% 时，Serverless 通常比 VM 划算；> 50% 时，常驻实例更便宜。**

这也解释了为什么"API 网关 + Lambda"适合初创（流量小且波动），大厂成熟业务反而回归 K8s。

## 🧩 云原生产品的四个层级

理解云上的产品分层，对选型至关重要：

| 层级 | 你要管什么 | 例子 |
|------|----------|------|
| **物理机** | 所有 | 裸金属实例 |
| **IaaS** | OS 以上 | EC2、ECS |
| **CaaS**（容器） | 应用 + 容器配置 | EKS、ACK、ECS Fargate |
| **PaaS** | 应用代码 | Elastic Beanstalk、Heroku、App Engine |
| **FaaS** | 函数代码 | Lambda、函数计算 |
| **SaaS** | 什么都不用管 | Gmail、钉钉 |

**越往上越便利，越往下越灵活**。大多数现代应用生活在 CaaS（K8s）和 FaaS（Lambda）之间做选择。

### 对象存储

```javascript
const OSS = require('ali-oss');

const client = new OSS({
  region: 'oss-cn-hangzhou',
  accessKeyId: process.env.OSS_ACCESS_KEY_ID,
  accessKeySecret: process.env.OSS_ACCESS_KEY_SECRET,
  bucket: 'my-bucket'

// 上传文件
async function uploadFile(filePath, objectName) {
  try {
    const result = await client.put(objectName, filePath);

  } catch (error) {

    throw error;
  }

  }

async function deleteFile(objectName) {

    console.error('Delete failed:', error);

  }

async function listFiles(prefix) {
```

### Serverless 最佳实践

**1. 冷启动优化：**
```javascript
// 预热连接
let dbConnection = null;

async function getDBConnection() {
  if (!dbConnection) {
    dbConnection = await createDBConnection();
  }
  return dbConnection;
}

exports.handler = async (event) => {
  const db = await getDBConnection();
  // 使用数据库连接
};
```

**2. 资源限制：**
```javascript
// 设置合理的内存和超时时间
const AWS = require('aws-sdk');
const lambda = new AWS.Lambda();

lambda.updateFunctionConfiguration({
  FunctionName: 'my-function',
  MemorySize: 256,
  Timeout: 30
}).promise();
```

**3. 错误处理：**
```javascript
exports.handler = async (event) => {
  try {
    // 业务逻辑
    return await processEvent(event);
  } catch (error) {
    // 记录错误
    console.error('Error:', error);
    
    // 发送到错误追踪服务
    await sendToErrorTracking(error);
    
    // 抛出错误以触发重试
    throw error;
  }
};
```
