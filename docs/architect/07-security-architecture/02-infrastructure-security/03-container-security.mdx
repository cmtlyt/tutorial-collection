# 容器安全

> **版本**：v1.2
> **最后更新**：2026-04-28

## 📚 概念介绍

容器是现代云原生架构的基石，但也引入了新的安全挑战：**镜像供应链风险**、**运行时逃逸**、**过度特权**、**编排层漏洞**。容器安全需要覆盖从镜像构建、分发、运行时到编排层的完整生命周期。

本文以 Docker + Kubernetes 为基础，讲解容器镜像安全、运行时防护、Pod 安全与 Kubernetes 集群加固的最佳实践。

## 📐 理论基础

### 容器 vs 虚拟机：隔离本质的差异

```
   虚拟机（VM）                       容器（Container）
 ┌─────────────────┐                ┌─────────────────┐
 │   App + Libs    │                │   App + Libs    │
 ├─────────────────┤                ├─────────────────┤
 │  Guest OS（完整） │                │  （共享宿主内核）  │
 ├─────────────────┤                ├─────────────────┤
 │   Hypervisor    │                │ Container Runtime│
 ├─────────────────┤                ├─────────────────┤
 │    Host OS      │                │     Host OS     │
 └─────────────────┘                └─────────────────┘

强隔离（硬件虚拟化）                 弱隔离（共享内核）
启动慢、资源重                        启动秒级、资源轻
攻击面小                              攻击面大（内核漏洞即逃逸）
```

容器安全的 **根本挑战**：共享内核意味着一旦内核漏洞被利用，容器隔离立即失效（如 Dirty COW、Dirty Pipe 等逃逸漏洞）。

### Linux 容器的七大基石

容器不是单一技术，而是 Linux 内核多个隔离机制的组合：

| 机制 | 作用 | 安全意义 |
|------|------|---------|
| Namespaces | 资源视图隔离 | 看不到其他容器的资源 |
| Cgroups | 资源配额限制 | 防止资源耗尽型攻击 |
| Capabilities | 细分 root 权限 | 最小权限原则 |
| Seccomp | 系统调用过滤 | 减小内核攻击面 |
| LSM（AppArmor/SELinux） | 强制访问控制 | 规则化约束进程行为 |
| Chroot / Pivot Root | 文件系统根目录切换 | 文件系统隔离 |
| User Namespace | UID/GID 重映射 | 容器内 root ≠ 宿主 root |

### Linux Namespaces 八种类型

当前内核共支持八种命名空间（`man 7 namespaces`）：

| 命名空间 | 隔离对象 | 作用 |
|---------|---------|------|
| mnt | 挂载点 | 独立文件系统视图 |
| pid | 进程 ID | 容器内 PID 1 是其自身 init |
| net | 网络栈 | 独立网卡、路由、iptables |
| ipc | System V IPC、POSIX 消息队列 | 进程间通信隔离 |
| uts | hostname 与 domain | 容器可有自己的主机名 |
| user | UID/GID 映射 | 权限重映射，容器 root 映射为宿主普通用户 |
| cgroup | Cgroup 根 | 限制容器看到的 cgroup 层级 |
| time | 系统时钟 | 独立单调/启动时间（5.6+） |

**User Namespace** 是防止逃逸的关键：启用后，容器内的 UID 0 在宿主机上是一个无特权用户。

### Cgroups v1 vs v2

| 维度 | Cgroups v1 | Cgroups v2 |
|------|-----------|-----------|
| 控制器组织 | 每个控制器独立层级 | 统一单层级 |
| 委派（Delegation） | 复杂 | 简单清晰 |
| PSI（Pressure Stall Info） | 无 | 有，检测资源压力 |
| Rootless 支持 | 弱 | 强 |
| 现代发行版 | 逐渐淘汰 | 默认（RHEL 9、Ubuntu 22.04+） |

可控资源：CPU、内存、IO、PID 数、网络（net_cls/net_prio）、设备访问（devices）、冻结（freezer）。

### Linux Capabilities（`man 7 capabilities`）

传统 Unix 权限只有 root / 非 root 二分，Capabilities 将 root 拆分为约 40 个细粒度能力，常见的高风险能力：

| Capability | 含义 | 风险 |
|-----------|------|------|
| CAP_SYS_ADMIN | 大量管理操作 | 几乎等于 root |
| CAP_SYS_PTRACE | 调试其他进程 | 进程注入 |
| CAP_SYS_MODULE | 加载内核模块 | 直接逃逸 |
| CAP_NET_ADMIN | 网络配置 | 修改路由、嗅探 |
| CAP_NET_RAW | 原始套接字 | ARP 欺骗、嗅探 |
| CAP_DAC_OVERRIDE | 绕过文件权限检查 | 读取任意文件 |
| CAP_SETUID / CAP_SETGID | 切换用户 | 提权 |
| CAP_CHOWN | 更改文件所有者 | 提权辅助 |

容器安全基线：**丢弃所有能力，按需精确授予**（如 `NET_BIND_SERVICE` 用于绑定 1024 以下端口）。

### Seccomp-BPF：系统调用过滤

Linux 约 400+ 系统调用是内核的主要攻击面。Seccomp-BPF 允许用户态定义过滤规则，Docker 默认配置会禁用约 50 个危险系统调用（`keyctl`、`reboot`、`mount`、`swapon` 等）。

过滤动作：

- `SCMP_ACT_ALLOW`：放行
- `SCMP_ACT_ERRNO`：返回错误（不崩溃，推荐）
- `SCMP_ACT_KILL`：杀死进程
- `SCMP_ACT_LOG`：放行并记录（审计模式）

### LSM：AppArmor vs SELinux

**Linux Security Modules** 提供 MAC（强制访问控制），在 DAC 之上再加一层：

| 机制 | 规则模型 | 易用性 | 代表发行版 |
|------|---------|-------|-----------|
| AppArmor | 基于路径 | 简单 | Ubuntu、Debian |
| SELinux | 基于标签 | 复杂但强大 | RHEL、CentOS、Fedora |

Docker 默认加载 `docker-default` AppArmor 配置。Kubernetes 中可通过 `annotations` 或 `SecurityContext.appArmorProfile`（v1.30+）声明。

### 容器运行时的两层架构（CRI）

```
┌─────────────────────────────────────┐
│   Kubernetes (kubelet)              │
└─────────────────────┬───────────────┘
                       │ CRI (gRPC)
┌─────────────────────▼───────────────┐
│   高级运行时（containerd / CRI-O）    │ ← 管理镜像、生命周期
└─────────────────────┬───────────────┘
                       │ OCI Runtime API
┌─────────────────────▼───────────────┐
│   低级运行时（runc / crun / youki）   │ ← 实际创建命名空间、cgroup
└─────────────────────┬───────────────┘
                       │
┌─────────────────────▼───────────────┐
│   Linux 内核（Namespaces/Cgroups等）  │
└─────────────────────────────────────┘
```

### 安全沙箱运行时

当默认的 runc 隔离强度不够时，可选用沙箱运行时：

| 运行时 | 隔离技术 | 开销 | 适用 |
|-------|---------|------|------|
| runc | 原生 Linux 隔离 | 极低 | 默认 |
| gVisor（runsc） | 用户态内核（拦截系统调用） | 中 | 多租户不可信负载 |
| Kata Containers | 轻量虚拟机 | 中高 | 强隔离需求 |
| Firecracker | microVM（AWS Lambda 基础） | 低 | Serverless |

### OCI 三大规范

**OCI（Open Container Initiative）** 由 Docker、CoreOS 等 2015 年成立，定义容器的开放标准：

1. **OCI Runtime Specification**：定义容器如何运行（`config.json` + 根文件系统）
2. **OCI Image Specification**：定义镜像格式（Manifest / Config / Layers，内容寻址）
3. **OCI Distribution Specification**：定义镜像分发协议（Registry API）

镜像的 **内容寻址**：每一层由 `sha256:...` digest 唯一标识，内容不可变，tag 可变但 digest 不可变，这是镜像签名与防篡改的基础。

### Kubernetes 威胁模型（MITRE ATT&CK for Containers）

MITRE 专门发布了 Kubernetes 攻击矩阵，覆盖九个战术：

```
初始访问 → 执行 → 持久化 → 权限提升 → 防御逃避 → 凭据访问 → 发现 → 横向移动 → 影响
```

典型攻击路径示例：

1. 通过暴露的 kubelet `:10250` 未授权端口执行命令
2. 利用 hostPath 挂载读取 `/var/run/docker.sock` 获得宿主控制
3. 滥用特权 Pod 加载内核模块逃逸
4. 利用过度授权的 ServiceAccount Token 访问 API Server
5. 通过 ImagePullSecrets 窃取 Registry 凭据

### 供应链攻击与 SLSA 等级

供应链攻击的真实案例：XZ Utils 后门（CVE-2024-3094）、SolarWinds、event-stream、ua-parser-js、Codecov、log4shell。

**SLSA**（Supply-chain Levels for Software Artifacts，发音 "salsa"）由 Google 提出，定义四个成熟度等级：

| 等级 | 要求 | 核心能力 |
|------|------|---------|
| SLSA 1 | 有构建文档 | 可追溯 |
| SLSA 2 | 托管构建服务 + 签名来源（Provenance） | 防止简单篡改 |
| SLSA 3 | 源码与构建平台经过审计，Provenance 不可伪造 | 防止中等级别攻击 |
| SLSA 4 | 两人评审、密封构建、可复现构建 | 防御国家级攻击 |

**Provenance**（来源证明）：描述"由谁、用什么源码、在哪台机器、何时、如何构建出"的可验证元数据，由 in-toto / SLSA Provenance / Sigstore 落地。

### SBOM：软件物料清单

SBOM 是软件的"配料表"，记录所有直接与传递依赖及其版本、许可证、哈希。三大主流格式：

| 格式 | 维护方 | 特点 |
|------|-------|------|
| CycloneDX | OWASP | 安全导向，生态丰富 |
| SPDX | Linux Foundation | 许可证与合规导向 |
| SWID | ISO/IEC 19770-2 | 资产标签 |

SBOM 的核心价值：**当新 CVE 披露时，可以在数分钟内定位受影响的应用**（例如 Log4Shell 爆发时，有 SBOM 的组织可精确定位到具体系统）。

### Kubernetes Pod 安全演进

```
PodSecurityPolicy (PSP)  →  Pod Security Standards (PSS) + Pod Security Admission (PSA)
     1.0~1.24 废弃                           1.25+ 正式
     规则复杂、难以理解              三档等级（Privileged/Baseline/Restricted），命名空间级强制
```

除内置 PSA，更灵活的方案是策略引擎：

- **OPA Gatekeeper**：基于 Rego 语言的通用策略引擎
- **Kyverno**：Kubernetes 原生语法，YAML 即策略
- **jsPolicy**：JavaScript 策略
- **Cloud Native Policy**：各云厂商的托管方案

### 容器逃逸典型路径

| 类别 | 典型漏洞/手法 |
|------|-------------|
| 特权容器 | `--privileged` 默认可访问宿主设备 |
| 敏感挂载 | 挂载 `/`、`/etc`、`docker.sock`、`/proc` |
| 内核漏洞 | Dirty COW（CVE-2016-5195）、Dirty Pipe（CVE-2022-0847） |
| 运行时漏洞 | runc CVE-2019-5736、CVE-2024-21626（Leaky Vessels） |
| 配置错误 | CAP_SYS_ADMIN、SYS_MODULE、禁用 seccomp |
| 组件漏洞 | cri-o、containerd 历史 CVE |

### 最小权限的实践谱

```
禁用（drop ALL capabilities） ← → 容器内非 root ← → 只读根文件系统 ← → seccomp=RuntimeDefault
         ↓                              ↓                    ↓                    ↓
  启用（按需 add）            User Namespace 重映射      tmpfs 挂载可写目录    自定义 seccomp 白名单
         ↓                              ↓                    ↓                    ↓
     启用 AppArmor/SELinux     禁止特权提升（no-new-privs） 无 hostPath/hostNet   gVisor/Kata 沙箱
```

## 🎯 镜像构建安全

### 安全 Dockerfile 示例

```dockerfile
# ❌ 反面示例
# FROM node:latest  # 避免 latest 标签
# COPY . /app       # 全量拷贝，可能带入 .env 等敏感文件
# USER root         # 以 root 运行
# RUN npm install   # 不区分生产/开发依赖

# ✅ 推荐写法：多阶段构建 + 最小化运行时
# 阶段 1：构建
FROM node:20.11.1-alpine3.19 AS builder

WORKDIR /build
COPY package.json package-lock.json ./
# 使用 ci 严格锁定依赖版本
RUN npm ci --prefer-offline --no-audit

COPY . .
RUN npm run build && npm prune --omit=dev

# 阶段 2：运行时（distroless，无 shell，无包管理器）
FROM gcr.io/distroless/nodejs20-debian12:nonroot

WORKDIR /app

# 拷贝非特权用户需要的最小产物
COPY --from=builder --chown=nonroot:nonroot /build/node_modules ./node_modules
COPY --from=builder --chown=nonroot:nonroot /build/dist ./dist
COPY --from=builder --chown=nonroot:nonroot /build/package.json ./

# 显式使用非 root 用户（distroless nonroot 镜像预设 UID 65532）
USER nonroot

# 仅暴露必要端口
EXPOSE 3000

# 健康检查
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
    CMD ["/nodejs/bin/node", "-e", "require('http').get('http://127.0.0.1:3000/health', r => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"]

ENTRYPOINT ["/nodejs/bin/node", "dist/index.js"]
```

### 安全基线检查清单

- [ ] 使用固定版本基础镜像，禁用 `latest`
- [ ] 使用官方或经过审计的基础镜像（distroless、chainguard、alpine）
- [ ] 多阶段构建，运行时镜像不包含编译工具
- [ ] 使用非 root 用户运行（`USER`）
- [ ] 通过 `.dockerignore` 排除敏感文件
- [ ] 使用 `COPY` 而非 `ADD`（ADD 会自动解压 tar）
- [ ] 不在 `ENV` 或 `ARG` 中放密钥（构建历史可见）
- [ ] 运行时文件系统只读（`--read-only`）
- [ ] 删除构建后的临时文件、缓存、包管理元数据
- [ ] 镜像最终大小最小化（优先使用 distroless / scratch）

### Trivy 使用示例

```bash
# 扫描本地镜像
trivy image --severity HIGH,CRITICAL myapp:1.0.0

# 扫描时失败（用于 CI 门禁）
trivy image --exit-code 1 --severity CRITICAL myapp:1.0.0

# 扫描 Dockerfile 配置错误
trivy config Dockerfile

# 扫描文件系统（源码仓库）

# 扫描 Kubernetes 集群
trivy k8s --report summary cluster

# 生成 SBOM（CycloneDX / SPDX）
trivy image --format cyclonedx --output sbom.json myapp:1.0.0
```

### CI 集成（GitHub Actions）

```yaml
# .github/workflows/container-security.yml
name: Container Security
on:
  pull_request:
  push:
    branches: [main]

jobs:
  image-scan:
    runs-on: ubuntu-latest
    permissions:
      security-events: write
      contents: read
    steps:
      - uses: actions/checkout@v4

      - name: Build image
        run: docker build -t myapp:${{ github.sha }} .

      - name: Trivy image scan
        uses: aquasecurity/trivy-action@0.20.0
        with:
          image-ref: myapp:${{ github.sha }}
          format: sarif
          output: trivy-results.sarif
          severity: HIGH,CRITICAL
          exit-code: 1
          ignore-unfixed: true

      - name: Upload to GitHub Security
        if: always()
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: trivy-results.sarif

      - name: Dockerfile scan
        uses: aquasecurity/trivy-action@0.20.0
        with:
          scan-type: config
          scan-ref: .
          severity: HIGH,CRITICAL
```

## 🎯 运行时安全

### Docker 安全运行参数

```bash
docker run \
  --read-only \                               # 根文件系统只读
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \   # 临时目录可写
  --cap-drop ALL \                            # 丢弃所有 Linux capability
  --cap-add NET_BIND_SERVICE \                # 仅保留必要 capability
  --security-opt no-new-privileges \          # 禁止提权（sudo/su）
  --security-opt seccomp=seccomp-profile.json \
  --security-opt apparmor=docker-default \
  --pids-limit 100 \                          # 进程数限制
  --memory 512m --memory-swap 512m \          # 内存限制
  --cpus 1.0 \                                # CPU 限制
  --user 1000:1000 \                          # 非 root
  --network my-net \                          # 自定义网络（不要 host）
  --restart unless-stopped \
  myapp:1.0.0
```

### 运行时威胁检测（Falco）

Falco 是 CNCF 毕业项目，基于 eBPF 实时检测异常行为。

```yaml
# /etc/falco/falco_rules.local.yaml
- rule: Shell in Container
  desc: Detect shell execution in a container
  condition: >
    container.id != host and
    proc.name in (bash, sh, zsh, ash, csh, fish, ksh)
  output: >
    Shell in container (user=%user.name container=%container.name
    image=%container.image.repository:%container.image.tag
    proc=%proc.cmdline parent=%proc.pname)
  priority: WARNING
  tags: [container, shell, mitre_execution]

- rule: Write to Sensitive File
  desc: Detect writes to sensitive system files
  condition: >
    container.id != host and
    open_write and
    (fd.name startswith /etc/passwd or
     fd.name startswith /etc/shadow or
     fd.name startswith /etc/sudoers)
  output: >
    Sensitive file write (user=%user.name file=%fd.name
    container=%container.name)
  priority: CRITICAL
  tags: [container, filesystem]

- rule: Outbound Connection to Suspicious Port
  desc: Detect outbound connections to mining pools or C2
  condition: >
    container.id != host and
    outbound and
    fd.sport in (3333, 4444, 5555, 7777, 14444)
  output: >
    Suspicious outbound (container=%container.name
    dest=%fd.sip:%fd.sport)
  priority: CRITICAL
  tags: [container, network, mitre_command_and_control]
```

## 🎯 Kubernetes Pod 安全

### Pod Security Standards（PSS）

Kubernetes 1.25+ 内置三个等级，替代已废弃的 PodSecurityPolicy：

| 等级 | 说明 |
|------|------|
| Privileged | 无限制，仅用于系统工作负载 |
| Baseline | 最小限制，防止已知的特权提升 |
| Restricted | 严格限制，符合 Pod 加固最佳实践 |

```yaml
# 命名空间启用 PSS Restricted
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

### 安全的 Pod 规范

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-api
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-api
  template:
    metadata:
      labels:
        app: web-api
    spec:
      # 禁用默认 ServiceAccount 自动挂载 Token
      automountServiceAccountToken: false
      serviceAccountName: web-api-sa

      securityContext:
        runAsNonRoot: true
        runAsUser: 65532
        runAsGroup: 65532
        fsGroup: 65532
        seccompProfile:
          type: RuntimeDefault

      containers:
        - name: app
          image: registry.example.com/web-api@sha256:abcdef123456 # 使用 digest 而非 tag
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 3000
              name: http

          # 容器级安全上下文
          securityContext:
            allowPrivilegeEscalation: false
            privileged: false
            readOnlyRootFilesystem: true
            runAsNonRoot: true
            runAsUser: 65532
            capabilities:
              drop:
                - ALL

          # 资源限制（防止 DoS）
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi

          # 只读根文件系统需要挂载可写的临时目录
          volumeMounts:
            - name: tmp
              mountPath: /tmp
            - name: cache
              mountPath: /var/cache

          # 健康检查
          livenessProbe:
            httpGet:
              path: /health
              port: http
            initialDelaySeconds: 10
            periodSeconds: 10
          readinessProbe:
            httpGet:
              path: /ready
              port: http
            initialDelaySeconds: 5
            periodSeconds: 5

          # 环境变量从 Secret 引用
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password

      volumes:
        - name: tmp
          emptyDir:
            medium: Memory
            sizeLimit: 64Mi
        - name: cache
          emptyDir:
            sizeLimit: 256Mi

      # 禁止调度到非特定节点
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: workload-type
                    operator: In
                    values: [general]
```

### 准入控制（OPA Gatekeeper / Kyverno）

使用 Kyverno 在集群层面强制执行策略：

```yaml
# 禁止特权容器
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-privileged
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: no-privileged-containers
      match:
        any:
          - resources:
              kinds: [Pod]
      validate:
        message: "Privileged containers are not allowed"
        pattern:
          spec:
            =(initContainers):
              - =(securityContext):
                  =(privileged): "false"
            containers:
              - =(securityContext):
                  =(privileged): "false"

---
# 要求镜像来自受信仓库
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: trusted-registries
spec:
  validationFailureAction: Enforce
  rules:
    - name: trusted-registry
      match:
        any:
          - resources:
              kinds: [Pod]
      validate:
        message: "Images must come from registry.example.com"
        pattern:
          spec:
            containers:
              - image: "registry.example.com/*"

---
# 要求镜像经过 Cosign 签名
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-image-signature
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-signature
      match:
        any:
          - resources:
              kinds: [Pod]
      verifyImages:
        - imageReferences:
            - "registry.example.com/*"
          attestors:
            - entries:
                - keys:
                    publicKeys: |
                      -----BEGIN PUBLIC KEY-----
                      MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...
                      -----END PUBLIC KEY-----
```

## 📝 实际应用示例：完整安全的 Node.js 容器化交付

**`Dockerfile`**

```dockerfile
FROM node:20.11.1-alpine3.19 AS builder
WORKDIR /build
COPY package.json package-lock.json ./
RUN npm ci --prefer-offline --no-audit
COPY . .
RUN npm run build && npm prune --omit=dev

FROM gcr.io/distroless/nodejs20-debian12:nonroot
WORKDIR /app
COPY --from=builder --chown=nonroot:nonroot /build/node_modules ./node_modules
COPY --from=builder --chown=nonroot:nonroot /build/dist ./dist
COPY --from=builder --chown=nonroot:nonroot /build/package.json ./
USER nonroot
EXPOSE 3000
ENTRYPOINT ["/nodejs/bin/node", "dist/index.js"]
```

**`src/index.js`**（最小 HTTP 服务示例，仅作运行时参考）

```js
import http from 'node:http'

const server = http.createServer((req, res) => {
  if (req.url === '/health') {
    res.writeHead(200, { 'Content-Type': 'application/json' })
    res.end(JSON.stringify({ status: 'ok' }))
    return
  }
  if (req.url === '/ready') {
    res.writeHead(200, { 'Content-Type': 'application/json' })
    res.end(JSON.stringify({ ready: true }))
    return
  }
  res.writeHead(200, { 'Content-Type': 'application/json' })
  res.end(JSON.stringify({ message: 'Hello from secure container' }))
})

const port = Number(process.env.PORT || 3000)
server.listen(port, '0.0.0.0', () => {
  console.log(`listening on ${port}`)
})

const shutdown = () => {
  server.close(() => process.exit(0))
}
process.on('SIGTERM', shutdown)
process.on('SIGINT', shutdown)
```

**构建、扫描、签名、部署**

```bash
# 1. 构建
IMAGE=registry.example.com/web-api:1.0.0
docker build -t "$IMAGE" .

# 2. 扫描
trivy image --severity HIGH,CRITICAL --exit-code 1 "$IMAGE"

# 3. 推送 + 拿到 digest
docker push "$IMAGE"
DIGEST=$(docker inspect --format='{{index .RepoDigests 0}}' "$IMAGE")

# 4. 签名
cosign sign --key cosign.key "$DIGEST"

# 5. 部署（使用 digest 锁定镜像）
kubectl set image deployment/web-api app="$DIGEST" -n production
```

## 🔗 相关概念

- **Distroless / Scratch**：最小运行时镜像，显著减少攻击面
