# 数据流设计

> **版本**：v1.1
> **最后更新**：2026-04-27

## 📖 概述

如果说数据建模回答的是"数据怎么存"，那么数据流设计回答的是"数据怎么动"。

在一个典型的企业数据架构中，数据需要从业务系统流向数据仓库，从数据仓库流向分析平台，从实时数据流流向监控大屏……每一条数据流都涉及**提取、转换、加载、同步**等操作，而这些操作的设计直接决定了数据的**时效性**、**可靠性**和**一致性**。

数据流设计面临一个核心矛盾：**实时性 vs 可靠性**。越是追求实时（低延迟），数据处理的复杂度和出错风险就越高；越是追求可靠（数据一致、容错），就越难做到实时。整个数据流架构的演进——从批处理到流处理再到流批一体——本质上就是在这两个维度上不断寻找更好的平衡。

## 🎯 学习目标

- 理解数据流设计的核心挑战和设计权衡
- 掌握 ETL 和 ELT 的差异、适用场景及技术演进
- 理解 Lambda、Kappa、流批一体三种架构的设计哲学
- 掌握 CDC（Change Data Capture）的实现方案及其理论基础
- 能够设计端到端的实时数据管道

## 📚 ETL vs ELT

### 两种范式的哲学差异

ETL 和 ELT 虽然只是字母顺序不同，却代表了两种截然不同的数据处理哲学：

- **ETL（Extract-Transform-Load）**：先转换再加载。代表了**"数据必须干净才能进仓库"** 的理念。这种思路源自传统数据仓库时代，因为存储和计算资源昂贵，只有经过清洗的"好数据"才值得被存储
- **ELT（Extract-Load-Transform）**：先加载再转换。代表了**"先把原始数据存下来，转换可以随时做"** 的理念。这种思路源自云计算时代，存储成本大幅降低，而云数据仓库（如 BigQuery、Snowflake）的计算能力足以在查询时完成转换

ETL 到 ELT 的转变不仅仅是技术层面的——它反映了一个更深层的范式转移：**从"存储为中心"到"计算为中心"**。当存储成本趋近于零时，"先存后算"比"先算后存"更灵活，也更安全（原始数据永远不会丢失）。

### ETL（Extract-Transform-Load）

```js
// ETL 流程
const etlProcess = {
  extract: {
    description: "从源系统提取数据",
    methods: [
      "数据库查询",
      "API 调用",
      "文件读取",
      "日志采集"
    ]
  },
  transform: {
    description: "在中间层转换数据",
    operations: [
      "数据清洗",
      "格式转换",
      "数据聚合",
      "数据验证"
    ],
    location: "独立的服务器或 ETL 工具"
  },
  load: {
    description: "加载到目标系统",
    targets: [
      "数据仓库",
      "数据集市",
      "分析数据库"
    ]
  },
  advantages: [
    "数据质量高",
    "减轻目标系统压力",
    "适合复杂转换逻辑"
  ],
  disadvantages: [
    "处理速度慢",
    "需要额外的转换层",
    "资源消耗大"
  ]
}
```

### ELT（Extract-Load-Transform）

```js
// ELT 流程
const eltProcess = {
  extract: {
    description: "从源系统提取数据",
    methods: ["与 ETL 相同"]
  },
  load: {
    description: "先加载到目标系统",
    targets: ["云数据仓库（如 Snowflake、BigQuery）"]
  },
  transform: {
    description: "在目标系统内转换数据",
    operations: ["使用目标系统的计算能力"],
    location: "目标系统内部"
  },
  advantages: [
    "处理速度快",
    "利用目标系统的计算能力",
    "成本更低",
    "保留原始数据"
  ],
  disadvantages: [
    "依赖目标系统性能",
    "数据质量需要额外保证"
  ]
}
```

### ETL vs ELT 对比

| 特性 | ETL | ELT |
|------|-----|-----|
| 转换位置 | 中间层 | 目标系统 |
| 处理速度 | 慢 | 快 |
| 数据质量 | 高 | 需要额外保证 |
| 成本 | 高 | 低 |
| 适用场景 | 传统数仓 | 云数据仓库 |
| 复杂转换 | 适合 | 受限 |

## 📚 流批一体架构

### 从批处理到流处理的演进

理解流批一体架构，首先需要理解"批处理"和"流处理"的本质区别：

- **批处理（Batch Processing）**：将数据按时间窗口（如每天、每小时）分批处理。就像邮局收集一天的信件后统一投递——效率高但延迟大
- **流处理（Stream Processing）**：数据到达后立即处理。就像快递员实时投递每一封信——延迟小但处理逻辑更复杂

在实际业务中，这两种需求往往同时存在：实时监控大屏需要秒级延迟的流处理，月度报表则可以接受小时级延迟的批处理。如何用一套架构同时满足这两种需求？这就是流批一体架构要解决的核心问题。

### Lambda 架构

```js
// Lambda 架构
const lambdaArchitecture = {
  batchLayer: {
    description: "批处理层",
    features: [
      "处理全量历史数据",
      "高容错性",
      "延迟高（小时级）"
    ],
    technologies: ["Hadoop", "Spark"]
  },
  speedLayer: {
    description: "速度层",
    features: [
      "处理实时数据",
      "低延迟（秒级）",
      "容错性较低"
    ],
    technologies: ["Flink", "Spark Streaming", "Kafka Streams"]
  },
  servingLayer: {
    description: "服务层",
    features: [
      "合并批处理和实时结果",
      "提供查询服务"
    ],
    technologies: ["Cassandra", "HBase", "Redis"]
  },
  disadvantages: [
    "需要维护两套代码",
    "架构复杂",
    "一致性难以保证"
  ]
}
```

### Kappa 架构

Lambda 架构虽然解决了实时性和准确性的矛盾，但它有一个致命的缺点：**需要维护两套完全不同的代码**——批处理层一套逻辑、速度层一套逻辑。这两套逻辑需要产生一致的结果，维护成本极高。

LinkedIn 的 Jay Kreps 在 2014 年提出了 Kappa 架构作为替代方案。其核心思想简洁而大胆：**如果流处理引擎足够强大，为什么还需要批处理？** 直接用流处理覆盖所有场景，当需要"重算"历史数据时，只需要重放消息队列中的历史消息即可。

```js
// Kappa 架构
const kappaArchitecture = {
  description: "简化的流处理架构",
  features: [
    "只有流处理层",
    "通过重放历史数据实现批处理",
    "代码统一"
  ],
  workflow: [
    "所有数据通过消息队列",
    "流处理引擎实时处理",
    "需要批处理时重放消息队列"
  ],
  advantages: [
    "架构简单",
    "代码统一",
    "维护成本低"
  ],
  disadvantages: [
    "依赖消息队列的保留能力",
    "重放历史数据成本高"
  ]
}
```

### 流批一体

Lambda 和 Kappa 各有局限：Lambda 维护成本高，Kappa 对消息队列的依赖过重。现代流批一体架构试图找到更好的解决方案——**用统一的编程模型和 API 处理流和批**。

Apache Flink 是流批一体的标杆实现。它将批处理视为**流处理的一种特殊情况**（有界流 vs 无界流），因此用同一套 API 就能处理两种工作负载。这种设计从根本上消除了 Lambda 架构中"两套代码"的问题。

```js
// 流批一体架构
const streamBatchUnified = {
  description: "统一的流批处理框架",
  features: [
    "一套代码处理流和批",
    "统一的 API",
    "自动容错和状态管理"
  ],
  technologies: [
    "Flink（流批一体）",
    "Spark Structured Streaming",
    "Kafka Streams"
  ],
  advantages: [
    "开发效率高",
    "维护成本低",
    "一致性好"
  ]
}
```

## 📚 CDC（Change Data Capture）

### CDC 的核心价值

CDC（变更数据捕获）解决的是一个看似简单但极其重要的问题：**如何高效地把一个数据库的变更同步到其他系统？**

传统的数据同步方式是"全量拉取"——定期查询源数据库中所有数据，与目标系统对比后更新差异。这种方式的问题在于：当数据量大到一定程度后，全量拉取的开销变得不可接受。

CDC 的思路是**只关注"变了什么"**，而不是"全部是什么"。它的灵感来自数据库内部的复制机制——MySQL 的主从复制就是通过读取 Binlog（事务日志）来同步变更的。CDC 把这种能力暴露给了外部系统，使得任何下游系统都可以"订阅"数据库的变更事件。

这带来了三个核心价值：

1. **实时性**：变更发生后毫秒级捕获，而不是等待下一次全量拉取
2. **低开销**：只传输变更的增量数据，对源数据库的性能影响极小
3. **完整性**：基于事务日志的 CDC 可以捕获所有类型的变更，包括 INSERT、UPDATE 和 DELETE

### CDC 实现方案

CDC 有三种主要的实现方式，它们在实时性、侵入性和复杂度上有不同的权衡：

```js
// CDC 实现方式
const cdcMethods = {
  timestampBased: {
    description: "基于时间戳",
    method: "查询 updated_at > last_sync_time 的记录",
    advantages: ["实现简单"],
    disadvantages: ["无法捕获删除", "需要额外字段"]
  },
  triggerBased: {
    description: "基于触发器",
    method: "在数据库触发器中捕获变更",
    advantages: ["实时性好"],
    disadvantages: ["影响数据库性能", "维护复杂"]
  },
  logBased: {
    description: "基于日志",
    method: "读取数据库的事务日志（Binlog/WAL）",
    advantages: [
      "实时性好",
      "不影响数据库性能",
      "能捕获所有变更（包括删除）"
    ],
    disadvantages: ["实现复杂"],
    tools: ["Debezium", "Canal", "Maxwell"]
  }
}
```

### Debezium + Kafka CDC 方案

在实践中，**基于日志的 CDC** 是最推荐的方案，而 Debezium + Kafka 是这一方案的事实标准组合：

- **Debezium** 负责连接源数据库、读取事务日志、将变更转换为标准化的事件格式
- **Kafka** 作为中间的消息总线，负责事件的持久化和分发
- **下游消费者** 可以是数据仓库、搜索引擎、缓存或任何需要数据同步的系统

这种架构的优雅之处在于**解耦**——源数据库不需要知道有哪些下游系统在消费它的变更，下游系统也不需要直接连接源数据库。新增一个下游消费者只需要订阅对应的 Kafka Topic，完全不影响源数据库和其他消费者。

```js
// Debezium CDC 架构
const debeziumArchitecture = {
  source: {
    description: "源数据库",
    databases: ["MySQL", "PostgreSQL", "MongoDB", "Oracle"]
  },
  debezium: {
    description: "CDC 连接器",
    features: [
      "读取数据库日志",
      "捕获变更事件",
      "转换为 Kafka 消息"
    ]
  },
  kafka: {
    description: "消息队列",
    role: "存储和传输变更事件"
  },
  consumers: {
    description: "消费者",
    destinations: [
      "数据仓库",
      "搜索引擎",
      "缓存",
      "其他应用"
    ]
  }
}

// Debezium 事件示例
const debeziumEvent = {
  before: "变更前的数据（UPDATE/DELETE）",
  after: "变更后的数据（INSERT/UPDATE）",
  op: "操作类型（c=create, r=read, u=update, d=delete）",
  ts_ms: "时间戳",
  source: {
    db: "数据库名",
    table: "表名",
    server_id: "服务器 ID",
    file: "日志文件",
    pos: "日志位置"
  }
}
```
