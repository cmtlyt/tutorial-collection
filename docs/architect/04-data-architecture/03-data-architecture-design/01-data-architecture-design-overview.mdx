# 数据架构设计 - 总览

> **版本**：v1.1
> **最后更新**：2026-04-27

## 📚 章节介绍

数据架构是企业技术架构中最核心的组成部分之一。如果说应用架构定义了"系统怎么运行"，那么数据架构定义了"数据怎么流动"。

一个好的数据架构需要回答四个根本性问题：

1. **数据从哪里来？**（数据源和数据采集）
2. **数据怎么存储？**（数据建模和存储选型）
3. **数据怎么流动？**（数据管道和 ETL/ELT）
4. **数据怎么治理？**（数据质量、安全和合规）

本章节围绕这四个问题，讲解企业级数据架构的设计方法。

## 🏛️ 理论基础

### 数据架构的角色定位

在企业架构的经典框架（如 TOGAF）中，数据架构与业务架构、应用架构、技术架构并列为四大架构域。但在实践中，数据架构往往是最容易被忽视的——很多团队在项目初期只关注应用功能的实现，到了后期才发现数据散落在各个系统中，难以整合和分析。

数据架构师的核心职责不是选型某个具体的数据库，而是**建立数据从产生到消费的完整生命周期管理**：

```
数据产生 → 数据采集 → 数据存储 → 数据处理 → 数据服务 → 数据消费
                                    ↑
                              数据治理（贯穿全链路）
```

### 数据架构演进

数据架构的演进反映了业务需求和技术能力的共同发展。理解这个演进脉络，有助于你判断当前企业处于哪个阶段，以及下一步应该往哪个方向发展：

```
单体数据库（满足基本业务需求）
    ↓ 瓶颈：读写性能不足
读写分离 + 分库分表（扩展在线事务处理能力）
    ↓ 需求：离线数据分析
数据仓库（结构化数据的集中分析）
    ↓ 需求：多源异构数据的统一存储
数据湖（存储所有格式的原始数据）
    ↓ 痛点：数据湖缺乏治理，变成"数据沼泽"
湖仓一体 Lakehouse（结合数据湖的灵活性和数仓的治理能力）
    ↓ 需求：实时性
实时数据平台（流批一体，秒级延迟）
```

每一次演进都不是对上一代的完全替代，而是在保留上一代能力的基础上，增加新的能力来解决新的问题。很多企业同时存在多种架构形态。

### OLTP 与 OLAP 的本质区别

理解数据架构设计，必须首先理解两种截然不同的数据处理模式：

| 维度 | OLTP（联机事务处理） | OLAP（联机分析处理） |
|------|-------|-------|
| **核心操作** | 增、删、改、查单条记录 | 复杂查询、聚合、分析 |
| **数据量** | 每次操作涉及少量行 | 每次操作扫描大量行 |
| **延迟要求** | 毫秒级 | 秒级到分钟级可接受 |
| **并发模式** | 高并发、短事务 | 低并发、长查询 |
| **数据模型** | 范式化（3NF），减少冗余 | 反范式化（星型/雪花），便于分析 |
| **代表系统** | MySQL、PostgreSQL | ClickHouse、Snowflake、Hive |

一个常见的架构反模式是**在 OLTP 数据库上跑 OLAP 查询**——这会严重影响在线业务的性能。数据架构设计的一个核心目标就是将这两种工作负载分离到不同的系统中。
