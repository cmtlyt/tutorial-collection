# 数据建模

> **版本**：v1.1
> **最后更新**：2026-04-27

## 📖 概述

数据建模是数据架构设计中最核心的环节——它决定了数据如何被组织、存储和查询。一个好的数据模型不仅能满足当前的业务需求，还能适应未来的变化。

数据建模有两大流派，分别服务于不同的目标：

- **ER 建模（实体关系建模）**：面向 OLTP 场景，追求**数据的规范化和一致性**。核心思想是消除冗余，确保每个事实只存储一次
- **维度建模**：面向 OLAP 场景，追求**查询的简洁和高效**。核心思想是通过适度冗余换取分析查询的性能

这两种方法不是互相替代的，而是在数据架构的不同层次各司其职——业务数据库使用 ER 建模保证事务的一致性，数据仓库使用维度建模提升分析的效率。

## 🎯 学习目标

- 理解 ER 建模和维度建模的设计哲学差异
- 掌握 ER 建模的规范化方法及其理论依据

- 掌握数据仓库的分层设计（ODS → DWD → DWS → ADS）及每层的职责
- 了解数据湖和湖仓一体架构的演进逻辑

## 📚 ER 建模

### 实体关系模型的理论基础

ER 模型由 Peter Chen 在 1976 年提出，是关系型数据库设计的标准方法论。它的核心思想是将现实世界抽象为三种基本元素：

- **实体（Entity）**：可以独立存在的"事物"，如用户、订单、商品
- **属性（Attribute）**：描述实体特征的数据，如用户的姓名、年龄
- **关系（Relationship）**：实体之间的关联，如用户"购买"商品

ER 建模的过程就是**从业务需求中识别出实体、属性和关系，然后通过规范化消除数据冗余**的过程。

### 实体关系模型

```js
// ER 模型核心概念
const erModel = {
  entity: {
    description: "实体",
    example: "用户、订单、商品",
    notation: "矩形"
  },
  attribute: {
    description: "属性",
    example: "姓名、年龄、价格",
    notation: "椭圆"
  },
  relationship: {
    description: "关系",
    example: "购买、关注、雇佣",
    notation: "菱形"
  },
  cardinality: {
    description: "基数",
    types: [
      "一对一（1:1）",
      "一对多（1:N）",
      "多对多（M:N）"
    ]
  }
}
```

### 数据库规范化

规范化（Normalization）是 ER 建模的核心技术，其目标是通过一系列规则（称为"范式"）来**消除数据冗余和更新异常**。

为什么数据冗余是有害的？考虑一个简单的例子：如果"部门名称"同时存储在每一行员工记录中，那么当部门改名时，你需要更新所有员工的记录——这就是"更新异常"。如果只更新了一部分记录，数据就不一致了。

规范化通过**将数据拆分到不同的表中**来消除这种冗余，使得每个事实只存储在一个地方。但规范化也有代价——查询时需要更多的 JOIN 操作。这就是为什么 OLTP 系统追求高度规范化（减少冗余），而 OLAP 系统倾向于反规范化（减少 JOIN）。

```js
// 规范化范式
const normalizationForms = {
  firstNF: {
    name: "第一范式（1NF）",
    requirement: "每个属性都是原子值，不可再分",
    example: `
-- 违反 1NF
用户: "Alice, Bob" (多个值在一个字段)

-- 符合 1NF
用户1: "Alice"
用户2: "Bob"
    `
  },
  secondNF: {
    name: "第二范式（2NF）",
    requirement: "满足 1NF，且非主属性完全依赖于主键",
    example: `
-- 违反 2NF
订单表: (订单ID, 商品ID, 商品名称, 数量)
-- 商品名称只依赖于商品ID，不依赖于(订单ID, 商品ID)

-- 符合 2NF
订单表: (订单ID, 商品ID, 数量)
商品表: (商品ID, 商品名称)
    `
  },
  thirdNF: {
    name: "第三范式（3NF）",
    requirement: "满足 2NF，且非主属性不传递依赖于主键",
    example: `
-- 违反 3NF
用户表: (用户ID, 姓名, 部门ID, 部门名称)
-- 部门名称传递依赖于用户ID

-- 符合 3NF
用户表: (用户ID, 姓名, 部门ID)
部门表: (部门ID, 部门名称)
    `
  }
}
```

## 📚 维度建模

### 维度建模的核心思想

维度建模由 Ralph Kimball 在 1996 年的《The Data Warehouse Toolkit》中系统化提出，是数据仓库设计的事实标准。

与 ER 建模"消除冗余"的思路截然不同，维度建模的核心思想是：**围绕业务过程（Business Process）组织数据，将数据分为"度量"和"维度"两类**。

- **度量（Measure）**：可以量化的业务指标，如销售额、订单数、点击次数。这些数据存储在**事实表（Fact Table）** 中
- **维度（Dimension）**：描述度量的上下文信息，回答"谁？什么时候？在哪里？什么产品？"等问题。这些数据存储在**维度表（Dimension Table）** 中

维度建模的设计流程遵循"四步法"：
1. **选择业务过程**：确定要建模的业务事件（如"用户下单"）
2. **声明粒度（Grain）**：确定事实表中每一行代表什么（如"一次购买行为"还是"一天的销售汇总"）
3. **识别维度**：确定哪些角度可以用来分析这个业务过程（如时间、用户、商品、地区）
4. **确定度量**：确定需要记录哪些可量化的指标（如金额、数量）

### 星型模型

```js
// 星型模型结构
const starSchema = {
  description: "一个事实表连接多个维度表",
  structure: {
    factTable: {
      description: "事实表",
      features: [
        "存储度量值（数值）",
        "包含外键引用维度表",
        "数据量大，增长快"
      ],
      example: "销售事实表：订单ID、用户ID、商品ID、销售额、数量"
    },
    dimensionTable: {
      description: "维度表",
      features: [
        "存储描述性属性",
        "数据量相对较小",
        "变化缓慢"
      ],
      examples: [
        "用户维度：用户ID、姓名、年龄、性别",
        "商品维度：商品ID、名称、类别、品牌",
        "时间维度：日期ID、年、月、日、星期"
      ]
    }
  },
  advantages: [
    "查询性能好（JOIN 少）",
    "结构简单，易于理解",
    "适合快速分析"
  ],
  disadvantages: [
    "数据冗余",
    "存储空间占用大"
  ]
}
```

### 雪花模型

```js
// 雪花模型结构
const snowflakeSchema = {
  description: "维度表进一步规范化，形成层次结构",
  structure: {
    factTable: "与星型模型相同",
    normalizedDimensions: {
      description: "规范化的维度表",
      example: `
商品维度表: 商品ID, 名称, 类别ID, 品牌ID
类别维度表: 类别ID, 类别名称, 父类别ID
品牌维度表: 品牌ID, 品牌名称, 国家ID
国家维度表: 国家ID, 国家名称, 大洲
      `
    }
  },
  advantages: [
    "数据冗余少",
    "存储空间占用小",
    "维护方便"
  ],
  disadvantages: [
    "查询性能差（JOIN 多）",
    "结构复杂"
  ]
}
```

### 星型 vs 雪花

| 特性 | 星型模型 | 雪花模型 |
|------|---------|---------|
| 查询性能 | 高（JOIN 少） | 中（JOIN 多） |
| 存储空间 | 大（数据冗余） | 小（规范化） |
| 结构复杂度 | 简单 | 复杂 |
| 维护性 | 中 | 高 |
| 适用场景 | 快速分析、数据集市 | 复杂分析、企业级数仓 |

## 📚 数据仓库分层设计

### 为什么需要分层？

数据仓库的分层设计解决的核心问题是**复杂性管理**。在一个企业级数据仓库中，数据来自数十甚至数百个源系统，经过清洗、转换、聚合后，最终服务于各种报表和分析需求。如果没有分层，数据加工逻辑会变得极其混乱——每个报表都直接从原始数据开始加工，导致大量重复计算和不一致的指标定义。

分层架构的核心理念是**逐层提炼**：

- 越靠近数据源的层次，数据越"原始"、越"明细"
- 越靠近应用的层次，数据越"干净"、越"汇总"
- 相邻层次之间有清晰的加工规则，每一层只依赖上一层

这种设计带来了三个关键好处：

1. **复用性**：中间层的公共指标可以被多个上层应用复用，避免重复计算
2. **可追溯性**：从最终的报表数据可以逐层追溯到原始数据，便于排查数据问题
3. **解耦性**：源系统的变化只影响最底层，不会波及到上层应用

### 分层架构

```js
// 数据仓库分层模型
const dataWarehouseLayers = {
  ODS: {
    name: "操作数据层（Operational Data Store）",
    description: "原始数据存储层",
    features: [
      "与源系统数据结构一致",
      "不做清洗和转换",
      "保留历史数据"
    ],
    example: "原始订单表、原始用户表"
  },
  DWD: {
    name: "数据仓库明细层（Data Warehouse Detail）",
    description: "明细数据层",
    features: [
      "数据清洗和规范化",
      "统一维度和度量",
      "保持明细粒度"
    ],
    example: "订单明细表、用户明细表"
  },
  DWS: {
    name: "数据仓库汇总层（Data Warehouse Summary）",
    description: "轻度汇总层",
    features: [
      "按主题域汇总",
      "预计算常用指标",
      "支持多维分析"
    ],
    example: "日销售汇总、月用户活跃度"
  },
  ADS: {
    name: "应用数据层（Application Data Store）",
    description: "应用数据层",
    features: [
      "面向业务应用",
      "高度汇总",
      "直接用于报表和 BI"
    ],
    example: "销售报表、用户增长报表"
  }
}
```

### 分层示例

```sql
-- ODS 层：原始订单数据
CREATE TABLE ods_order_raw (
    order_id BIGINT,
    user_id BIGINT,
    product_id BIGINT,
    amount DECIMAL(10,2),
    status VARCHAR(20),
    created_at TIMESTAMP,
    updated_at TIMESTAMP
) PARTITIONED BY (dt STRING);

-- DWD 层：清洗后的订单明细
CREATE TABLE dwd_order_detail (
    order_id BIGINT,
    user_id BIGINT,
    product_id BIGINT,
    amount DECIMAL(10,2),
    status VARCHAR(20),
    order_date DATE,
    created_at TIMESTAMP,
    updated_at TIMESTAMP
) PARTITIONED BY (dt STRING);

-- DWS 层：日销售汇总
CREATE TABLE dws_sales_daily (
    product_id BIGINT,
    sales_date DATE,
    order_count BIGINT,
    total_amount DECIMAL(15,2),
    avg_amount DECIMAL(10,2)
) PARTITIONED BY (dt STRING);

-- ADS 层：销售报表
CREATE TABLE ads_sales_report (
    product_id BIGINT,
    product_name STRING,
    period STRING,
    total_sales DECIMAL(15,2),
    growth_rate DECIMAL(5,2)
);
```

## 📚 数据湖与湖仓一体

### 数据仓库的局限性

传统数据仓库在处理**结构化数据的分析**方面表现优异，但面对以下场景时力不从心：

- **非结构化数据**：图片、视频、日志文件等无法装进"表和列"的数据
- **Schema 未知的数据**：在数据采集时还不清楚将来会怎么分析，无法预先定义表结构
- **机器学习工作负载**：ML 模型训练需要大量的原始数据，而不是预先聚合好的汇总数据

数据湖的诞生就是为了解决这些问题。它的核心理念是：**先把所有数据存下来，以后再决定怎么用**。这种 "Schema-on-Read"（读取时定义模式）的策略与数据仓库的 "Schema-on-Write"（写入时定义模式）形成了鲜明对比。

### 数据湖架构

```js
// 数据湖特点
const dataLake = {
  description: "存储原始数据的集中式存储库",
  features: [
    "存储所有格式的数据（结构化、半结构化、非结构化）",
    "Schema-on-read（读取时定义模式）",
    "低成本存储",
    "支持大规模数据处理"
  ],
  advantages: [
    "数据存储成本低",
    "支持多种数据类型",
    "灵活的数据处理"
  ],
  disadvantages: [
    "缺乏数据治理",
    "查询性能相对较差",
    "数据质量难以保证"
  ]
}
```

### 湖仓一体架构

数据湖虽然解决了灵活性问题，但在实践中暴露了一个严重的问题：**缺乏治理的数据湖会变成"数据沼泽"（Data Swamp）**——数据越积越多，但没人知道里面有什么、数据质量如何、哪些数据还有用。

湖仓一体（Lakehouse）架构应运而生，它试图**取两者之长**：

- 继承数据湖的**低成本存储**和**格式灵活性**（底层仍然使用对象存储）
- 引入数据仓库的 **ACID 事务**、**Schema 管理**和**查询优化**（通过 Delta Lake、Apache Iceberg、Apache Hudi 等表格式实现）

Lakehouse 的关键技术创新在于在开放的文件格式（如 Parquet）之上增加了一个**元数据层**，这个元数据层提供了事务日志、Schema 演化、时间旅行（Time Travel）等能力，使得数据湖也能像数据仓库一样被可靠地管理和查询。

```js
// 湖仓一体（Lakehouse）
const lakehouse = {
  description: "结合数据湖的灵活性和数据仓库的性能",
  features: [
    "数据湖的低成本存储",
    "数据仓库的 ACID 事务",
    "Schema enforcement（模式强制）",
    "支持 BI 和机器学习",
    "统一的数据治理"
  ],
  technologies: [
    "Delta Lake",
    "Apache Iceberg",
    "Apache Hudi"
  ],
  advantages: [
    "存储成本低",
    "查询性能高",
    "支持事务",
    "统一的数据管理"
  ]
}
```

### 数据架构演进

```
单体数据库
    ↓
数据仓库（结构化数据）
    ↓
数据湖（多源异构数据）
    ↓
湖仓一体（Lakehouse）
    ↓
实时数据平台（流批一体）
```

## 📝 实际应用示例

### 电商数据仓库设计

```sql
-- 1. ODS 层：原始数据
CREATE TABLE ods_orders (
    order_id BIGINT,
    user_id BIGINT,
    order_items ARRAY<STRUCT<product_id BIGINT, quantity INT, price DECIMAL(10,2)>>,
    total_amount DECIMAL(10,2),
    status VARCHAR(20),
    created_at TIMESTAMP,
    updated_at TIMESTAMP
) PARTITIONED BY (dt STRING);

-- 2. DWD 层：订单明细（展开商品）
CREATE TABLE dwd_order_items (

    price DECIMAL(10,2),
    amount DECIMAL(10,2),
    status VARCHAR(20),
    order_date DATE,
    created_at TIMESTAMP
) PARTITIONED BY (dt STRING);

-- 3. DWS 层：商品日销售汇总
CREATE TABLE dws_product_sales_daily (
    product_id BIGINT,
    sales_date DATE,
    order_count BIGINT,
    total_quantity BIGINT,
    total_amount DECIMAL(15,2),
    avg_price DECIMAL(10,2),
    distinct_users BIGINT
) PARTITIONED BY (dt STRING);

-- 4. ADS 层：商品销售趋势
CREATE TABLE ads_product_trend (
    product_id BIGINT,
    product_name STRING,
    period STRING,
    total_sales DECIMAL(15,2),
    order_count BIGINT,
```
