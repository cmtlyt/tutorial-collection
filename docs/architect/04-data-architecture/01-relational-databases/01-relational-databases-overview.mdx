# 关系型数据库 - 总览

> **版本**：v1.1
> **最后更新**：2026-04-27

## 📚 章节介绍

关系型数据库是现代信息系统的基石。自 1970 年 Edgar F. Codd 提出关系模型以来，它已经发展了半个多世纪，至今仍然是绝大多数企业级应用的首选数据存储方案。

本章节深入讲解关系型数据库的**理论基础**和**核心原理**，再到生产环境中的优化技术，帮助你从底层原理到工程实践建立完整的知识体系。

## 🏛️ 理论基础

### 关系模型的诞生

1970 年，IBM 研究员 Edgar F. Codd 发表了开创性论文《A Relational Model of Data for Large Shared Data Banks》，提出了**关系模型**（Relational Model）的概念。这一理论的核心思想是：

- **数据以表（关系）的形式组织**：每个表是一组元组（行）的集合，每个元组由固定数量的属性（列）组成
- **数据操作基于关系代数**：通过选择（Selection）、投影（Projection）、连接（Join）等数学运算来查询和处理数据
- **数据独立性**：应用程序不需要关心数据的物理存储方式，只需要通过逻辑视图操作数据

这三个思想奠定了关系型数据库的理论基础，也解释了为什么 SQL 语言是**声明式**的——你只需要描述"想要什么"，而不需要告诉数据库"怎么去找"。

### ACID 特性

关系型数据库之所以在金融、电商等对数据一致性要求极高的场景中不可替代，核心原因在于它提供了 **ACID** 事务保证：

- **原子性（Atomicity）**：事务中的所有操作要么全部成功，要么全部失败回滚。不存在"做了一半"的中间状态。例如，银行转账时从 A 账户扣款和向 B 账户加款必须同时成功或同时失败
- **一致性（Consistency）**：事务执行前后，数据库必须从一个一致状态转换到另一个一致状态。所有的数据约束（主键、外键、CHECK 约束等）在事务结束后仍然成立
- **隔离性（Isolation）**：并发执行的事务之间互不干扰。即使多个事务同时操作同一份数据，每个事务也感知不到其他事务的存在
- **持久性（Durability）**：事务一旦提交，其结果是永久性的。即使系统崩溃，已提交的数据也不会丢失

ACID 的实现依赖于一系列精密的底层机制——**WAL（Write-Ahead Logging）** 保证原子性和持久性，**锁机制和 MVCC** 保证隔离性，**约束检查** 保证一致性。这些机制将在后续章节中详细展开。

### CAP 定理与关系型数据库

分布式系统中著名的 **CAP 定理**指出，一个分布式系统最多只能同时满足以下三项中的两项：

- **一致性（Consistency）**：所有节点看到的数据是相同的
- **可用性（Availability）**：每个请求都能得到响应
- **分区容错性（Partition Tolerance）**：网络分区时系统仍能运行

传统的单机关系型数据库选择了 **CA**——强一致性 + 高可用性。而当数据量增长到单机无法承载时，就需要引入分库分表、读写分离等方案，这时就不可避免地要面对 CAP 的权衡取舍。理解这一点，是理解后续数据库优化策略的前提。

## 🔑 核心概念

### 事务隔离级别

SQL 标准定义了四种事务隔离级别，它们在**并发性能**和**数据一致性**之间做出了不同的权衡。隔离级别越高，数据一致性越好，但并发性能越差：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---------|------|----------|------|------|
| 读未提交 | ✓ | ✓ | ✓ | 最高 |
| 读已提交 | ✗ | ✓ | ✓ | 高 |
| 可重复读 | ✗ | ✗ | ✓* | 中 |
| 串行化 | ✗ | ✗ | ✗ | 最低 |

*InnoDB 通过 MVCC + 间隙锁在可重复读级别也可以防止幻读

理解这些异常现象很重要：

- **脏读（Dirty Read）**：读到了其他事务尚未提交的数据。如果那个事务最终回滚了，你就读到了"不存在"的数据
- **不可重复读（Non-Repeatable Read）**：同一个事务内，两次读取同一行数据得到了不同的结果，因为其间有另一个事务修改并提交了该行
- **幻读（Phantom Read）**：同一个事务内，两次执行相同的范围查询，第二次多出了或少了一些行，因为其间有另一个事务插入或删除了满足条件的行

### 为什么 MySQL 默认使用可重复读？

大多数数据库（如 PostgreSQL、Oracle、SQL Server）默认使用**读已提交**隔离级别，但 MySQL（InnoDB）默认使用**可重复读**。这是一个历史决策——MySQL 早期的主从复制依赖 Statement-Based Replication（SBR），而在读已提交隔离级别下，SBR 可能导致主从数据不一致。虽然现在 MySQL 已经支持 Row-Based Replication（RBR），但默认隔离级别的惯例一直保留了下来。
