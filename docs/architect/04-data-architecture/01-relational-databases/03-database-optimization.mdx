# 数据库优化

> **版本**：v1.1
> **最后更新**：2026-04-27

## 📖 概述

数据库优化不是一项孤立的技术活动，而是一个**系统性的工程实践**。它涉及从 SQL 语句级别的微观调优，到数据库架构级别的宏观设计。

一个常见的误区是"遇到性能问题就加索引"。实际上，数据库优化应当遵循一个清晰的层次：

1. **SQL 优化**（成本最低、见效最快）：通过优化查询语句和索引设计来提升性能
2. **架构优化**（成本中等）：通过读写分离、连接池调优等手段提升系统整体吞吐
3. **分库分表**（成本最高、风险最大）：当前两层优化都无法满足需求时，才考虑数据分片

这三个层次之间存在明确的**优先级关系**——永远先尝试低成本的方案。过早引入分库分表不仅增加系统复杂度，还会带来分布式事务、跨分片查询等一系列棘手问题。

## 🎯 学习目标

- 能够分析 SQL 执行计划并进行查询优化
- 理解查询优化器的工作原理和决策逻辑
- 掌握分库分表的策略、适用场景和限制
- 理解读写分离的架构设计及一致性权衡
- 掌握连接池的原理、配置和调优

## 📚 查询优化

### 查询优化器的工作原理

当你向数据库发送一条 SQL 语句时，它不会直接执行你写的内容，而是经过以下流程：

```
SQL 语句 → 解析器 → 语法树 → 优化器 → 执行计划 → 执行引擎 → 结果
```

其中**优化器（Optimizer）** 是最关键的环节。MySQL 使用**基于成本的优化器（CBO, Cost-Based Optimizer）**，它会：

1. 枚举所有可能的执行方式（使用哪个索引、用什么连接算法、以什么顺序连接表）
2. 根据统计信息（表的行数、索引的基数、数据分布等）估算每种执行方式的"成本"
3. 选择成本最低的方案作为最终的执行计划

理解优化器的决策逻辑很重要——有时优化器"选错"了执行计划（比如统计信息过时），这时你需要通过 `ANALYZE TABLE` 更新统计信息，或使用 `FORCE INDEX` 提示来引导优化器。

### 执行计划分析

```sql
-- 使用 EXPLAIN 分析查询执行计划
EXPLAIN SELECT 
    o.id,
    o.order_no,
    u.username,
    p.product_name,
    oi.quantity,
    oi.price
FROM orders o
INNER JOIN users u ON o.user_id = u.id
INNER JOIN order_items oi ON o.id = oi.order_id
INNER JOIN products p ON oi.product_id = p.id
WHERE o.status = 'pending'
AND o.created_at >= '2025-01-01'
ORDER BY o.created_at DESC
LIMIT 100;

-- 执行计划关键字段说明
const explainColumns = {
  id: "查询序列号，表示执行顺序",
  select_type: "查询类型（SIMPLE/PRIMARY/SUBQUERY/DERIVED）",
  type: "访问类型（性能：const > eq_ref > ref > range > index > ALL）",
  possible_keys: "可能使用的索引",
  key: "实际使用的索引",
  key_len: "使用的索引长度",
  ref: "索引引用的列",
  rows: "预估扫描行数",
  filtered: "过滤后的行数百分比",
  Extra: "额外信息（Using index/Using filesort/Using temporary）"
}
```

### SQL 优化技巧

SQL 优化的核心目标是**减少数据库引擎需要处理的数据量**。大部分性能问题都可以归结为以下三类：

- **读取了不需要的数据**：使用 `SELECT *` 读取了所有列，但实际只需要其中几个
- **扫描了不需要的行**：没有合适的索引，导致全表扫描
- **做了不必要的计算**：在索引列上使用了函数，导致索引失效

```sql
-- 1. 避免 SELECT *
-- 错误示例
SELECT * FROM orders WHERE user_id = 123;

-- 正确示例：只查询需要的字段
SELECT id, order_no, status, total_amount 
FROM orders 
WHERE user_id = 123;

-- 2. 避免在索引列上使用函数
-- 错误示例
SELECT * FROM users WHERE YEAR(created_at) = 2025;

-- 正确示例：使用范围查询
SELECT * FROM users 
WHERE created_at >= '2025-01-01' 
AND created_at < '2026-01-01';

-- 3. 使用 UNION ALL 替代 UNION（如果不需要去重）
-- UNION 会进行去重操作，性能较差
SELECT user_id FROM orders WHERE status = 'pending'
UNION
SELECT user_id FROM orders WHERE status = 'processing';

-- UNION ALL 不会去重，性能更好
SELECT user_id FROM orders WHERE status = 'pending'
UNION ALL
SELECT user_id FROM orders WHERE status = 'processing';

-- 4. 使用 LIMIT 限制结果集
SELECT * FROM orders 
WHERE status = 'pending' 
ORDER BY created_at DESC 
LIMIT 20;
```

## 📚 分库分表

### 什么时候需要分库分表？

分库分表是数据库优化的"最后手段"，在引入之前应当先考虑以下替代方案：

- **单表数据量超过 2000 万行**（经验值，取决于硬件和查询模式）且查询性能已经无法通过索引优化来满足
- **单库的写入 QPS 超过了实例上限**，且无法通过硬件升级解决
- **单库的存储容量已经接近上限**

分库分表的代价是巨大的——它会引入以下复杂性：

- **分布式事务**：跨库的 ACID 保证变得困难，需要引入 2PC、TCC 等方案
- **跨分片查询**：涉及多个分片的 JOIN、ORDER BY、GROUP BY 操作需要在应用层完成
- **全局唯一 ID**：自增主键不再适用，需要引入分布式 ID 生成方案（Snowflake、UUID 等）
- **数据迁移**：扩容时需要将数据重新分布到新的分片上

因此，架构师在做决策时应当遵循一个原则：**能不分就不分，非分不可时再分**。

### 垂直分库 vs 水平分表

```js

  }

```

### 分片键选择

分片键（Sharding Key）的选择是分库分表方案中**最关键的设计决策**，一旦确定就很难更改。好的分片键需要同时满足两个目标：

- **数据均匀分布**：避免出现数据倾斜（某些分片数据远多于其他分片），否则会形成"热点"
- **查询路由高效**：大部分查询应当能够直接定位到具体的分片，避免"广播查询"（查询所有分片再合并结果）

这两个目标有时是矛盾的。例如，按用户 ID 分片可以让"查询某用户的所有订单"只命中一个分片，但"查询某个时间段的所有订单"就需要广播到所有分片。选择分片键时，**应当优先满足最高频的查询场景**。

```js
// 分片键设计原则
const shardingKeyDesign = {
  principles: [
    "查询频率高的字段",
    "数据分布均匀",
    "避免热点数据",
    "考虑业务扩展性"
  ],
  commonShardingKeys: {
    user_id: "用户相关数据，按用户 ID 取模",
    order_id: "订单数据，按订单 ID 哈希",
    date: "按时间范围分片（适合报表查询）",
    region: "按地域分片（就近访问）"
  }
}

// 分片算法示例
const shardAlgorithms = {
  modulo: {
    name: "取模分片",
    formula: "shard = id % shard_count",
    example: "user_id % 16",
    advantages: "数据分布均匀",
    disadvantages: "扩容困难（需要数据迁移）"
  },
  range: {
    name: "范围分片",
    formula: "shard = (id - min_id) / range_size",
    example: "user_id / 1000000",
    advantages: "范围查询高效",
    disadvantages: "数据分布不均"
  },
  hash: {
    name: "哈希分片",
    formula: "shard = hash(id) % shard_count",
    example: "MD5(user_id) % 16",
    advantages: "数据分布均匀",
    disadvantages: "不支持范围查询"
  }
}
```

## 📚 读写分离

### 读写分离的理论基础

在大多数互联网应用中，读请求的数量远大于写请求（通常是 10:1 甚至 100:1）。读写分离的核心思想是：**将写操作集中到主库，将读操作分散到多个从库**，从而水平扩展读能力。

这种方案的理论基础是**最终一致性（Eventual Consistency）**——从库的数据可能比主库"滞后"一小段时间（通常是毫秒级），但最终会追上。对于大部分业务场景（如商品列表、文章阅读），这种短暂的延迟是可以接受的。

但需要特别注意**"读写不一致"问题**：用户写入一条数据后立即查询，如果查询被路由到了从库，可能看不到刚写入的数据。这就是所谓的"写后读不一致"。解决方案包括：

- **写后读走主库**：在写操作后的短时间窗口内，将读请求路由到主库
- **等待复制完成**：利用半同步复制确保至少一个从库收到了最新数据
- **设置会话级别的路由**：同一会话内的读请求在写操作后自动路由到主库

### 主从复制架构

## 📚 连接池管理

### 为什么需要连接池？

数据库连接是一种**昂贵的资源**。每次建立一个新连接，数据库需要完成 TCP 三次握手、身份认证、分配内存等操作，耗时通常在毫秒级。如果每个请求都创建新连接，在高并发场景下会导致：

- **连接建立的开销**占据了大部分请求时间
- **数据库连接数爆满**，超过 `max_connections` 限制后新请求被拒绝
- **频繁的连接创建和销毁**给数据库带来额外的 GC 压力

连接池的核心思想是**预先创建一批数据库连接，放入"池"中复用**。应用程序需要连接时从池中"借"一个，用完后"还"回去。这样避免了频繁的连接创建和销毁开销。

连接池的配置需要在**资源利用率**和**请求等待时间**之间找到平衡：

- 连接数太少：请求需要排队等待可用连接
- 连接数太多：占用过多数据库资源，反而降低整体性能（上下文切换开销）

一个常用的经验公式是：`最大连接数 = CPU 核心数 × 2 + 有效磁盘数`。对于 SSD 磁盘，有效磁盘数通常为 1。

### 连接池配置

```js
// 连接池配置示例（以 HikariCP 为例）
const hikariCPConfig = {
  basic: {
    minimumIdle: 10,
    maximumPoolSize: 50,
    connectionTimeout: 30000,
    idleTimeout: 600000,
    maxLifetime: 1800000
  },
  tuning: {
    description: "连接池调优建议",
    rules: [
      "minimumIdle = maximumPoolSize / 2",
      "maximumPoolSize = 核心数 * 2 + 有效磁盘数",
      "maxLifetime 不应超过数据库的 wait_timeout",
      "监控活跃连接数和等待时间"
    ]
  },
  monitoring: {
    metrics: [
      "活跃连接数（activeConnections）",
      "空闲连接数（idleConnections）",
      "等待线程数（waitingThreads）",
      "连接获取时间（connectionTimeout）"
    ]
  }
}
```

## 📝 实际应用示例

### 综合优化方案

```sql
-- 场景：优化订单查询性能

-- 1. 创建合适的索引
CREATE INDEX idx_order_user_status_created ON orders(user_id, status, created_at);
CREATE INDEX idx_order_status_created ON orders(status, created_at);

-- 2. 优化查询语句
SELECT 
    o.id,
    o.order_no,
    o.status,
    o.total_amount,
    o.created_at
FROM orders o
WHERE o.user_id = ?
AND o.status IN ('pending', 'processing')
AND o.created_at >= ?
ORDER BY o.created_at DESC
LIMIT 20;

-- 3. 分析执行计划
EXPLAIN SELECT ...;

-- 4. 监控慢查询
-- 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow-query.log';

-- 5. 定期优化表
OPTIMIZE TABLE orders;
ANALYZE TABLE orders;
```
