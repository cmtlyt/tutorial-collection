# 文档数据库

> **版本**：v1.1
> **最后更新**：2026-04-27

## 📖 概述

文档数据库是 NoSQL 家族中应用最广泛的一类。它的核心理念是：**数据以自包含的文档（Document）为单位存储，而不是分散在多个关联的表中**。

想象一下，在关系型数据库中存储一个"用户"的完整信息，可能需要 `users`、`addresses`、`preferences` 三张表加上 JOIN 查询。而在文档数据库中，所有信息可以存储在一个 JSON 文档中——就像你在代码中使用的对象一样自然。

这种设计带来了两个显著的优势：

1. **数据局部性（Data Locality）**：相关数据存储在一起，一次磁盘读取就能获取完整信息，避免了多表 JOIN 的开销
2. **Schema 灵活性**：不需要预定义表结构，同一集合中的文档可以有不同的字段。这在产品快速迭代的场景中非常有价值

当然，文档数据库也有其局限：**不擅长处理复杂的关系查询**。如果你的数据模型中大量存在多对多关系和跨集合的关联查询，关系型数据库可能仍然是更好的选择。

## 📚 MongoDB 核心概念

### 文档模型

MongoDB 中的基本概念与关系型数据库有一一对应关系，但语义有所不同：

| 关系型数据库 | MongoDB | 关键区别 |
|------------|---------|---------|
| Database | Database | 基本相同 |
| Table | Collection | Collection 不强制 Schema |
| Row | Document | Document 可以嵌套、结构可变 |
| Column | Field | Field 的类型在不同文档间可以不同 |
| JOIN | $lookup / 嵌入 | 推荐嵌入而非关联 |

## 📚 文档建模策略

### 建模思维的转变

从关系型数据库转到文档数据库，最大的思维转变在于：**不再以"规范化"为目标，而是以"查询模式"为导向**。

在关系型数据库中，我们追求第三范式（3NF），尽量消除数据冗余。但在文档数据库中，**适度的数据冗余是被鼓励的**——只要它能减少查询次数、提升读取性能。

建模的核心问题变成了：**这个数据最常被怎么查询？** 如果两种数据总是一起被访问，就应该存储在一起（嵌入）；如果它们有独立的生命周期或被独立访问，就应该分开存储（引用）。

### 一对多关系建模

一对多关系是文档建模中最常见的场景，也是嵌入 vs 引用决策最典型的案例。关键在于判断"多"端的**基数（Cardinality）**：

- **一对少（One-to-Few）**：如用户的收货地址（通常 1-5 个）→ 嵌入
- **一对多（One-to-Many）**：如用户的订单（可能数百个）→ 取决于查询模式
- **一对巨量（One-to-Squillions）**：如主机的日志记录（可能数百万条）→ 必须引用

MongoDB 文档的最大限制是 **16MB**。当嵌入数据可能导致文档超过这个限制时，必须使用引用模式。


## 📚 聚合管道

### 聚合框架的设计思想

MongoDB 的聚合管道（Aggregation Pipeline）采用了 **Unix 管道**的设计思想：数据流经一系列阶段（Stage），每个阶段对数据进行一种变换，前一个阶段的输出是后一个阶段的输入。

这种设计的优势在于**可组合性**——复杂的数据处理可以分解为多个简单的步骤。就像 Unix 命令行中 `cat file | grep pattern | sort | head` 一样，每个步骤只负责一件事。

聚合管道中最常用的阶段按功能分为三类：

- **过滤类**：`$match`（相当于 WHERE）、`$limit`、`$skip`
- **变换类**：`$group`（相当于 GROUP BY）、`$project`（相当于 SELECT）、`$unwind`（展开数组）
- **关联类**：`$lookup`（相当于 LEFT JOIN）、`$graphLookup`（递归关联）

性能优化的黄金法则是：**尽早过滤数据**。将 `$match` 和 `$limit` 放在管道最前面，可以大幅减少后续阶段需要处理的数据量，并且允许 MongoDB 使用索引。

### 基本聚合操作

```js
// 聚合管道示例
const aggregationPipeline = [
  // 1. 匹配阶段（过滤文档）
  {
    $match: {
      status: "completed",
      createdAt: {
        $gte: new Date("2025-01-01"),
        $lt: new Date("2025-02-01")
      }
    }
  },
  // 2. 分组阶段
  {
    $group: {
      _id: "$userId",
      totalOrders: { $sum: 1 },
      totalAmount: { $sum: "$totalAmount" },
      avgOrderValue: { $avg: "$totalAmount" }
    }
  },
  // 3. 排序阶段
  {
    $sort: {
      totalAmount: -1
    }
  },
  // 4. 限制结果
  {
    $limit: 10
  },
  // 5. 查找关联数据
  {
    $lookup: {
      from: "users",
      localField: "_id",
      foreignField: "_id",
      as: "userInfo"
    }
  },
  // 6. 展开数组
  {
    $unwind: "$userInfo"
  },
  // 7. 投影字段
  {
    $project: {
      username: "$userInfo.username",
      email: "$userInfo.email",
      totalOrders: 1,
      totalAmount: 1,
      avgOrderValue: 1
    }
  }
]

// 聚合最佳实践
const aggregationBestPractices = {
  matchEarly: "尽早使用 $match 过滤数据，减少处理量",
  limitEarly: "尽早使用 $limit 限制结果集",
  useIndexes: "确保 $match 和 $sort 使用索引",
  avoidUnnecessaryStages: "移除不必要的聚合阶段",
  monitorPerformance: "使用 explain() 分析聚合性能"
}
```
