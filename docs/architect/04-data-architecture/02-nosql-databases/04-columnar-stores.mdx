# 列式存储

> **版本**：v1.1
> **最后更新**：2026-04-27

## 📖 概述

列式存储是数据库存储引擎的一种根本性不同的设计选择。传统的行式存储将一行数据的所有列连续存放，而列式存储则将**同一列的所有值连续存放**。

这个看似简单的存储顺序差异，带来了截然不同的性能特征，也决定了两者分别适用于完全不同的工作负载。理解这一原理，是理解大数据分析领域（OLAP）和时序数据库设计的基础。

### 核心原理：数据访问模式决定存储方式

数据库性能优化的第一原则是：**让磁盘 I/O 尽可能少**。而磁盘 I/O 的效率取决于数据的访问模式：

- **OLTP（在线事务处理）**：典型操作是"读取或更新某一行的所有列"，如 `SELECT * FROM users WHERE id = 123`。行式存储将一行数据连续存放，一次磁盘读取就能获取完整行，非常高效
- **OLAP（在线分析处理）**：典型操作是"对某一列的所有值做聚合"，如 `SELECT AVG(salary) FROM employees`。如果使用行式存储，需要把每一行都读出来但只用其中一个字段，浪费了大量 I/O。而列式存储只需要读取 `salary` 这一列的数据，I/O 量大幅减少

此外，列式存储还有一个显著的优势：**压缩率极高**。同一列的数据类型相同、取值范围相近，非常适合压缩。例如，"性别"列只有"男/女"两个值，可以用 1 bit 表示；"年龄"列的取值范围通常在 0-120 之间，可以用 Delta 编码大幅压缩。

## 📚 列式存储 vs 行式存储

### 存储架构对比

```js
// 行式存储示例
const rowStorage = {
  description: "同一行的数据存储在一起",
  structure: `
Row 1: [id:1, name:Alice, age:25, city:NYC]
Row 2: [id:2, name:Bob, age:30, city:LA]
Row 3: [id:3, name:Charlie, age:35, city:Chicago]
  `,
  advantages: [
    "适合事务处理（OLTP）",
    "单行查询高效",
    "插入和更新性能好"
  ],
  disadvantages: [
    "分析查询需要读取整列",
    "压缩率较低"
  ]
}

// 列式存储示例
const columnStorage = {
  description: "同一列的数据存储在一起",
  structure: `
id:   [1, 2, 3]
name: [Alice, Bob, Charlie]
age:  [25, 30, 35]
city: [NYC, LA, Chicago]
  `,
  advantages: [
    "适合分析查询（OLAP）",
    "只读取需要的列",
    "压缩率高（同列数据相似）",
    "聚合查询高效"
  ],
  disadvantages: [
    "单行查询性能差",
    "插入和更新开销大"
  ]
}
```

### 适用场景对比

| 特性 | 行式存储 | 列式存储 |
|------|---------|---------|
| 典型场景 | OLTP（事务处理） | OLAP（数据分析） |
| 查询类型 | 单行查询、小范围查询 | 聚合分析、报表查询 |
| 写入性能 | 高 | 中 |
| 读取性能 | 单行快、聚合慢 | 单行慢、聚合快 |
| 压缩率 | 低 | 高（可达 70%+） |
| 代表产品 | MySQL、PostgreSQL | HBase、Cassandra、ClickHouse |

## 📚 宽列存储

### 宽列模型的设计思想

需要注意的是，"宽列存储"（Wide Column Store）和"列式存储"（Columnar Store）虽然名字相似，但**概念不完全相同**：

- **列式存储**（如 ClickHouse、Parquet）：按列连续存储，专注于分析查询的高效扫描和压缩
- **宽列存储**（如 HBase、Cassandra）：数据按"列族"组织，同一列族的数据存储在一起。它更像是一种灵活的、可以动态添加列的键值存储

宽列存储的核心优势在于：**每一行可以有不同的列**。不需要像关系型数据库那样预先定义所有的列，可以在运行时动态添加。这种特性特别适合稀疏数据（大部分行只有少量列有值）和半结构化数据。

### HBase 架构

HBase 是 Google Bigtable 的开源实现，建立在 Hadoop HDFS 之上。它的设计目标是在廉价的商用硬件上实现**海量数据（PB 级）的随机、实时读写**。

HBase 的架构采用 **Master-Slave** 模式，但与传统主从不同的是，Master 节点不参与数据的读写，只负责元数据管理和负载均衡。真正的数据读写由 RegionServer 处理，这使得 Master 不会成为性能瓶颈。

HBase 的写入流程体现了 **LSM-Tree（Log-Structured Merge-Tree）** 的设计思想：写入先进入内存中的 MemStore，当 MemStore 满了之后刷写到磁盘形成 HFile。后台定期合并（Compaction）多个 HFile。这种"先写内存、后台合并"的策略使得写入性能极高。

### Cassandra 架构

Cassandra 的设计融合了 Amazon DynamoDB 的分布式架构和 Google Bigtable 的数据模型，但它做了一个关键的不同选择：**完全去中心化**。

与 HBase 的 Master-Slave 架构不同，Cassandra 中所有节点地位平等（Peer-to-Peer），没有单点故障。节点之间通过 **Gossip 协议**交换状态信息——每个节点定期随机选择几个节点交换自己知道的集群状态，信息像"八卦"一样在集群中扩散，最终所有节点达成一致。

Cassandra 最独特的特性是**可调一致性（Tunable Consistency）**：每次读写操作都可以独立指定一致性级别。例如，写入时要求 `QUORUM`（多数节点确认），读取时要求 `ONE`（任一节点即可）。通过合理搭配读写一致性级别，可以在一致性和性能之间找到最佳平衡点。

特别地，当 `W + R > N`（W 是写入确认节点数，R 是读取确认节点数，N 是副本总数）时，可以保证**强一致性**——因为读取的节点集合和写入的节点集合必然有交集。


## 📚 时序数据库

### 为什么需要专门的时序数据库？

时序数据（Time Series Data）是按时间顺序排列的数据点序列，如服务器的 CPU 使用率、股票价格、温度传感器的读数等。虽然通用数据库也能存储时序数据，但专用时序数据库能提供数量级的性能优势，原因在于时序数据有非常独特的特征：

1. **写入是追加式的**：新数据总是"追加"到最近的时间点之后，很少更新或删除历史数据。这意味着存储引擎可以针对顺序写入做极致优化
2. **查询总是带时间范围的**：几乎所有查询都包含时间范围条件（如"最近 1 小时"、"昨天"）。存储引擎可以按时间分区，快速定位到目标时间段
3. **数据量巨大但价值衰减**：原始数据的价值随时间递减——你可能需要秒级精度的最近 1 小时数据，但 1 年前的数据只需要天级精度。时序数据库通过**降采样（Downsampling）** 和**保留策略（Retention Policy）** 自动管理数据生命周期
4. **高压缩率**：连续的时序数据点之间的差值通常很小，可以使用 Delta 编码、XOR 编码等算法实现极高的压缩率（通常 10:1 以上）

### InfluxDB 设计原理

InfluxDB 是目前最流行的开源时序数据库之一。它的存储引擎 **TSM（Time-Structured Merge Tree）** 是 LSM-Tree 在时序场景下的变体，针对时序数据的"追加写入 + 时间范围查询"模式做了深度优化。

InfluxDB 的数据模型设计也很有特色——它区分了**标签（Tags）** 和**字段（Fields）**。标签会被索引，用于快速过滤和分组（如 `host=server1`）；字段不会被索引，存储实际的测量值（如 `cpu_usage=75.5`）。这种设计避免了对所有数据都建索引的开销，同时保证了常见查询模式的高效。

### TDengine 设计原理

TDengine 是一款国产的高性能时序数据库，它的独特设计理念是**"一个设备一张表"**。在传统方案中，所有设备的数据通常写入同一张大表；而 TDengine 为每个数据采集点（如每个传感器）自动创建一张独立的子表，所有同类型设备的子表由一个"超级表"统一管理。

这种设计的优势在于：
- 每个子表的数据天然按时间排序，写入和查询都非常高效
- 超级表提供统一的查询入口，通过标签（如设备类型、区域）可以灵活地对多个子表进行聚合查询
- 避免了传统"大宽表"方案中数据倾斜和热点问题
