# 键值存储

> **版本**：v1.1
> **最后更新**：2026-04-27

## 📖 概述

键值存储（Key-Value Store）是最简单也最高效的 NoSQL 数据模型——每条数据由一个唯一的 **Key** 和对应的 **Value** 组成，所有操作本质上都是 `GET(key)` 和 `SET(key, value)`。

这种极简的数据模型带来了极致的性能。以 Redis 为例，它将所有数据存储在内存中，单线程模型避免了锁竞争的开销，单实例可以达到 **10 万+ QPS** 的读写性能。

但"简单"不等于"简陋"。Redis 成功的关键在于它在简单的键值接口之上，提供了丰富的数据结构——不只是存储字符串，还能存储哈希表、列表、集合、有序集合等结构化数据。这使得 Redis 远远超越了"缓存"的定位，成为了一个通用的**内存数据结构服务器**。

### 单线程模型的设计哲学

Redis 选择单线程模型（Redis 6.0 之前核心处理是单线程），这看似反直觉，但背后有深刻的工程考量：

1. **瓶颈不在 CPU**：Redis 的性能瓶颈在于内存和网络 I/O，而不是 CPU 计算。单线程足以充分利用内存带宽
2. **避免锁的开销**：多线程需要加锁来保护共享数据结构，锁的获取和释放本身就有开销，而且可能引入死锁等复杂问题
3. **I/O 多路复用**：Redis 使用 epoll/kqueue 等 I/O 多路复用技术，单线程就能同时处理数万个客户端连接
4. **原子性保证**：单线程天然保证了每个命令的原子性，不需要额外的事务机制

Redis 6.0 引入了多线程 I/O（用于网络数据的读写），但命令执行仍然是单线程的。这是一个精妙的折中——在保持简单性的同时，提升了网络 I/O 密集场景的性能。

## 📚 Redis 核心数据结构

### 数据结构的选择原则

Redis 提供五种基础数据结构，选择哪一种取决于你的**操作语义**而非数据本身的形态。核心问题是：**你需要对数据执行什么样的操作？**

- 需要原子递增？→ String 的 INCR
- 需要存取对象的某个字段而不是整个对象？→ Hash
- 需要维护一个先进先出的队列？→ List
- 需要判断某元素是否存在于集合中？→ Set
- 需要按分数排序并获取 Top N？→ Sorted Set

### 数据结构应用示例

```js
// 1. String - 分布式锁实现
const distributedLock = {
  acquire: async (key, ttl) => {
    const result = await redis.set(
      key,
      'locked',
      'PX', ttl,
      'NX'
    )
    return result === 'OK'
  },
  release: async (key) => {
    await redis.del(key)
  }
}

// 2. Hash - 购物车实现
const shoppingCart = {
  addItem: async (userId, productId, quantity) => {
    await redis.hincrby(`cart:${userId}`, productId, quantity)
  },
  getCart: async (userId) => {
    return await redis.hgetall(`cart:${userId}`)
  },
  removeItem: async (userId, productId) => {
    await redis.hdel(`cart:${userId}`, productId)
  }
}

// 3. Sorted Set - 排行榜实现
const leaderboard = {
  addScore: async (userId, score) => {
    await redis.zadd('leaderboard', score, userId)
  },
  getTopN: async (n) => {
    return await redis.zrevrange('leaderboard', 0, n - 1, 'WITHSCORES')
  },
  getRank: async (userId) => {
    return await redis.zrevrank('leaderboard', userId)
  }
}
```

## 📚 持久化机制

### 持久化的两难困境

Redis 将数据存储在内存中，这带来了极快的读写速度，但内存是**易失性**的——一旦进程退出或服务器宕机，数据就会丢失。持久化机制就是要解决这个矛盾：**如何在保持内存速度的同时，确保数据不丢失？**

Redis 提供了两种截然不同的持久化策略，它们代表了两种经典的数据持久化思路：

- **RDB（快照）**：定期把内存中的数据"拍一张照片"保存到磁盘。类比：每隔一段时间给整个房间拍一张全景照片
- **AOF（日志）**：记录每一次写操作命令。类比：用摄像机持续录像，记录房间里发生的每一个动作

两者各有优劣，实际生产环境中通常**同时开启**，取长补短。

```js
// RDB 持久化机制
const rdbPersistence = {
```

## 📚 集群方案

### 集群方案的演进

Redis 的集群方案经历了一个清晰的**演进过程**，每一步都是为了解决上一步的不足：

```
主从复制（解决数据备份和读扩展）
    ↓ 问题：主节点故障需要手动切换
哨兵模式（解决自动故障转移）
    ↓ 问题：单主节点的写入和存储容量有上限
Redis Cluster（解决水平扩展）
```

理解这个演进脉络，比孤立地记忆每种方案的配置参数更有价值。

### 主从复制

```js

    "主库将后续写命令发送给从库"
  ],
  advantages: [
    "数据备份",
    "读写分离，提升读性能",
    "故障恢复"
  ],
  disadvantages: [
    "主库故障需要手动切换",
    "主库压力仍然较大"

}
```

### 哨兵（Sentinel）

主从复制解决了数据备份和读扩展的问题，但没有解决**高可用性**问题——当主节点故障时，需要人工介入来选举新的主节点并更新客户端配置。在要求 7×24 小时可用的生产环境中，这是不可接受的。

哨兵模式引入了一组独立的**监控进程**，它们负责自动检测主节点故障并执行故障转移（Failover）。其核心算法借鉴了分布式系统中的 **Raft 选举**思想——多个哨兵通过投票达成共识来决定是否执行故障转移以及选举哪个从节点为新的主节点。

```js

const sentinelArchitecture = {
  description: "自动故障转移的高可用方案",

    "自动故障检测和转移",
    "配置提供者"
  ],
  workflow: [
    "Sentinel 监控主从节点",
    "主节点故障时投票选举新主节点",
    "通知客户端新的主节点地址"
  ],
  advantages: [
    "自动故障转移",
    "高可用性",
    "监控和通知"
  ],
  config: {
    sentinel_monitor: "mymaster master_ip 6379 2",
    sentinel_down_after_milliseconds: "mymaster 30000",
    sentinel_failover_timeout: "mymaster 180000"
  }
}
```

### Redis Cluster

主从 + 哨兵解决了高可用问题，但整个集群仍然只有一个主节点承担所有写入。当写入 QPS 或数据量超过单节点的极限时，就需要**数据分片（Sharding）**。

Redis Cluster 采用**去中心化的分片架构**——没有中心协调节点，所有节点通过 Gossip 协议交换状态信息。它将所有数据划分到 **16384 个哈希槽（Hash Slot）** 中，每个节点负责一部分槽。客户端通过 `CRC16(key) % 16384` 计算出 key 应该落在哪个槽，从而路由到对应的节点。

为什么是 16384 个槽？这是一个工程上的权衡——槽太少会导致数据分布不均，槽太多会增加节点间交换状态信息的开销。16384 个槽在实践中被证明是一个很好的平衡点。

```js
// Redis Cluster 架构
const redisCluster = {
  description: "分布式集群，支持数据分片",
  features: [
    "16384 个哈希槽",
    "自动分片",
    "高可用性",
    "自动故障转移"
  ],
  slotAllocation: {
    description: "每个节点负责一部分槽",
    formula: "CRC16(key) % 16384"
  },
  advantages: [
    "水平扩展",
    "高可用性",
    "自动故障转移"
  ],
  disadvantages: [
    "不支持多键操作（除非键在同一槽）",
    "事务支持有限",
    "客户端需要支持集群模式"
  ],
  config: {
    cluster_enabled: "yes",
    cluster_config_file: "nodes.conf",
    cluster_node_timeout: "15000"
  }
}
```

## 📝 实际应用示例

### 高并发缓存方案

在高并发场景中使用 Redis 作为缓存层，最核心的挑战不是"怎么用 Redis"，而是**当缓存失效时如何保护后端数据库**。业界总结了三种经典的缓存失效场景，也被称为"缓存三大问题"：

- **缓存穿透（Cache Penetration）**：查询一个**根本不存在**的数据，缓存和数据库中都没有，每次请求都会打到数据库。常见于恶意攻击
- **缓存击穿（Cache Breakdown）**：某个**热点 key 过期**的瞬间，大量并发请求同时打到数据库。就像大坝上的一个缺口
- **缓存雪崩（Cache Avalanche）**：大量 key **同时过期**，导致海量请求同时涌入数据库。就像整个大坝同时崩溃

理解这三个问题的区别和各自的解决思路，是设计生产级缓存方案的基础：

```js
// 缓存穿透、击穿、雪崩防护
const cacheProtection = {
  // 缓存穿透：查询不存在的数据
  cachePenetration: {
    solution: [
      "布隆过滤器预判",
      "缓存空值（设置较短过期时间）"
    ],
    code: `
const getWithBloomFilter = async (key) => {
  // 1. 布隆过滤器判断
  if (!bloomFilter.mightContain(key)) {
    return null
  }
  
  // 2. 查询缓存
  let value = await redis.get(key)
  if (value !== null) {
    return value === 'NULL' ? null : JSON.parse(value)
  }
  
  // 3. 查询数据库
  value = await db.query(key)
  
  // 4. 缓存结果（包括空值）
  await redis.setex(
    key,
    value ? 3600 : 60,
    value ? JSON.stringify(value) : 'NULL'
  )
  
  return value
}
    `
  },
  
  // 缓存击穿：热点 key 过期
  cacheBreakdown: {
    solution: [
      "互斥锁",
      "逻辑过期（不设置过期时间）"
    ],
    code: `
const getWithLock = async (key) => {
  // 1. 查询缓存
  let value = await redis.get(key)
  if (value !== null) {
    return JSON.parse(value)
  }
  
  // 2. 获取锁
  const lockKey = \`lock:\${key}\`
  const lockAcquired = await redis.set(lockKey, '1', 'PX', 10000, 'NX')
  
  if (lockAcquired) {
    try {
      // 3. 双重检查
      value = await redis.get(key)
      if (value !== null) {
        return JSON.parse(value)
      }
      
      // 4. 查询数据库
      value = await db.query(key)
      
      // 5. 设置缓存
      await redis.setex(key, 3600, JSON.stringify(value))
      
      return value
    } finally {
      await redis.del(lockKey)
    }
  } else {
    // 6. 等待并重试
    await sleep(100)
    return getWithLock(key)
  }
}
    `
  },
  
  // 缓存雪崩：大量 key 同时过期
  cacheAvalanche: {
    solution: [
      "随机过期时间",
      "缓存预热",
      "高可用集群"
    ],
    code: `
const setWithRandomExpire = async (key, value) => {
  // 随机过期时间：基础时间 + 随机时间
  const baseExpire = 3600
  const randomExpire = Math.floor(Math.random() * 600)
  await redis.setex(key, baseExpire + randomExpire, JSON.stringify(value))
}
    `
  }
}
```

### 分布式限流

```js
// 令牌桶限流算法
const rateLimiter = {
  acquire: async (key, capacity, rate) => {
    const now = Date.now()
    const pipe = redis.pipeline()
    
    // 1. 获取当前令牌数和上次更新时间
    pipe.hget(key, 'tokens')
    pipe.hget(key, 'last_refill')
    
    const [tokens, lastRefill] = await pipe.exec()
    
    let currentTokens = parseInt(tokens) || capacity
    const lastRefillTime = parseInt(lastRefill) || now
    const elapsed = (now - lastRefillTime) / 1000
    
    // 2. 补充令牌
    currentTokens = Math.min(capacity, currentTokens + elapsed * rate)
    
    // 3. 检查是否有足够令牌
    if (currentTokens >= 1) {
      currentTokens -= 1
      
      // 4. 更新令牌数和时间
      await redis.hmset(key, {
        tokens: currentTokens,
        last_refill: now
      })
      
      return true
    }
    
    return false
  }
}
```
