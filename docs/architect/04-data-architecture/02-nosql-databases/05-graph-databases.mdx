# 图数据库

> **版本**：v1.1
> **最后更新**：2026-04-27

## 📖 概述

图数据库是 NoSQL 家族中最"学术"的一类——它直接基于**图论（Graph Theory）** 这一数学分支来组织和查询数据。

在现实世界中，很多数据天然就是"图"的形态：社交网络中的人际关系、知识图谱中的实体关联、物流网络中的路线规划……这些数据用关系型数据库的"表和 JOIN"来表达不仅不自然，而且在多跳查询（如"朋友的朋友的朋友"）时性能急剧下降。

图数据库的核心价值在于：**关系是一等公民**。在关系型数据库中，关系通过外键和 JOIN 操作"临时"建立；而在图数据库中，关系作为独立的数据实体直接存储，遍历关系的时间复杂度与数据总量无关，只与遍历的深度有关。

### 图数据库 vs 关系型数据库的性能差异

为什么图数据库在关系查询上比关系型数据库快？关键在于**索引无关邻接（Index-Free Adjacency）**：

- **关系型数据库**：要找"Alice 的朋友"，需要在 `friendships` 表中做一次索引查找。要找"Alice 的朋友的朋友"，需要做两次 JOIN，每次都要走索引。随着跳数增加，JOIN 次数线性增长，每次 JOIN 的开销取决于表的大小
- **图数据库**：每个节点直接持有指向其邻居节点的指针。要找"Alice 的朋友"，直接沿指针访问即可，不需要任何索引查找。遍历的时间复杂度是 **O(k)**（k 是邻居数量），与图的总节点数无关

这意味着在百万节点的图中做 3-5 跳的关系遍历，图数据库可以在毫秒级完成，而关系型数据库可能需要数秒甚至更久。

### 图数据库 vs 关系型数据库：深入对比

理解两者的差异，最好的方式是看一个具体的例子。假设要查询"Alice 的三度好友"（朋友的朋友的朋友）：

**关系型数据库的做法**：
```sql
SELECT DISTINCT f3.name
FROM users u
JOIN friendships f1 ON u.id = f1.user_id
JOIN friendships f2 ON f1.friend_id = f2.user_id
JOIN friendships f3_rel ON f2.friend_id = f3_rel.user_id
JOIN users f3 ON f3_rel.friend_id = f3.id
WHERE u.name = 'Alice';
```

这条查询需要 4 次 JOIN，每次 JOIN 都可能触发索引查找和嵌套循环。当用户表有 100 万行、友谊表有 1000 万行时，性能会急剧下降。

**图数据库的做法**：
```cypher
MATCH (u:User {name: 'Alice'})-[:FRIENDS*3]->(f)
RETURN DISTINCT f.name
```

这条查询直接沿着关系指针遍历 3 跳，不需要任何 JOIN 或索引查找。无论图有多大，性能只取决于遍历路径上的节点数量。

## 📚 Neo4j 与 Cypher

### Cypher 查询语言的设计哲学

Cypher 是 Neo4j 的声明式查询语言，其设计灵感来自 SQL，但用一种更直观的方式表达图模式——**ASCII Art**。

核心语法模拟了图的可视化表达：
- 节点用圆括号表示：`(alice:User {name: 'Alice'})`
- 关系用箭头和方括号表示：`-[:FRIENDS]->`
- 路径就是节点和关系的串联：`(a)-[:FRIENDS]->(b)-[:WORKS_FOR]->(c)`

这种设计使得 Cypher 查询几乎是"所见即所得"的——你在代码中画出的模式，就是你要在图中匹配的模式。对于理解和维护复杂的图查询来说，这是一个巨大的优势。

### Cypher 查询语言

```cypher
-- Cypher 基本语法示例

-- 1. 创建节点
CREATE (p:Person {name: 'Alice', age: 30})
CREATE (c:Company {name: 'TechCorp', founded: 2010})

-- 2. 创建关系
MATCH (p:Person {name: 'Alice'})
MATCH (c:Company {name: 'TechCorp'})
CREATE (p)-[:WORKS_FOR {since: 2020, position: 'Engineer'}]->(c)

-- 3. 查询节点
MATCH (p:Person)
WHERE p.age > 25
RETURN p.name, p.age
ORDER BY p.age DESC
LIMIT 10

-- 4. 查询关系和路径
MATCH path = (p1:Person)-[:FRIENDS]->(p2:Person)
WHERE p1.name = 'Alice'
RETURN path

-- 5. 多跳查询（朋友的朋友）
MATCH (p:Person {name: 'Alice'})-[:FRIENDS]->(friend)-[:FRIENDS]->(fof)
RETURN fof.name

-- 6. 最短路径
MATCH (start:Person {name: 'Alice'}), (end:Person {name: 'Bob'})
MATCH path = shortestPath((start)-[*]-(end))
RETURN path

-- 7. 聚合查询
MATCH (p:Person)-[:WORKS_FOR]->(c:Company)
RETURN c.name, count(p) as employee_count
ORDER BY employee_count DESC
```

## 📚 图建模最佳实践

### 图建模的核心原则

图建模与关系型数据库建模有本质的不同。关系型建模追求的是**规范化和去冗余**，而图建模追求的是**查询模式的高效表达**。

图建模的三条核心原则：

1. **关系即数据**：不要把重要的关系信息隐藏在节点属性中。例如，"Alice 在 2020 年加入 TechCorp"中的"加入"应该建模为一条关系 `[:WORKS_FOR {since: 2020}]`，而不是在 Alice 节点中放一个 `company: 'TechCorp'` 属性
2. **为查询而建模**：先确定最重要的查询模式，再设计图结构。如果最常见的查询是"找到所有在同一公司工作过的人"，那么 `Person -[:WORKS_FOR]-> Company` 的模型比 `Person -[:COLLEAGUE_OF]-> Person` 更合适（因为前者可以通过公司节点自动推导出同事关系）
3. **避免超级节点**：如果一个节点有百万级的关系（如"中国"节点连接了十几亿"居民"），会导致遍历该节点时性能急剧下降。可以通过引入中间层（如"省份"、"城市"）来分散关系

### 社交网络建模

```cypher
-- 社交网络数据模型

-- 创建用户节点
CREATE (alice:User {id: 'user1', name: 'Alice', age: 30})
CREATE (bob:User {id: 'user2', name: 'Bob', age: 25})
CREATE (charlie:User {id: 'user3', name: 'Charlie', age: 35})

-- 创建关注关系
CREATE (alice)-[:FOLLOWS {since: datetime('2025-01-01')}]->(bob)
CREATE (bob)-[:FOLLOWS {since: datetime('2025-02-01')}]->(alice)
CREATE (alice)-[:FOLLOWS {since: datetime('2025-03-01')}]->(charlie)

-- 创建帖子节点
CREATE (post1:Post {id: 'post1', content: 'Hello World!', createdAt: datetime('2025-04-20')})
CREATE (post2:Post {id: 'post2', content: 'Graph databases are awesome!', createdAt: datetime('2025-04-21')})

-- 创建发布关系
CREATE (alice)-[:POSTED]->(post1)
CREATE (bob)-[:POSTED]->(post2)

-- 创建点赞关系
CREATE (bob)-[:LIKED {at: datetime('2025-04-20')}]->(post1)
CREATE (charlie)-[:LIKED {at: datetime('2025-04-20')}]->(post1)
CREATE (alice)-[:LIKED {at: datetime('2025-04-21')}]->(post2)
```

### 推荐系统建模

图数据库天然适合推荐系统，因为推荐的本质就是**在图中寻找相似路径**。基于协同过滤的推荐可以简洁地表达为图遍历模式：

- **用户推荐**：`(我)-[:关注]->(我关注的人)-[:关注]->(推荐的人)`——推荐"我关注的人也关注了"的用户
- **商品推荐**：`(我)-[:购买]->(我买过的商品)<-[:购买]-(其他买家)-[:购买]->(推荐的商品)`——推荐"买了同样商品的人还买了"的商品

这种推荐逻辑用 SQL 表达需要多层嵌套 JOIN，但用 Cypher 只需一行模式匹配：

```cypher
-- 推荐系统：基于协同过滤

-- 查询共同好友
MATCH (u1:User {name: 'Alice'})-[:FRIENDS]->(common)-[:FRIENDS]->(u2:User)
WHERE u1 <> u2
RETURN u2.name, count(common) as mutual_friends
ORDER BY mutual_friends DESC
LIMIT 10

-- 查询推荐关注（好友的好友）
MATCH (u:User {name: 'Alice'})-[:FRIENDS]->(friend)-[:FRIENDS]->(recommendation)
WHERE NOT (u)-[:FRIENDS]->(recommendation) AND u <> recommendation
RETURN recommendation.name, count(friend) as common_friends
ORDER BY common_friends DESC
LIMIT 10

-- 商品推荐（基于购买行为）
MATCH (u:User {name: 'Alice'})-[:PURCHASED]->(:Product)-[:PURCHASED]->(other:Product)
WHERE NOT (u)-[:PURCHASED]->(other)
RETURN other.name, count(*) as purchase_count
ORDER BY purchase_count DESC
LIMIT 10
```

### 知识图谱建模

知识图谱（Knowledge Graph）是图数据库最典型的应用场景之一。它将现实世界的知识表示为**三元组（Subject-Predicate-Object）**：

- `(Elon Musk) -[:FOUNDED]-> (Tesla)`
- `(Tesla) -[:HEADQUARTERED_IN]-> (Austin)`
- `(Austin) -[:LOCATED_IN]-> (Texas)`

通过这种方式，零散的知识被组织成一个可查询的网络。知识图谱的核心价值在于**推理能力**——通过图遍历可以发现隐含的关系。例如，从上面三条关系可以推导出"Elon Musk 与 Texas 有关联"，尽管我们从未显式地建立这个关系。

Google 的搜索引擎、阿里巴巴的商品知识图谱、金融行业的风控知识图谱，都是知识图谱的大规模应用。

```cypher
-- 知识图谱示例

-- 创建实体
CREATE (person1:Person {name: 'Elon Musk'})
CREATE (company1:Company {name: 'Tesla'})
CREATE (company2:Company {name: 'SpaceX'})
CREATE (company3:Company {name: 'Twitter'})

-- 创建关系
CREATE (person1)-[:FOUNDED {year: 2003}]->(company1)
CREATE (person1)-[:FOUNDED {year: 2002}]->(company2)
CREATE (person1)-[:ACQUIRED {year: 2022}]->(company3)

-- 查询某人的所有公司
MATCH (p:Person {name: 'Elon Musk'})-[r]->(c:Company)
RETURN c.name, type(r) as relationship, r.year

-- 查询公司间的关联
MATCH (c1:Company)<-[:FOUNDED]-(p:Person)-[:FOUNDED]->(c2:Company)
WHERE c1.name = 'Tesla'
RETURN c2.name
```

## 📝 实际应用示例

### 欺诈检测

图数据库在金融欺诈检测中有独特的优势。传统的欺诈检测基于规则或机器学习，分析的是单个用户或单笔交易的特征。但很多欺诈行为——如洗钱、团伙欺诈——的特征不在于单个节点，而在于**节点之间的关系模式**。

例如，循环转账（A → B → C → A）是洗钱的典型模式，在关系型数据库中检测这种模式需要多层自连接 JOIN，非常复杂且低效。但在图数据库中，这只是一个简单的环路检测查询。

```cypher
-- 欺诈检测场景：检测异常交易模式

-- 1. 检测循环转账（洗钱模式）
MATCH (a:Account)-[t1:TRANSFERRED]->(b:Account)-[t2:TRANSFERRED]->(c:Account)-[t3:TRANSFERRED]->(a)
WHERE t1.amount = t2.amount AND t2.amount = t3.amount
RETURN a, b, c, t1.amount as suspicious_amount

-- 2. 检测短时间内的多笔大额交易
MATCH (a:Account)-[t:TRANSFERRED]->(:Account)
WHERE t.amount > 10000
WITH a, count(t) as large_transactions, sum(t.amount) as total_amount
WHERE large_transactions > 5
RETURN a.id, large_transactions, total_amount

-- 3. 检测共享账户（多个账户使用同一设备）
MATCH (d:Device)<-[:USED]-(a1:Account)
MATCH (d)<-[:USED]-(a2:Account)
WHERE a1 <> a2
RETURN d.id, collect(DISTINCT a1.id) as accounts
WHERE size(accounts) > 5
```

### 路径规划

```cypher
-- 路径规划场景：查找最短路线

-- 创建地点和道路
CREATE (a:Location {name: 'A'})
CREATE (b:Location {name: 'B'})
CREATE (c:Location {name: 'C'})
CREATE (d:Location {name: 'D'})

CREATE (a)-[:ROAD {distance: 10}]->(b)
CREATE (b)-[:ROAD {distance: 15}]->(c)
CREATE (c)-[:ROAD {distance: 20}]->(d)
CREATE (a)-[:ROAD {distance: 30}]->(d)

-- 查找最短路径
MATCH (start:Location {name: 'A'}), (end:Location {name: 'D'})
MATCH path = shortestPath((start)-[*]-(end))
RETURN path, reduce(total = 0, r IN relationships(path) | total + r.distance) as total_distance

-- 查找所有路径并按距离排序
MATCH (start:Location {name: 'A'}), (end:Location {name: 'D'})
MATCH path = (start)-[*]-(end)
WITH path, reduce(total = 0, r IN relationships(path) | total + r.distance) as total_distance
RETURN path, total_distance
ORDER BY total_distance
LIMIT 5
```
