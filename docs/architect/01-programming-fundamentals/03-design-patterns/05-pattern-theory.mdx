# 设计模式理论基础

> **版本**：v1.0
> **最后更新**：2026-04-27

## 📚 概念介绍

设计模式理论探讨模式的本质、分类、应用原则以及模式与架构的关系。理解设计模式的理论基础，能够帮助架构师不仅仅是"套用模式"，而是真正理解模式背后的思想，从而做出更合理的设计决策。

## 🎯 学习目标

- 理解设计模式的本质和目的
- 掌握模式分类的理论依据
- 深入理解模式的应用原则
- 了解模式与架构模式的关系
- 能够批判性地选择和使用模式

## 🔑 核心概念

### 什么是设计模式

设计模式是经过验证的、可复用的解决方案：

```
设计模式的定义：

设计模式是一套被反复使用、多数人知晓的、经过分类编目的、
代码设计经验的总结。使用设计模式是为了可重用代码、让代码更容
易被他人理解、保证代码可靠性。

—— GoF《设计模式》

设计模式的四个要素：

1. 模式名称（Pattern Name）
   - 用一两个词描述模式的问题、解决方案和效果
   - 便于交流和文档化

2. 问题（Problem）
   - 描述了何时应用模式
   - 模式的前置条件和上下文

3. 解决方案（Solution）
   - 描述设计的组成成分
   - 它们之间的相互关系及各自的职责和协作方式

4. 效果（Consequences）
   - 应用模式后的效果和权衡
   - 优点和缺点
```

### 模式的本质

模式不仅仅是代码模板，更是一种思维方式：

```
模式的三个层次：

┌─────────────────────────────────────────┐
│ 1. 代码层（Code Level）                 │
│    - 具体的实现代码                     │
│    - 可以直接复制使用                   │
│    - 最浅层的理解                       │
│                                         │
│ 2. 结构层（Structure Level）            │
│    - 类和对象的关系                     │
│    - 模式的结构图                       │
│    - 理解"怎么做"                       │
│                                         │
│ 3. 意图层（Intent Level）               │
│    - 模式要解决的问题                   │
│    - 设计思想和原则                     │
│    - 理解"为什么"                       │
└─────────────────────────────────────────┘

真正掌握模式需要达到意图层：
  - 理解模式要解决什么问题
  - 知道何时使用、何时不使用
  - 能够根据实际情况调整模式
```

## 🧠 模式分类理论

### GoF 23 种模式的分类

GoF（Gang of Four）将设计模式分为三类：

```
分类依据：模式的作用范围

┌─────────────────────────────────────────┐
│ 创建型模式（Creational）                │
│ 关注对象的创建过程                      │
│                                         │
│ 目的：                                  │
│ - 将对象的创建和使用分离                │
│ - 降低系统的耦合度                      │
│ - 提高创建的灵活性                      │
│                                         │
│ 5 种模式：                              │
│ 1. 工厂方法（Factory Method）          │
│ 2. 抽象工厂（Abstract Factory）        │
│ 3. 建造者（Builder）                   │
│ 4. 单例（Singleton）                   │
│ 5. 原型（Prototype）                   │
├─────────────────────────────────────────┤
│ 结构型模式（Structural）                │
│ 关注类和对象的组合                      │
│                                         │
│ 目的：                                  │
│ - 通过继承或组合实现更灵活的结构        │
│ - 解决类之间的兼容性问题                │
│ - 优化类的结构                          │
│                                         │
│ 7 种模式：                              │
│ 1. 适配器（Adapter）                   │
│ 2. 桥接（Bridge）                      │
│ 3. 组合（Composite）                   │
│ 4. 装饰器（Decorator）                 │
│ 5. 外观（Facade）                      │
│ 6. 代理（Proxy）                       │
│ 7. 享元（Flyweight）                   │
├─────────────────────────────────────────┤
│ 行为型模式（Behavioral）                │
│ 关注对象之间的通信和职责分配            │
│                                         │
│ 目的：                                  │
│ - 优化对象之间的通信                    │
│ - 分配职责                              │
│ - 定义算法的骨架                        │
│                                         │
│ 11 种模式：                             │
│ 1. 策略（Strategy）                    │
│ 2. 观察者（Observer）                  │
│ 3. 责任链（Chain of Responsibility）   │
│ 4. 模板方法（Template Method）          │
│ 5. 状态（State）                       │
│ 6. 命令（Command）                     │
│ 7. 迭代器（Iterator）                  │
│ 8. 中介者（Mediator）                  │
│ 9. 备忘录（Memento）                   │
│ 10. 解释器（Interpreter）               │
│ 11. 访问者（Visitor）                  │
└─────────────────────────────────────────┘
```

### 模式的粒度

模式还可以按照粒度分类：

```
按粒度分类：

┌─────────────────────────────────────────┐
│ 微型模式（Idiom）                       │
│ - 语言特定的编程技巧                    │
│ - 示例：RAII（C++）、Promise 链（JS）   │
│ - 粒度：几行代码                        │
├─────────────────────────────────────────┤
│ 小型模式（Mini Pattern）                │
│ - 解决局部问题的模式                    │
│ - 示例：空对象模式、对象池模式          │
│ - 粒度：单个类或函数                    │
├─────────────────────────────────────────┤
│ 中型模式（Design Pattern）              │
│ - GoF 23 种模式                         │
│ - 解决常见设计问题                      │
│ - 粒度：几个类之间的协作                │
├─────────────────────────────────────────┤
│ 大型模式（Architectural Pattern）       │
│ - 系统级别的架构模式                    │
│ - 示例：MVC、微服务、事件驱动           │
│ - 粒度：整个系统或子系统                │
└─────────────────────────────────────────┘
```

## 📐 模式的结构

### 模式的描述格式

一个完整的模式描述应该包含以下部分：

```
模式描述的标准格式：

1. 意图（Intent）
   - 模式要解决的问题
   - 一句话概括

2. 动机（Motivation）
   - 为什么要使用这个模式
   - 具体的应用场景

3. 适用性（Applicability）
   - 什么情况下可以使用
   - 什么情况下不应该使用

4. 结构（Structure）
   - 类图或对象图
   - 参与者及其关系

5. 参与者（Participants）
   - 模式中涉及的类/对象
   - 各自的职责

6. 协作（Collaboration）
   - 参与者如何协作
   - 时序图

7. 效果（Consequences）
   - 使用模式的优点
   - 使用模式的缺点
   - 权衡

8. 实现（Implementation）
   - 实现要点
   - 代码示例

9. 已知应用（Known Uses）
   - 现实中的应用
   - 框架和库中的使用

10. 相关模式（Related Patterns）
    - 与其他模式的关系
    - 可以组合使用的模式
```

## 🎯 模式的应用原则

### 何时使用模式

使用模式需要遵循以下原则：

```js
// 模式应用的决策框架

function shouldUsePattern(problemContext) {
  const checks = {
    // 1. 是否真的有需要解决的问题？
    hasRealProblem: problemContext.problem !== null,

    // 2. 模式是否适合这个问题？
    patternFits: problemContext.patternMatchesProblem,

    // 3. 引入模式是否值得？
    worthTheCost: problemContext.benefit > problemContext.cost,

    // 4. 团队是否理解这个模式？
    teamUnderstands: problemContext.teamKnowledge > 0.7,

    // 5. 是否有更简单的解决方案？
    simplerAlternative: problemContext.simplerSolution === null,
  };

  // 所有检查都通过才使用模式
  return Object.values(checks).every((value) => value === true);
}

// 示例：评估是否应该使用单例模式
const singletonEvaluation = {
  problem: "需要全局唯一的日志实例",
  patternMatchesProblem: true,
  benefit: 8,  // 1-10
  cost: 2,    // 1-10
  teamKnowledge: 0.9,
  simplerSolution: null, // 模块级常量更简单，所以应该是 null
};

console.log("Use Singleton?", shouldUsePattern(singletonEvaluation));
// false - 因为有更简单的解决方案（模块级常量）
```

### 模式滥用的陷阱

```
常见的模式滥用：

┌─────────────────────────────────────────┐
│ 1. 为了使用而使用                      │
│   - 没有明确的问题                      │
│   - 只是为了"看起来专业"                │
│   - 结果：增加不必要的复杂度            │
├─────────────────────────────────────────┤
│ 2. 过度设计                            │
│   - 在简单问题上使用复杂模式            │
│   - 提前优化                            │
│   - 结果：违反 YAGNI 原则               │
├─────────────────────────────────────────┤
│ 3. 死板套用                            │
│   - 不考虑上下文                        │
│   - 机械地套用模式结构                  │
│   - 结果：不适合实际情况                │
├─────────────────────────────────────────┤
│ 4. 模式堆砌                            │
│   - 在一个地方使用多个模式              │
│   - 模式之间没有协调                    │
│   - 结果：代码难以理解                  │
└─────────────────────────────────────────┘

反模式（Anti-pattern）：
  - 看起来像解决方案，但实际上会让问题恶化
  - 示例：Singleton 滥用、God Object
```

## 🔗 模式与设计原则

### 模式是原则的具体体现

设计模式是设计原则的具体实现：

```js
// 设计原则与设计模式的映射

const principleToPatternMapping = {
  // 单一职责原则（SRP）
  SRP: [
    "Strategy",      // 将不同的算法封装成独立的策略
    "Command",       // 将请求封装成独立的命令
    "State",         // 将不同的状态封装成独立的状态
  ],

  // 开闭原则（OCP）
  OCP: [
    "Factory Method",  // 通过工厂方法扩展产品
    "Decorator",       // 通过装饰器扩展功能
    "Observer",        // 通过观察者扩展监听器
  ],

  // 里氏替换原则（LSP）
  LSP: [
    "Strategy",      // 策略可以互相替换
    "Composite",     // 组合对象可以替换单个对象
  ],

  // 接口隔离原则（ISP）
  ISP: [
    "Adapter",       // 适配器隔离不兼容的接口
    "Facade",        // 外观简化接口
  ],

  // 依赖反转原则（DIP）
  DIP: [
    "Factory Method",  // 依赖工厂而非具体类
    "Abstract Factory", // 依赖抽象工厂
    "Dependency Injection", // 依赖注入（虽然不是 GoF 模式）
  ],

  // 其他原则
  DRY: ["Template Method"],  // 模板方法避免重复
  KISS: ["Facade"],          // 外观简化复杂度
  CoI: ["Composite", "Decorator"], // 组合优于继承
};

console.log("Design Patterns by Principle:");
Object.entries(principleToPatternMapping).forEach(([principle, patterns]) => {
  console.log(`\n${principle}:`);
  patterns.forEach((pattern) => console.log(`  - ${pattern}`));
});
```

### 模式组合

多个模式可以组合使用以解决复杂问题：

```js
// 模式组合示例：构建一个可观察的单例工厂

// 1. 单例模式：确保只有一个工厂实例
class NotificationFactory {
  static #instance = null;

  static getInstance() {
    if (!NotificationFactory.#instance) {
      NotificationFactory.#instance = new NotificationFactory();
    }
    return NotificationFactory.#instance;
  }

  // 2. 工厂方法模式：创建不同类型的通知
  createNotification(type) {
    switch (type) {
      case "email":
        return new EmailNotification();
      case "sms":
        return new SMSNotification();
      case "push":
        return new PushNotification();
      default:
        throw new Error(`Unknown notification type: ${type}`);
    }
  }
}

// 3. 观察者模式：通知可以被观察
class ObservableNotification {
  #observers = [];

  subscribe(observer) {
    this.#observers.push(observer);
  }

  unsubscribe(observer) {
    const index = this.#observers.indexOf(observer);
    if (index > -1) {
      this.#observers.splice(index, 1);
    }
  }

  notify(event) {
    this.#observers.forEach((observer) => observer.update(event));
  }
}

// 4. 装饰器模式：为通知添加额外功能
class NotificationDecorator extends ObservableNotification {
  constructor(wrappedNotification) {
    super();
    this.wrapped = wrappedNotification;
  }

  send(recipient, message) {
    this.wrapped.send(recipient, message);
    this.notify({ type: "sent", recipient, message });
  }
}

// 使用组合模式
const factory = NotificationFactory.getInstance();

const emailNotification = factory.createNotification("email");
const decoratedEmail = new NotificationDecorator(emailNotification);

// 订阅通知事件
decoratedEmail.subscribe({
  update: (event) => {
    console.log(`[Observer] Notification sent to ${event.recipient}`);
  },
});

// 发送通知
decoratedEmail.send("alice@example.com", "Hello!");
// [Observer] Notification sent to alice@example.com
```

## 🏗️ 模式与架构

### 代码模式 vs 架构模式

设计模式和架构模式在不同层次上解决问题：

```
模式层次对比：

┌─────────────────────────────────────────┐
│ 代码模式（Code Pattern）                │
│                                         │
│ 作用范围：单个类或几个类                │
│ 解决问题：代码级别的复用和灵活性        │
│ 示例：GoF 23 种设计模式                │
│ 关注点：对象创建、结构、交互            │
├─────────────────────────────────────────┤
│ 架构模式（Architectural Pattern）       │
│                                         │
│ 作用范围：整个系统或子系统              │
│ 解决问题：系统级别的组织和通信          │
│ 示例：MVC、微服务、事件驱动             │
│ 关注点：模块划分、通信方式、数据流      │
└─────────────────────────────────────────┘

架构模式往往是设计模式的放大：
  - 观察者模式 → 事件驱动架构
  - 代理模式 → API 网关
  - 外观模式 → BFF（Backend for Frontend）
  - 责任链模式 → 中间件管道
  - 策略模式 → 负载均衡策略
```

### 模式在微服务架构中的应用

```js
// 设计模式在微服务架构中的体现

// 1. 工厂方法模式 → 服务发现
class ServiceFactory {
  static createService(serviceName) {
    const serviceRegistry = ServiceRegistry.getInstance();
    const serviceInfo = serviceRegistry.discover(serviceName);
    return new ServiceClient(serviceInfo);
  }
}

// 2. 适配器模式 → 协议适配
class ProtocolAdapter {
  constructor(targetProtocol) {
    this.targetProtocol = targetProtocol;
  }

  adapt(request) {
    // 将请求转换为目标协议格式
    return this.transformRequest(request);
  }
}

// 3. 装饰器模式 → 中间件
class MiddlewareDecorator {
  constructor(handler) {
    this.handler = handler;
  }

  async handle(request) {
    // 前置处理
    await this.before(request);

    // 执行实际处理
    const response = await this.handler.handle(request);

    // 后置处理
    await this.after(response);

    return response;
  }
}

// 4. 观察者模式 → 事件驱动
class EventEmitter {
  #listeners = new Map();

  on(event, listener) {
    if (!this.#listeners.has(event)) {
      this.#listeners.set(event, []);
    }
    this.#listeners.get(event).push(listener);
  }

  emit(event, data) {
    const listeners = this.#listeners.get(event) || [];
    listeners.forEach((listener) => listener(data));
  }
}

// 5. 策略模式 → 负载均衡
class LoadBalancer {
  constructor(strategy) {
    this.strategy = strategy;
  }

  setStrategy(strategy) {
    this.strategy = strategy;
  }

  selectServer(servers) {
    return this.strategy.select(servers);
  }
}

class RoundRobinStrategy {
  #index = 0;

  select(servers) {
    const server = servers[this.#index];
    this.#index = (this.#index + 1) % servers.length;
    return server;
  }
}

class RandomStrategy {
  select(servers) {
    return servers[Math.floor(Math.random() * servers.length)];
  }
}

// 使用策略模式
const loadBalancer = new LoadBalancer(new RoundRobinStrategy());
const server = loadBalancer.selectServer(["s1", "s2", "s3"]);
```

### 模式评估矩阵

```js
// 模式评估矩阵

const patternMatrix = [
  {
    name: "Singleton",
    complexity: "Low",
    flexibility: "Low",
    testability: "Low",
    commonality: "High",
    useCases: ["配置管理", "日志记录", "连接池"],
  },
  {
    name: "Factory Method",
    complexity: "Medium",
    flexibility: "High",
    testability: "High",
    commonality: "High",
    useCases: ["对象创建", "框架扩展", "插件系统"],
  },
  {
    name: "Strategy",
    complexity: "Medium",
    flexibility: "Very High",
    testability: "High",
    commonality: "High",
    useCases: ["算法切换", "业务规则", "负载均衡"],
  },
  {
    name: "Observer",
    complexity: "Medium",
    flexibility: "High",
    testability: "Medium",
    commonality: "Very High",
    useCases: ["事件处理", "UI 更新", "消息通知"],
  },
];

// 根据需求选择模式
function selectPattern(requirements) {
  return patternMatrix.filter((pattern) => {
    // 检查复杂度是否满足要求
    if (requirements.maxComplexity === "Low" && pattern.complexity !== "Low") {
      return false;
    }

    // 检查灵活性是否满足要求
    if (requirements.minFlexibility === "High" && pattern.flexibility === "Low") {
      return false;
    }

    return true;
  });
}

const selected = selectPattern({
  maxComplexity: "Medium",
  minFlexibility: "High",
});

console.log("Recommended Patterns:");
selected.forEach((pattern) => {
  console.log(`\n${pattern.name}:`);
  console.log(`  Complexity: ${pattern.complexity}`);
  console.log(`  Flexibility: ${pattern.flexibility}`);
  console.log(`  Use Cases: ${pattern.useCases.join(", ")}`);
});
```
