## 🔑 核心概念

### DDD 的核心价值

DDD 不仅是一套技术模式，更是一种**将业务复杂度转化为技术架构**的思维方式：

- **战略设计**解决的是"边界在哪里"的问题 → 决定系统如何拆分
- **战术设计**解决的是"内部如何组织"的问题 → 决定代码如何结构化
- **通用语言**解决的是"团队如何沟通"的问题 → 消除业务与技术的鸿沟

### DDD 的核心原则

领域驱动设计由 Eric Evans 在 2003 年的《Domain-Driven Design: Tackling Complexity in the Heart of Software》一书中提出。其核心原则包括：

#### 1. 以领域为中心

> "将软件的核心重点放在领域本身和领域逻辑上"

**理论内涵**：
- 软件的本质是解决业务问题
- 技术是实现业务目标的手段
- 领域模型应该准确反映业务现实

**实践体现**：
- 代码结构与业务结构一致
- 业务概念直接映射为代码概念
- 技术决策服务于业务需求

#### 2. 通用语言（Ubiquitous Language）

> "领域专家和开发者使用统一的语言进行沟通"

**理论内涵**：
- 语言是思维的载体
- 统一语言消除沟通鸿沟
- 代码即语言，语言即代码

**实践体现**：
- 类名、方法名使用业务术语
- 文档、讨论使用相同术语
- 持续精炼和演进语言

#### 3. 知识精炼（Knowledge Crunching）

> "将复杂的业务知识精炼为简洁、准确的领域模型"

**理论内涵**：
- 业务知识是分散的、隐性的
- 需要通过建模过程提取和精炼
- 模型是知识的结晶

**实践体现**：
- 与领域专家深入访谈
- 通过可视化工具（UML、领域模型图）表达
- 迭代精炼模型

#### 4. 限界上下文（Bounded Context）

> "明确语言和模型的适用边界"

**理论内涵**：
- 同一概念在不同上下文中有不同含义
- 边界内语言和模型一致
- 边界间通过映射关系连接

**实践体现**：
- 按业务能力划分模块
- 每个模块有独立的领域模型
- 模块间通过接口通信

### 领域建模方法论

#### 什么是领域模型？

领域模型是对业务领域的**抽象和简化**，它捕捉了业务领域中的核心概念、关系和规则。

#### 领域建模的核心要素

| 要素 | 定义 | 示例 |
|------|------|------|
| **实体（Entity）** | 有唯一标识、可变的对象 | 订单、用户、产品 |
| **值对象（Value Object）** | 无标识、不可变的对象 | 金额、地址、日期范围 |
| **聚合（Aggregate）** | 一组相关对象的集合，作为一致性边界 | 订单聚合（订单+订单项） |
| **领域服务（Domain Service）** | 不属于任何实体的业务逻辑 | 转账服务、运费计算 |
| **领域事件（Domain Event）** | 领域中已发生的事实 | 订单已创建、支付已完成 |
| **仓储（Repository）** | 聚合的存储和检索接口 | 订单仓储、用户仓储 |

#### 领域建模的步骤

1. **理解业务领域**：
   - 与领域专家访谈
   - 收集业务需求和规则
   - 识别核心业务流程

2. **识别核心概念**：
   - 提取业务术语
   - 识别关键实体和值对象
   - 理解概念间的关系

3. **建立领域模型**：
   - 绘制领域模型图
   - 定义聚合边界
   - 明确领域规则

4. **精炼和演进**：
   - 通过实践验证模型
   - 持续精炼和改进
   - 适应业务变化

### 限界上下文与微服务

限界上下文是微服务拆分的最佳指导原则：

```
业务领域
  ├── 核心子域 → 自研、重点投入
  ├── 支撑子域 → 可外包、适度投入
  └── 通用子域 → 购买/使用开源方案
```
