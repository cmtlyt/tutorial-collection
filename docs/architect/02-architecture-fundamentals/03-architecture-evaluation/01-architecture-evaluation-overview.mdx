## 🔑 核心概念

### 软件质量模型理论基础

#### 什么是软件质量模型？

软件质量模型是**用于理解和测量软件系统质量的一组属性及其关系**。它提供了一个系统化的框架来评估软件系统的质量。

#### 经典质量模型

**1. McCall 质量模型（1977）**

McCall 模型是最早的软件质量模型之一，将质量属性分为三大类：

| 类别 | 属性 | 说明 |
|------|------|------|
| **产品运行** | 正确性 | 程序满足需求的程度 |
| | 可靠性 | 程序在规定条件下正常运行的能力 |
| | 效率 | 程序运行时资源使用的效率 |
| | 完整性 | 程序数据和访问控制的安全性 |
| | 可用性 | 用户学习和使用程序的难易程度 |
| **产品修正** | 可维护性 | 定位和修复错误的难易程度 |
| | 灵活性 | 修改程序以满足新需求的难易程度 |
| | 可测试性 | 测试程序以确保其正确性的难易程度 |
| **产品过渡** | 可移植性 | 将程序移植到新环境的难易程度 |
| | 可复用性 | 程序组件在其他程序中使用的难易程度 |
| | 互操作性 | 程序与其他系统交互的难易程度 |

**2. Boehm 质量模型（1978）**

Boehm 模型从用户和系统两个角度定义质量属性：

**用户视角**：
- 易用性（As-is utility）
- 可维护性（Maintainability）
- 可移植性（Portability）

**系统视角**：
- 可靠性（Reliability）
- 效率（Efficiency）
- 人工程性（Human engineering）

**3. ISO/IEC 9126 质量模型**

ISO/IEC 9126 是国际标准化组织发布的软件质量模型，包含六大质量特性：

1. **功能性**：软件是否满足明确和隐含需求
2. **可靠性**：软件在规定条件下和时间段内维持性能的能力
3. **易用性**：用户使用软件所需付出的努力程度
4. **效率**：软件在规定条件下使用资源的关系
5. **可维护性**：进行指定修改所需的努力
6. **可移植性**：软件从一个环境移植到另一个环境的能力

#### 现代质量模型：ISO/IEC 25010

ISO/IEC 25010 是 ISO/IEC 9126 的继任者，将质量分为两大类：

**产品质量（Product Quality）**：
1. **功能性适用性**：功能完备性、功能正确性、功能适合性
2. **性能效率**：时间特性、资源利用性、容量特性
3. **兼容性**：共存性、互操作性
4. **易用性**：易学性、易操作性、用户错误防护、易访问性、用户界面美观性
5. **可靠性**：成熟性、可用性、容错性、可恢复性
6. **安全性**：保密性、完整性、不可否认性、可问责性
7. **可维护性**：模块性、可复用性、易分析性、易修改性、易测试性
8. **可移植性**：适应性、易安装性、共存性、易替换性

**使用质量（Quality in Use）**：
1. **有效性**：用户在特定环境中达到指定目标的准确性和完整性
2. **效率性**：用户在达到目标时消耗的资源
3. **满意度**：用户在使用产品后的态度和感受
4. **无风险性**：产品对用户、业务、软件环境的风险
5. **上下文覆盖性**：产品在特定上下文中的适用范围

### 架构评估方法论

#### 什么是架构评估？

架构评估是**系统性地分析架构设计是否满足质量属性要求的过程**。它帮助识别架构中的风险、权衡和改进机会。

#### 架构评估的核心目标

1. **风险识别**：发现架构中可能导致质量问题的决策
2. **权衡分析**：理解不同质量属性之间的权衡关系
3. **决策验证**：验证架构决策是否满足业务需求
4. **持续改进**：为架构演进提供指导

#### 主要架构评估方法

**1. SAAM（Software Architecture Analysis Method）**

- **提出者**：SEI（Software Engineering Institute）
- **核心思想**：基于场景评估架构的可修改性
- **适用场景**：早期架构评估，关注可修改性

**2. ATAM（Architecture Tradeoff Analysis Method）**

- **提出者**：SEI
- **核心思想**：基于场景分析质量属性权衡
- **适用场景**：综合评估多个质量属性

**3. CBAM（Cost Benefit Analysis Method）**

- **提出者**：SEI
- **核心思想**：在 ATAM 基础上增加成本效益分析
- **适用场景**：需要考虑经济因素的项目

### 质量属性权衡分析理论

#### 权衡的本质

架构决策本质上是**在不同质量属性之间进行权衡**。没有任何架构能够在所有质量属性上都达到最优。

#### 权衡关系的类型

**1. 正相关关系**

一个质量属性的改进会同时改善另一个质量属性：

- 可维护性 ↔ 可测试性：代码结构清晰，易于维护和测试
- 可用性 ↔ 效率：良好的用户体验设计通常也考虑性能

**2. 负相关关系**

一个质量属性的改善会导致另一个质量属性的下降：

- 一致性 ↔ 可用性（CAP 定理）
- 性能 ↔ 安全性：加密操作会增加延迟
- 灵活性 ↔ 简单性：过度抽象增加复杂度

**3. 独立关系**

质量属性之间没有明显的相互影响。

#### 权衡分析的方法

**1. 敏感性分析（Sensitivity Analysis）**

分析架构决策对质量属性的敏感程度：
- 识别关键架构决策
- 评估决策变化对质量属性的影响
- 确定需要重点关注的决策点

**2. 权衡点分析（Tradeoff Point Analysis）**

识别多个质量属性相互影响的架构决策：
- 分析决策对多个质量属性的影响
- 评估权衡的合理性
- 确定最优的权衡方案

**3. 风险分析（Risk Analysis）**

评估架构决策带来的风险：
- 识别潜在的质量风险
- 评估风险的影响和概率
- 制定风险缓解策略

### 架构是权衡的艺术

每个架构决策都涉及权衡。例如：
- **一致性 vs 可用性**（CAP 定理）
- **性能 vs 可维护性**（过度优化降低可读性）
- **灵活性 vs 复杂度**（过度抽象增加认知负担）

```
# ADR-001: 选择消息队列方案

## 状态：已接受

## 背景
系统需要异步解耦订单和支付模块...

## 决策
选择 Apache Kafka 作为消息队列...

## 后果
- 正面：高吞吐、持久化、可回溯
- 负面：运维复杂度增加、学习成本
```
