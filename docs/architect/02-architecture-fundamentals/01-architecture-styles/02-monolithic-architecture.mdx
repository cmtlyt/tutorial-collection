## 🏗️ 分层架构（Layered Architecture）

### 什么是分层架构？

分层架构是最经典的软件架构模式，通过将系统划分为若干水平层次，每层负责特定的职责，层与层之间通过接口进行交互。

### 理论基础：关注点分离原则（Separation of Concerns）

关注点分离是软件设计的**核心原则**，由 Edsger W. Dijkstra 在 1974 年提出：

> "将系统分解为相互独立、互不重叠的部分，每个部分解决一个特定的问题。"

#### 原则内涵

1. **单一职责**：每个组件只负责一个明确的功能领域
2. **高内聚**：相关的功能应该聚集在一起
3. **低耦合**：组件之间的依赖关系应该最小化
4. **接口隔离**：通过明确定义的接口进行交互

#### 在分层架构中的应用

```
┌─────────────────────────────────┐
│         表现层 (Presentation)    │  ← 用户交互、请求处理
├─────────────────────────────────┤
│         业务层 (Business)        │  ← 业务逻辑、规则验证
├─────────────────────────────────┤
│         持久层 (Persistence)     │  ← 数据访问、ORM 映射
├─────────────────────────────────┤
│         数据层 (Database)        │  ← 数据存储
└─────────────────────────────────┘

每一层只关注自己的职责，通过接口与上下层交互
```

### 表现层架构模式理论

#### MVC（Model-View-Controller）

MVC 是最古老的表现层架构模式，由 Trygve Reenskaug 在 1979 年为 Smalltalk-80 设计。

**核心思想**：将应用分为三个相互协作的组件

| 组件 | 职责 | 特点 |
|------|------|------|
| **Model（模型）** | 数据和业务逻辑 | 独立于视图和控制器 |
| **View（视图）** | 用户界面展示 | 被动显示模型数据 |
| **Controller（控制器）** | 处理用户输入 | 协调模型和视图 |

**数据流向**：
```
用户输入 → Controller → Model 更新 → View 更新 → 用户看到结果
```

**优势**：
- 关注点分离清晰
- 模型可被多个视图复用
- 便于测试和维护

**局限**：
- 视图和控制器紧密耦合
- 复杂应用的控制器容易变得臃肿

#### MVP（Model-View-Presenter）

MVP 是 MVC 的演进版本，主要改进是**视图和模型的完全解耦**。

**核心改进**：
- 视图完全被动，不直接与模型交互
- 所有交互通过 Presenter 中介
- Presenter 处理所有业务逻辑

**数据流向**：
```
用户输入 → View → Presenter → Model → Presenter → View 更新
```

**与 MVC 的区别**：

| 维度 | MVC | MVP |
|------|-----|-----|
| 视图与模型 | 直接交互 | 完全解耦 |
| 控制器职责 | 路由和简单协调 | 复杂业务逻辑 |
| 测试性 | 较难（视图耦合） | 容易（视图可 mock） |

#### MVVM（Model-View-ViewModel）

MVVM 是 Microsoft 为 WPF 设计的模式，引入了**数据绑定**的概念。

**核心创新**：
- ViewModel 暴露可观察的属性
- View 通过数据绑定自动更新
- 双向绑定简化状态管理

**数据流向**：
```
用户输入 → View ←→ ViewModel → Model
           ↑         ↓
        自动更新    数据绑定
```

**适用场景**：
- 需要大量 UI 状态管理
- 实时数据展示和更新
- 前端框架（Vue.js、Angular、React + MobX）

### 分层架构的理论分类

#### 严格分层 vs 松散分层

**严格分层（Strict Layering）**：
- 只能访问相邻的下一层
- 优点：依赖关系清晰，易于理解
- 缺点：可能需要不必要的转发

**松散分层（Relaxed Layering）**：
- 可以访问下方的任意层
- 优点：减少不必要的转发
- 缺点：依赖关系复杂，难以维护

#### 分层粒度

| 粒度 | 层次 | 适用场景 |
|------|------|---------|
| **粗粒度** | 3 层（表现、业务、数据） | 简单应用、快速开发 |
| **中粒度** | 4-5 层 | 标准企业应用 |
| **细粒度** | 6+ 层 | 复杂系统、特定领域 |

### 分层架构的反模式

#### 架构坍塌（Architecture Sinkhole）

**定义**：请求简单地穿过各层而不做任何有意义的处理。

**示例**：
```
表现层：直接传递请求到业务层
业务层：直接调用持久层方法
持久层：直接查询数据库

结果：各层形同虚设，没有实际价值
```

**解决方案**：
- 确保每层都有明确的职责
- 避免无意义的"传递式"方法
- 定期审查代码，识别坍塌层

### 典型四层结构

```
┌─────────────────────────────────┐
│         表现层 (Presentation)    │  ← 处理用户交互、请求响应
├─────────────────────────────────┤
│         业务层 (Business)        │  ← 核心业务逻辑
├─────────────────────────────────┤
│         持久层 (Persistence)     │  ← 数据访问与存储
├─────────────────────────────────┤
│         数据层 (Database)        │  ← 数据库
└─────────────────────────────────┘
```

### 代码示例：分层架构的实现

以一个订单系统为例，展示各层的职责和交互方式：

```js
// ========== 数据访问层（Persistence Layer）==========
class OrderRepository {
  constructor() {
    this.orders = new Map();
    this.nextId = 1;
  }

  save(orderData) {
    const orderId = this.nextId++;
    const order = { id: orderId, ...orderData, createdAt: new Date().toISOString() };
    this.orders.set(orderId, order);
    return order;
  }

  findById(orderId) {
    return this.orders.get(orderId) || null;
  }

  findByUserId(userId) {
    return Array.from(this.orders.values()).filter(order => order.userId === userId);
  }

  updateStatus(orderId, status) {
    const order = this.orders.get(orderId);
    if (!order) return null;
    order.status = status;
    order.updatedAt = new Date().toISOString();
    return order;
  }
}

// ========== 业务逻辑层（Business Layer）==========
class OrderService {
  constructor(orderRepository) {
    this.orderRepository = orderRepository;
  }

  createOrder(userId, items) {
    if (!items || items.length === 0) {
      throw new Error('订单必须包含至少一个商品');
    }

    const totalAmount = items.reduce((sum, item) => {
      if (item.quantity <= 0) {
        throw new Error(`商品 ${item.name} 的数量必须大于 0`);
      }
      return sum + item.price * item.quantity;
    }, 0);

    return this.orderRepository.save({
      userId,
      items,
      totalAmount,
      status: 'pending',
    });
  }

  getOrder(orderId) {
    const order = this.orderRepository.findById(orderId);
    if (!order) {
      throw new Error(`订单 ${orderId} 不存在`);
    }
    return order;
  }

  confirmOrder(orderId) {
    const order = this.getOrder(orderId);
    if (order.status !== 'pending') {
      throw new Error(`订单 ${orderId} 当前状态为 ${order.status}，无法确认`);
    }
    return this.orderRepository.updateStatus(orderId, 'confirmed');
  }
}

// ========== 表现层（Presentation Layer）==========
class OrderController {
  constructor(orderService) {
    this.orderService = orderService;
  }

  handleCreateOrder(requestBody) {
    try {
      const { userId, items } = requestBody;
      const order = this.orderService.createOrder(userId, items);
      return { status: 201, body: { message: '订单创建成功', data: order } };
    } catch (error) {
      return { status: 400, body: { message: error.message } };
    }
  }

  handleGetOrder(orderId) {
    try {
      const order = this.orderService.getOrder(orderId);
      return { status: 200, body: { data: order } };
    } catch (error) {
      return { status: 404, body: { message: error.message } };
    }
  }

  handleConfirmOrder(orderId) {
    try {
      const order = this.orderService.confirmOrder(orderId);
      return { status: 200, body: { message: '订单已确认', data: order } };
    } catch (error) {
      return { status: 400, body: { message: error.message } };
    }
  }
}

// ========== 组装与运行 ==========
const orderRepository = new OrderRepository();
const orderService = new OrderService(orderRepository);
const orderController = new OrderController(orderService);

const createResult = orderController.handleCreateOrder({
  userId: 'user-001',
  items: [
    { name: '机械键盘', price: 599, quantity: 1 },
    { name: '鼠标垫', price: 49, quantity: 2 },
  ],
});
console.log('创建订单:', createResult);

const confirmResult = orderController.handleConfirmOrder(1);
console.log('确认订单:', confirmResult);
```

### 分层架构的关键规则

| 规则 | 说明 |
|------|------|
| **单向依赖** | 上层依赖下层，下层不能依赖上层 |
| **跨层调用** | 严格分层禁止跨层调用；松散分层允许跨层 |
| **职责隔离** | 每层只处理自己职责范围内的逻辑 |
| **接口抽象** | 层与层之间通过接口交互，降低耦合 |

### 优缺点分析

**优势**：
- **简单直观**：大多数开发者都熟悉这种模式
- **职责清晰**：每层职责明确，易于理解和维护
- **易于测试**：可以对每层单独进行单元测试
- **技术成熟**：大量框架（如 Spring MVC、Express.js）原生支持

**局限**：
- **架构坍塌（Architecture Sinkhole）**：请求简单地穿过各层而不做任何有意义的处理
- **部署耦合**：任何层的修改都需要重新部署整个应用
- **扩展困难**：无法对单个层独立扩展
- **团队协作瓶颈**：大团队在同一代码库上工作容易冲突

## 📦 模块化单体（Modular Monolith）

### 什么是模块化单体？

模块化单体是分层架构的演进方案，它将系统按**业务能力**划分为多个独立模块，每个模块内部自包含，模块之间通过明确定义的接口通信。

### 架构图示

```
┌──────────────────────────────────────────────┐
│                  单体应用                      │
│                                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ 订单模块  │  │ 用户模块  │  │ 支付模块  │   │
│  │          │  │          │  │          │   │
│  │ Controller│  │ Controller│  │ Controller│   │
│  │ Service  │  │ Service  │  │ Service  │   │
│  │ Repository│  │ Repository│  │ Repository│   │
│  │ Model    │  │ Model    │  │ Model    │   │
│  └─────┬────┘  └─────┬────┘  └─────┬────┘   │
│        │             │             │         │
│  ┌─────┴─────────────┴─────────────┴─────┐   │
│  │           共享基础设施层                 │   │
│  │    (数据库连接、日志、配置、安全)        │   │
│  └───────────────────────────────────────┘   │
└──────────────────────────────────────────────┘
```

### 代码示例：模块化单体设计

```js
// ========== 模块接口定义 ==========
// 每个模块对外暴露清晰的公共 API，隐藏内部实现

// 用户模块的公共 API
class UserModule {
  constructor() {
    this.users = new Map();
    this.nextId = 1;
  }

  registerUser(name, email) {
    const userId = `user-${this.nextId++}`;
    const user = { id: userId, name, email, createdAt: new Date().toISOString() };
    this.users.set(userId, user);
    return { id: userId, name, email };
  }

  getUserById(userId) {
    const user = this.users.get(userId);
    if (!user) return null;
    return { id: user.id, name: user.name, email: user.email };
  }

  verifyUserExists(userId) {
    return this.users.has(userId);
  }
}

// 库存模块的公共 API
class InventoryModule {
  constructor() {
    this.stock = new Map();
  }

  addStock(productId, productName, quantity) {
    const existing = this.stock.get(productId) || { productId, productName, quantity: 0 };
    existing.quantity += quantity;
    this.stock.set(productId, existing);
    return existing;
  }

  checkAvailability(productId, requiredQuantity) {
    const item = this.stock.get(productId);
    if (!item) return { available: false, currentStock: 0 };
    return { available: item.quantity >= requiredQuantity, currentStock: item.quantity };
  }

  reserveStock(productId, quantity) {
    const item = this.stock.get(productId);
    if (!item || item.quantity < quantity) {
      throw new Error(`商品 ${productId} 库存不足`);
    }
    item.quantity -= quantity;
    return { productId, reservedQuantity: quantity, remainingStock: item.quantity };
  }
}

// 订单模块：依赖其他模块的公共 API，而非直接访问其内部数据
class OrderModule {
  constructor(userModule, inventoryModule) {
    this.userModule = userModule;
    this.inventoryModule = inventoryModule;
    this.orders = new Map();
    this.nextId = 1;
  }

  createOrder(userId, items) {
    // 通过用户模块的公共 API 验证用户
    if (!this.userModule.verifyUserExists(userId)) {
      throw new Error('用户不存在');
    }

    // 通过库存模块的公共 API 检查并预留库存
    for (const item of items) {
      const availability = this.inventoryModule.checkAvailability(item.productId, item.quantity);
      if (!availability.available) {
        throw new Error(`商品 ${item.productId} 库存不足，当前库存: ${availability.currentStock}`);
      }
    }

    for (const item of items) {
      this.inventoryModule.reserveStock(item.productId, item.quantity);
    }

    const orderId = `order-${this.nextId++}`;
    const totalAmount = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
    const order = { id: orderId, userId, items, totalAmount, status: 'created', createdAt: new Date().toISOString() };
    this.orders.set(orderId, order);
    return order;
  }
}

// ========== 模块组装 ==========
const userModule = new UserModule();
const inventoryModule = new InventoryModule();
const orderModule = new OrderModule(userModule, inventoryModule);

// 初始化数据
userModule.registerUser('张三', 'zhangsan@example.com');
inventoryModule.addStock('prod-001', '机械键盘', 100);
inventoryModule.addStock('prod-002', '鼠标垫', 200);

// 创建订单
const order = orderModule.createOrder('user-1', [
  { productId: 'prod-001', price: 599, quantity: 1 },
  { productId: 'prod-002', price: 49, quantity: 2 },
]);
console.log('订单创建成功:', order);
console.log('键盘剩余库存:', inventoryModule.checkAvailability('prod-001', 1));
```

### 模块化单体的关键原则

1. **模块边界明确**：每个模块有独立的公共 API，禁止直接访问其他模块的内部实现
2. **数据所有权**：每个模块拥有并管理自己的数据，其他模块只能通过 API 访问
3. **独立可测试**：每个模块可以独立进行单元测试和集成测试
4. **渐进式拆分**：未来需要时，可以沿模块边界拆分为独立服务

## 🔄 从单体到微服务的演进路径

### 演进策略

```
经典分层单体
    ↓ 识别业务模块边界
模块化单体
    ↓ 选择高价值模块优先拆分
混合架构（单体 + 部分微服务）
    ↓ 逐步拆分更多模块
完全微服务化（如果确实需要）
```

### 何时保持单体？何时演进？

| 场景 | 建议 |
|------|------|
| 团队少于 10 人 | 保持模块化单体 |
| 业务变化快，频繁试错 | 保持单体，降低试错成本 |
| 各模块需要独立扩展 | 考虑拆分高负载模块 |
| 多团队并行开发，频繁冲突 | 沿模块边界拆分 |
| 需要多语言/多技术栈 | 部分模块独立为服务 |
| 部署频率要求极高（日发布数十次） | 考虑微服务化 |

### 拆分示例：绞杀者模式（Strangler Fig Pattern）

```js
// 绞杀者模式：用新服务逐步替代旧单体中的功能

// 旧单体中的用户服务
class LegacyUserService {
  getUser(userId) {
    console.log(`[旧单体] 查询用户 ${userId}`);
    return { id: userId, name: '旧系统用户', source: 'legacy' };
  }
}

// 新独立的用户微服务
class NewUserService {
  getUser(userId) {
    console.log(`[新服务] 查询用户 ${userId}`);
    return { id: userId, name: '新系统用户', source: 'new-service' };
  }
}

// 代理层：根据功能开关决定调用旧系统还是新系统
class UserServiceProxy {
  constructor(legacyService, newService, featureFlags) {
    this.legacyService = legacyService;
    this.newService = newService;
    this.featureFlags = featureFlags;
  }

  getUser(userId) {
    if (this.featureFlags.useNewUserService) {
      return this.newService.getUser(userId);
    }
    return this.legacyService.getUser(userId);
  }
}

// 使用功能开关平滑切换
const featureFlags = { useNewUserService: false };
const proxy = new UserServiceProxy(new LegacyUserService(), new NewUserService(), featureFlags);

console.log(proxy.getUser('user-1'));   // 调用旧系统
featureFlags.useNewUserService = true;  // 切换到新系统
console.log(proxy.getUser('user-1'));   // 调用新系统
```

## 📊 单体架构对比总结

| 维度 | 经典分层架构 | 模块化单体 |
|------|------------|-----------|
| **组织方式** | 按技术层次划分 | 按业务能力划分 |
| **模块耦合** | 层间松耦合，层内高耦合 | 模块间松耦合 |
| **数据管理** | 共享数据库 | 每模块独立数据空间 |
| **团队协作** | 容易冲突 | 可按模块分配团队 |
| **演进能力** | 重构成本高 | 易于拆分为微服务 |
| **部署** | 整体部署 | 整体部署（但模块独立开发） |
